## 2 核心问题的标准答案

### C01：S0 解决了什么问题？

**标准回答：**

S0 建立本地客户端与 Core 服务之间的通信骨架。Core 启动 TCP 服务，CLI 发送规定格式的 JSON-RPC 请求，Core 分发给处理方法并返回结构化结果。ping/pong 用来验证连接、序列化、校验、分发和响应这条链路。

这一阶段还提供配置加载、日志、错误响应、协议模型及相关测试，为后续执行 Agent 和增加前端准备接口。S0 本身尚未实现模型调用、工具循环和多轮会话。

**面试简答：**“我先把本地双进程通信和协议边界做通，用 ping 验证一次完整 RPC，再让后续 Agent 能力接入这个边界。”

**源码：** [Core 入口](../../src/kama_claude/core/app.py)、[CLI 入口](../../src/kama_claude/cli/main.py)。

### C02：一次 ping 的完整调用链是什么？

**标准回答：**

1. 用户执行 kama ping，CLI 的 main 解析子命令，加载配置和日志。
2. cmd_ping 用 asyncio.run 执行异步 _ping。
3. _ping 用 open_connection 连接 Core，获得 reader、writer。
4. 构造带 id、method、params 的请求，序列化为 JSON，编码成字节并添加换行。
5. write 后 await drain，随后等待读取一行响应。
6. Core 为该连接执行 _handle_connection，_read_loop 读取一行，交给 _handle_line。
7. 服务端解析 JSON、校验请求模型、根据 method 查找 handler。
8. _ping_handler 生成 PongResult，包含服务版本、运行时长和接收时间。
9. 传输层把结果包装成 JsonRpcSuccess，保留请求 ID，序列化并发送。
10. CLI 校验响应外壳和 PongResult，打印 pong、版本、uptime、latency。

当前 CLI 在成功读到响应后先关闭连接，再解析响应；这两个动作的实际顺序可以在 _ping 中确认。错误和超时路径仍有进一步完善资源清理的空间。

**理解检查：**你应该能分别指出哪里处理字节、哪里处理 Python 字典、哪里处理 Pydantic 对象，不能只背“客户端请求、服务端返回”。

**源码：** [ping 命令](../../src/kama_claude/cli/commands/ping.py)、[SocketServer](../../src/kama_claude/core/transport/socket_server.py)。

### C03：CLI 和 Core 为什么分开？

**标准回答：**

CLI 是客户端，负责命令行输入、发请求、显示结果；Core 是独立服务进程，负责接收请求、调用业务方法和管理服务生命周期。启动两个命令就得到两个进程，它们通过 TCP 交换数据，不能像同一进程内那样直接调用彼此对象。

拆分后，Core 可以保持运行，CLI 用完退出；以后 TUI 或其他客户端可以复用同一协议。代价是增加了编码、连接、超时、错误处理和版本兼容问题，因此要先用 S0 的简单业务把边界验证清楚。

这种结构为后续常驻执行做准备；不能因为 Core 名字里有 daemon，就声称 S0 已有完整后台进程管理器。

**追问：客户端退出，Core 会退出吗？**正常情况下不会，两个进程生命周期独立。连接关闭后服务端处理该连接的协程结束，监听服务仍继续等待其他连接。

### C04：TCP 为什么还需要 NDJSON？

**标准回答：**

TCP 提供有序字节流，不承诺一次发送对应一次接收。一个 JSON 可能分多次到达，两个 JSON 也可能一起进入接收缓冲。应用必须自己定义一条消息在哪里结束。

S0 采用 NDJSON：每条消息编码成单行 JSON，末尾加实际换行字节，接收端 readline 按行取消息。完整分帧后再做 JSON 解析。

例如两个消息连续发送：

```text
{"id":"1","method":"core.ping","params":{}}\n
{"id":"2","method":"core.ping","params":{}}\n
```

上面文本中的 `\n` 表示帧尾换行，不是要求发送字面量反斜线和 n。JSON 字符串内部的换行会被编码为转义形式，不会与帧尾换行混淆。

**常见答错：**“TCP 可靠，所以一次 read 能读到完整 JSON。”可靠传输与应用消息边界是不同保证。

### C05：JSON-RPC 各字段有什么用？

**标准回答：**

| 字段 | 本项目中的作用 |
| --- | --- |
| jsonrpc | 标记协议版本，本实现使用 2.0 |
| id | 由客户端提供，响应带回以关联请求 |
| method | 要调用的业务方法名，例如 core.ping |
| params | 传给处理方法的业务参数字典 |
| result | 成功响应中的业务结果 |
| error | 失败响应中的错误码、消息及可选详情 |

JSON-RPC 定义消息语义；本项目另外选择 TCP 传输和换行分帧。协议本身不绑定 TCP。[JSON-RPC 官方规范](https://www.jsonrpc.org/specification)

S0 每次 ping 使用固定字符串 cli-1，在一次新连接只发一个请求的简单场景中足够；未来同连接同时存在多个未完成请求时，应使用不冲突的 ID 并建立响应分发表。该 ID 不能当作全系统永久唯一业务编号。

**理解检查：**jsonrpc=2.0 与 server_version=0.0.1 分别是协议版本和软件版本，两者不能混用。

**源码：** [协议外壳](../../src/kama_claude/core/bus/envelope.py)。

### C06：合法 JSON 为什么还要校验？现在的业务校验完整吗？

**标准回答：**

JSON 解析只确认文本可以变成 Python 数据；它不保证数据是一个包含正确字段和类型的 RPC 请求。比如数字 123 也是合法 JSON，但不是本项目需要的请求对象。

因此第一层 json.loads 解析语法，第二层 JsonRpcRequest.model_validate 校验外壳，第三层应由具体命令模型校验业务参数。通过某一层不代表自动通过所有层。

当前 S0 的 _ping_handler 直接读取 params.get("client", "unknown")，没有调用 PingCommand.model_validate。PingCommand 已定义，但业务校验没有真正接入。这是可以补的小改进，不能在面试中说成“所有命令参数都已严格校验”。

另一个细节：JsonRpcRequest.jsonrpc 有默认值，输入缺少这个字段时模型可能补为 2.0。模型设计和是否完整遵守外部规范，需要逐项核对。

**源码：** [命令模型](../../src/kama_claude/core/bus/commands.py)、[业务 handler](../../src/kama_claude/core/app.py)。

### C07：core.ping 怎样找到 _ping_handler？

**标准回答：**

Core 启动时执行 server.register("core.ping", self._ping_handler)，把字符串名称和异步方法保存到 handlers 字典。收到请求后，用 req.method 查字典，查到后 await handler(req.params)，查不到就返回方法不存在。

register 保存函数引用，不会立即执行函数。真正执行发生在收到请求之后。handler 返回业务对象，传输层再处理请求 ID、成功外壳与网络发送，所以 handler 不必直接操作 writer。

同名 register 会覆盖旧映射。扩展接口时要检查名称冲突，不能只新增函数而忘记注册。

**理解检查：**如果请求 method 改成 core.unknown，应停在字典查找处，不会进入 _ping_handler。

### C08：网络读写方法分别保证什么？

**标准回答：**

write 提交字节到传输层，必要时进入写缓冲；drain 根据缓冲区水位等待，避免持续无节制写入。drain 完成不代表对方业务执行完，业务完成要根据响应判断。[Python 流控说明](https://docs.python.org/3.12/library/asyncio-stream.html#asyncio.StreamWriter.drain)

readline 等待一行数据；如果连接结束且缓冲为空，返回空字节。close 发起关闭，wait_closed 等待流关闭。服务端在 _handle_connection 的 finally 中执行连接清理。

如果连接保持开启又一直不发换行，readline 可以继续等待；如果收到 EOF，则可能返回尚未换行的残留数据。当前客户端还需判断响应是否为空、是否可解析。

**常见答错：**把 drain 理解成“清空全部缓冲并收到对端执行确认”；把 close 理解成“删除 reader/writer 变量”。

### C09：不同错误怎样分类？

**标准回答：**

| 情况 | 当前 S0 的响应 |
| --- | --- |
| JSON 语法错误 | -32700：Parse Error |
| 请求外壳不符合模型 | -32600：Invalid Request |
| method 未注册 | -32601：Method Not Found |
| handler 抛出 ValidationError | 当前也返回 -32600，存在语义缺口 |
| handler 抛出其他普通异常 | -32603：Internal Error |

参数错误应归到 -32602，项目已定义 INVALID_PARAMS 常量，但上述 handler 分支尚未使用它。要修复应同时接入业务校验并验证错误码，而不只是修改一个常量。[JSON-RPC 错误分类](https://www.jsonrpc.org/specification#error_object)

已成功解析外壳的未知方法错误可以带回原请求 ID；无法确认请求 ID 的解析/外壳错误使用 null。服务端内部异常记日志，对客户端返回统一内部错误，避免直接依赖 Python traceback 作为协议。

**理解检查：**手写一个合法外壳但 method 不存在的请求，应能预测响应 id 与 code。

### C10：shutdown.wait 会卡死服务吗？

**标准回答：**

await shutdown.wait 只暂停 Core 的主协程，事件循环仍可调度其他已经注册的工作。asyncio.start_server 接受新连接后，会为异步连接回调安排任务，继续处理客户端读写。

async 并不意味着每个方法在独立线程执行。异步等待网络时可以让其他协程工作；如果在同一事件循环里直接执行长时间同步计算或阻塞调用，其他连接也会受影响。

还要区分连接之间与同一连接内：不同连接可以并发等待；S0 的 _read_loop 会 await 当前 _handle_line 完成，再读取同连接的下一条请求，所以同连接的业务分发是顺序的。

**追问：为什么同一连接先处理完再读下一条？**实现简单，适合 ping；后续若有长任务与需要新消息完成的审批，就必须重新设计接收与执行的关系。

### C11：配置优先级与时间计算怎么解释？

**标准回答：**

有效配置从低到高是：内置默认值 → TOML 文件 → .env → 已有系统环境变量。实现先 load_dotenv(override=False)，使已有系统变量不被覆盖，再决定 KAMA_CONFIG 路径、读 TOML，最后应用环境变量。

所以 .env 在执行顺序上较早加载，不代表它最终优先级低于 TOML。例如默认端口 7437、TOML 6000、.env 7000、系统变量 8000，最终为 8000。两个终端分别运行客户端和服务端时，应使用一致的 host/port 配置。

时间分两种：time.monotonic 的差值用于 uptime 和 latency，避免系统墙上时钟调整影响时长；UTC 时间字符串用于描述接收请求的时间点。monotonic 的绝对值没有普通日期含义，不应当作日志日期展示。

当前 CLI 的 latency 从连接前计时到收到响应，包含连接、传输和服务端处理等时间，不是纯粹的 handler 耗时。

**源码：** [配置加载](../../src/kama_claude/core/config.py)、[ping 计时](../../src/kama_claude/cli/commands/ping.py)。

### C12：Core 的生命周期与 Windows 适配怎么解释？

**标准回答：**

启动阶段加载配置、初始化日志、创建服务器并注册方法，然后启动监听。运行阶段主协程等待退出通知，连接协程处理请求。退出阶段停止监听，等待服务器关闭。

原始 S0 无条件调用 loop.add_signal_handler 注册 SIGINT、SIGTERM，Windows 的 asyncio 不支持这个接口，因此启动会抛 NotImplementedError。[Python Windows 平台限制](https://docs.python.org/zh-cn/3.12/library/asyncio-platforms.html#windows)

当前修改让 Windows 跳过该注册，正常前台运行时由 Python 3.12 asyncio.run 的 Ctrl+C 处理取消主任务；用 finally 执行 server.stop；最外层捕获 KeyboardInterrupt，使用户主动退出不显示异常堆栈。macOS/Linux 仍保留原有信号通知路径。[Python Ctrl+C 处理说明](https://docs.python.org/3.12/library/asyncio-runner.html#handling-keyboard-interruption)

关键是清理放在 finally，而不是普通 await 后：任务取消时，await 会抛出取消异常，普通后续代码可能被跳过。最外层捕获中断只是退出表现，实际资源清理由 finally 完成。

该适配针对当前 S0 前台 Core 与 ping。强制终止进程未必执行 finally；SocketServer.stop 主要关闭监听，也不是完整的所有活跃任务排空方案。

**源码：** [修复后的 Core](../../src/kama_claude/core/app.py)、[生命周期回归](../../tests/unit/test_core_app.py)。

## 3 面试中可能继续追问的 8 个问题

### M01：为什么选择 TCP？HTTP、Unix Socket 行不行？

**标准回答：**

当前项目用本地 TCP、JSON-RPC 和换行分帧，实现了一条简单且能扩展为持续连接的命令通道。TCP 的客户端接口在多个系统上都有对应实现，但整个应用是否跨平台，还取决于信号、进程和工具代码，本次 Windows 问题正说明这一点。

HTTP 或 Unix Socket 都是可比较方案。HTTP 适合复用成熟接口和工具；Unix Socket 适合同机进程通信，但要考虑目标平台的具体支持。本项目没有基准测试证明 TCP 比 HTTP 更快，所以我不会把“性能最好”作为已经证明的选择理由。

**面试官可能继续问：**将来换传输，哪些能复用？答：业务 handler、结果模型和部分错误语义可复用，连接管理与分帧适配需要替换。

### M02：你说用了 asyncio，是不是就支持高并发？

**标准回答：**

当前支持多个连接在 I/O 等待期间交错运行，但没有做高并发能力的系统性证明。是否承受高负载还取决于 handler 是否阻塞、连接和队列是否有界、超时、内存及关闭策略。

S0 在同一连接内顺序处理请求，没有实现请求多路复用。若未来增加长任务，要先定义请求关联和生命周期，再考虑并发数量及背压，不能只把调用换成 create_task 就宣称完成高并发架构。

**答题重点：**区分“异步机制”“并发路径”“容量与性能指标”，只描述测过的保证。

### M03：启动前能连接端口，为什么还不能断定已有正确的 Core？

**标准回答：**

端口接受连接，只能证明有监听进程，可能是其他程序。当前 start 探测能给出占用提示，但没有发真正 ping 校验返回的协议与版本，所以提示“core already running”比实际证据更强。

改进可以把端口占用与协议健康检查分开：建立连接后发 ping、校验响应，再判断是不是兼容的 Core。探测和真正 bind 之间仍有竞争窗口，最终 bind 失败也必须处理。

**理解检查：**能说明为什么“先检查空闲”无法替代操作系统最终的端口绑定结果。

### M04：Core 无响应时怎么办？当前超时和清理有什么不足？

**标准回答：**

当前 CLI 用 wait_for 给读取一行响应设置 10 秒超时，防止一直等响应。但这个限制没有覆盖之前的连接建立，不能说整个 ping 严格最多 10 秒。

客户端 writer 的 close/wait_closed 放在成功读取之后；读取异常时没有统一 finally，因此可以改成连接成功后在 finally 中关闭。错误展示也应区分连接拒绝、连接建立超时、响应超时、EOF、坏 JSON 和响应模型错误。

Python 3.12 的 TimeoutError 属于 OSError，所以当前 cmd_ping 可能把响应超时也显示为 core not running。这个提示便于快速反馈，但定位不准确。

**改进验收：**用一个接受连接但不回复的假服务复现超时，验证错误分类、退出码和连接清理，不靠真实服务碰巧变慢。

### M05：对方一直不发换行，或者发特别长的一行怎么办？

**标准回答：**

连接一直保持又不发换行时，readline 会等待；当前服务端没有为每次读行显式设置超时。它设置了约 1 MiB 的读取 limit，可以限制大行读取，但还需要核对超限异常实际如何抛出，以及是否只关闭问题连接。

当前代码捕获 LimitOverrunError；Python 3.12 的 readline 在某些超限情况下会包装成 ValueError，因此不能仅看到 except 就认定超限分支已经验证。后续应使用超长行、慢速半行、连接中断测试实际行为，再完善异常与清理。

目标是：问题连接可识别、可关闭，正常客户端仍能 ping；进一步再限制连接数量和空闲等待。本文列的是改进方向，当前最小 Windows 修复没有同时完成这些功能。

### M08：你自己的 Windows 改进，怎样讲清楚价值和边界？

**可直接练习的标准回答：**

“我在 S0 的 Windows 环境运行时发现，Core 在启动后无条件注册 asyncio 信号处理器，会抛 NotImplementedError。我沿启动链定位到 add_signal_handler，这是平台接口差异。

我保留了 Unix 的信号处理，在 Windows 下使用 Python 3.12 asyncio.run 的 Ctrl+C 取消机制，并把服务器清理放进 finally，外层处理 KeyboardInterrupt，保证正常用户退出时完成监听关闭。

验证包括原问题回归、取消清理、模拟 Unix 信号路径、真实 daemon 的 TCP 往返，以及 Windows 下触发 SIGINT 后的端口重启。这个修复解决当前 S0 前台运行的兼容问题，后续后台进程管理和工具执行还要继续验证。”

**可能的追问与回答：**

- 为什么不只 catch KeyboardInterrupt？最外层不再报堆栈，不代表服务器清理执行，清理要在异步生命周期的 finally 中落实。
- 为什么不能删掉所有信号代码？需要保留 Unix 上 SIGTERM 的原有退出行为，并对目标平台分别适配。
- finally 是否任何时候都会执行？正常异常和任务取消通常会经过它；进程被强制终止、系统崩溃等情况不能依赖它。
- 这算性能优化吗？这项贡献是兼容性和生命周期正确性修复，没有测量就不写性能提升百分比。
