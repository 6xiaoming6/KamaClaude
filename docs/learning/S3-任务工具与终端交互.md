# S3 任务工具与终端交互

基准：`origin/stage/s3`，提交 `16bbe3b`。S3 扩充为八种工具，引入持久化任务记录、并发顶层 run、可折叠 TUI 块和 Trace。Trace 内容较独立，放在 [系统时间线](Trace-系统时间线.md) 中继续学习。

## 1 为什么任务列表也要成为工具

复杂目标往往需要“先分析、再实现、再验证”。只让模型在文本里说计划，程序无法可靠查询每一步的状态。把计划转换为结构化 task，模型就可以通过工具创建、查询和更新它。

但此阶段的任务系统不是调度器。它记录依赖和状态，没有一个程序循环根据依赖自动启动工作，也没有强制所有依赖完成后才能把任务标记为 in_progress。实际选择下一步的仍然是模型。

理解这点之后再看“自主规划”：自主的部分是模型决定调用哪个任务工具、写什么任务、执行什么动作；工程的部分是把这些决策保存、返回和展示。

## 3 八工具的分工

| 工具 | 输入重点 | 输出或副作用 |
| --- | --- | --- |
| read_file | path | 读取文本，上限返回前 512 KiB |
| list_dir | path、max_depth | 目录树，最大深度 4、最多约 200 条目 |
| write_file | path、content | 创建父目录并覆盖写文件，内容最多 1 MiB |
| bash | command、timeout | shell 子进程，合并 stdout/stderr |
| task_create | subject、description、blocked_by | 新任务 JSON |
| task_update | task_id、status、增减依赖 | 更新任务 JSON |
| task_list | 无必需业务参数 | 人类可读任务摘要 |
| task_get | task_id | 单个任务详细 JSON |

文件工具的路径相对 Core 的工作目录，因为执行发生在 daemon 内。客户端从另一个目录启动并不会自动改变 daemon 的 cwd。此阶段也没有把 workspace 参数作为每次 run 的执行边界。

## 4 用三个任务理解依赖管理

例子：任务 1“检查输入格式”；任务 2“实现转换”，blocked_by=[1]；任务 3“运行验证”，blocked_by=[2]。

TaskManager 保存在 `runs/<run_id>/.tasks/task_<id>.json`。初始化时扫描最大 ID，下一次创建加一。`create()` 会检查初始依赖 ID 对应文件是否存在。

当 `update(1, status="completed")` 被调用，`_clear_dependency(1)` 扫描其他任务文件，把 1 从它们的 blocked_by 删除。于是任务 2 的阻塞列表变空。这个行为方便模型识别“目前还有哪些未完成依赖”，但也会丢掉原始依赖关系：事后无法单靠 blocked_by 还原整个计划图。

还要注意：`update()` 添加依赖时没有与 create 同等完整的有效性检查，没有环检测，也没有拒绝自依赖。pending、in_progress、completed 是允许的状态值，不是一个严格状态迁移表；调用者可能把 completed 改回 pending。

可以用这一段教学伪代码理解它的边界：

```text
模型：创建任务 1、2、3
模型：把任务 2 设为进行中
程序：保存状态，并不因任务 1 未完成自动拒绝
模型：完成任务 1
程序：把其他任务对 1 的未完成依赖移除
```

因此面试可以说“实现了模型可操作的任务管理与依赖记录”，若要说“DAG 调度引擎”，还需要状态约束、环检测、就绪队列和调度策略等实现。

## 5 shell 工具带来的新复杂度

`BashTool.invoke()` 调用 `asyncio.create_subprocess_shell()`，等待 `proc.communicate()`。stdout 和 stderr 合并为一个输出；非零退出码返回 is_error=True。

S3 工具内部默认等待 60 秒，参数最多 120 秒，但统一 `invoke_tool()` 仍沿用 S1 的默认 10 秒外层超时。外层取消可能先发生，内部只处理自身 TimeoutError，没有完整的外部取消清理路径。于是“工具允许 60 秒”并不表示实际能跑满 60 秒。

输出代码先完整收集，再根据字节数判断是否超过 64 KiB，随后切的是解码后的字符串。它限制的是返回展示大小，未限制子进程产生多少输出，也存在字节与字符单位不一致。对大量输出更合理的是流式读取、分别限制内存与落盘大小。

S3 尚无 S5 的审批。做实验应限定在专门的练习文件和可重复的只读命令上。这里的重点是理解执行和副作用，不能把“有超时”当成“已经沙箱化”。

## 6 TUI 如何表达执行过程

S2 用 RichLog，S3 改成 VerticalScroll 中的一组控件。`LLMStreamBlock` 在同一个文本块上追加片段，避免每个 token 都成为一行。遇到非 token 事件时 `_break_llm()` 结束当前块，下次 token 创建新块。

`ToolCallBlock` 保存工具名、参数、输出、耗时和完成状态。收到 `tool.call_started` 时创建控件并放入 `_pending_tool_blocks[tool_use_id]`；收到 finished 或 failed 时按 ID 找回、更新，并从 pending 表移除。点击已完成块切换详情展开。

S3 同时把 `output` 放入工具完成事件，让 TUI 能展示结果。展示层消费事件，不直接读取工具实例。这样更换 UI 不必修改工具执行代码。

此时 TUI 仍主要是观察器，没有 S4 的聊天输入。不要照最终版本截图去找本阶段尚未存在的输入框。

## 7 并发 run 的得与失

Core 从单个 `_current_run_task` 改为 `_running_runs` 集合：每次 create_task 加入集合，完成回调移除；退出时取消并 gather 当前运行任务。

这允许多个顶层 run 同时推进，但它们仍共享 Core cwd、事件总线和可操作文件。并发不等于隔离。两个任务写同一个文件可能覆盖；不同 run 的事件可能进入同一个订阅者；一个全局 token 文本块可能混合并行输出。

Runner 的 EventWriter 没有按 run_id 过滤，因此并发存在日志串写风险。这个风险要追踪“谁共享 bus”，不能只看每个 run 有独立目录就以为完全隔离。

## 8 动手实验

运行对应阶段单元测试：

```powershell
uv run pytest tests/unit/test_task_model.py tests/unit/test_task_manager.py tests/unit/test_builtin_tools.py tests/unit/test_tui_app.py -v
```

S3 还包含 `tests/integration/test_s3_task_graph.py`，它在 S4 被删除；需要在 S3 分支阅读和执行，不能在 main 上找不到文件后误以为文档引用错误。

实验一：直接实例化 TaskManager，创建上述三个任务，保存每次任务 JSON。将任务 1 标 completed，检查任务 2 的依赖删除。这能把模型随机性排除掉。

实验二：给未完成前置的任务设置 in_progress，观察当前代码是否拒绝；再尝试构造环。记录现状后决定自己希望的约束，不要把预期当成代码事实。

实验三：让两个 FakeProvider 同时运行，给事件带不同 run_id，检查两个 events 文件是否只含自己。可以用这个小实验为 S8 建立可复现基线。

实验四：手动向 TUI 送一组 started、finished 事件，验证工具块能按 ID 更新。UI 测试不必每次都消耗模型调用。

## 9 面试问题

**为什么任务也是工具？** 模型已通过工具协议与宿主交互，任务管理复用这个接口，可以结构化保存计划并让后续模型查询。

**任务依赖能保证执行顺序吗？** 当前只能记录未完成依赖，没有强制门禁。执行顺序主要靠模型遵循描述；改进时应在后端验证。

**多个 run 与多个工具并行是一回事吗？** 不是。S3 允许多个顶层 run 并发，但每次响应内的工具仍由循环逐个 await。

**为什么前端只看事件？** 让运行与显示分离，同时支持历史回放和不同客户端；代价是必须维护事件关联与状态一致性。

## 10 核心方法逐个精读

### 10.1 AgentRunner._build_registry

输入一个 TaskManager，返回新 ToolRegistry。文件和 shell 工具各自实例化；四个任务工具都收到同一个 TaskManager，所以它们操作同一任务目录。

如果 task_create 和 task_list 使用不同 Manager 指向不同目录，模型刚创建的任务就会“查不到”。依赖注入不仅用于测试，也用于保证多个功能共享正确的业务状态。

### 10.2 AgentRunner.run 与 run_and_capture

S3 的 run 不再独自承载完整逻辑，而是 await run_and_capture 并忽略返回值。`run_and_capture(goal, run_id=None)` 创建运行目录和 TaskManager，装配 Loop，结束后返回 RunOutcome，包含 status、result、reason。

相较 S1/S2，增加返回对象让其他代码可以直接获得最终文本。Loop 在 end_turn 时保存 context.result，Runner 再复制到 RunOutcome。运行事件和返回结果仍是两条通道：调用者可以等待结果，观察者通过 Bus 看过程。

### 10.3 Task.to_dict 与 Task.from_dict

Task 是内部 dataclass，字段包含整数 ID、标题、描述、状态、blocked_by 和时间。to_dict 把这些字段变成 JSON 可写的普通字典；from_dict 从持久化字典重建对象，并对部分值做 int/str 转换。

这里不是完整强类型反序列化，状态等仍可能来自缺乏严格验证的磁盘数据。不要因为 TaskStatus 是 Literal 就认为 from_dict 会自动拒绝任意坏状态。

### 10.4 TaskManager.__init__ 与 _max_id

构造器接收 tasks_dir，创建目录，再用 `_max_id()+1` 初始化下一任务编号。_max_id 扫描 task_*.json，从文件名提取数字，空目录返回 0。

因此重建同一个目录的 Manager 时，通常不会从 1 覆盖已有任务。它靠文件名推断编号，没有跨进程唯一性保证；两个独立写者同时创建时仍可能争用同一个 ID。

### 10.5 TaskManager._load 与 _save

`_load(task_id)` 组合路径、检查存在、读取 JSON、Task.from_dict；不存在抛 ValueError。`_save(task)` 把 to_dict 后的 JSON 覆盖写进对应文件，没有返回业务结果。

_load 的路径由整数 task_id 形成；_save 没有临时文件加原子替换。写入中途故障可能留下半个 JSON，所以“文件持久化”并不自动等于“事务安全”。

### 10.6 TaskManager.create

输入 subject、description、blocked_by。先检查每个初始依赖文件是否存在；再取当前时间，构造 pending 状态 Task，写盘；写成功后 `_next_id += 1`，最后返回 Task。

编号自增放在保存之后，避免正常保存失败却已经把编号消耗掉。不过它没有数据库事务，多个文件或多个写者的一致性仍需额外处理。

例如 create("实现功能", blocked_by=[1]) 不会执行任务 1，也不会等待它完成；只验证依赖存在，然后记录关系。

### 10.7 TaskManager.get 与 list_all

get 是 _load 的公开入口。list_all 按文件名中的数字排序逐个读取，将能解析的记录转换为 Task 列表，部分格式异常会被跳过。

数字排序让 task_2 在 task_10 前，而不是按普通字符串排序排错。跳过坏记录能让列表继续显示，但可能掩盖缺失任务，应在改进时记录可见诊断。

### 10.8 TaskManager.update

先加载指定任务。若提供 status，检查它属于三个允许值并修改；若新状态 completed，调用 _clear_dependency；然后处理新增和删除依赖，更新时间，保存并返回。

这个顺序意味一次更新可能先改其他文件，再保存当前任务。若最后写当前文件失败，其他任务的依赖可能已被删除。研究事务问题时，不能只盯住“一个 JSON 文件写得是否正确”。

add_blocked_by 用 set 去重，但不保证原顺序；remove 则过滤指定 ID。它没有在本方法中强制依赖完成或检测环。

### 10.9 _clear_dependency 与 format_list

`_clear_dependency(completed_id)` 扫描其他任务文件，把该 ID 从 blocked_by 移除并更新时间。返回 None，副作用是可能改多个文件。它没有保存“原来依赖过谁”的独立图。

`format_list()` 先 list_all，再把 pending/in_progress/completed 映射为 `[ ]/[>]/[x]`，拼接标题和仍阻塞的 ID；空列表返回 No tasks。它服务于模型快速阅读，不是机器可依赖的完整 JSON 协议。

### 10.10 四个任务工具的 invoke

TaskCreateTool.invoke 把模型参数转成标题、描述、整数依赖，调用 manager.create，再把 task.to_dict 序列化为字符串塞进 ToolResult。TaskGetTool.invoke 解析 task_id，调用 manager.get 并返回 JSON。TaskListTool.invoke 直接调用 format_list。TaskUpdateTool.invoke 解析 ID、状态与增减依赖，再 manager.update 并返回 JSON。

这些工具是适配层：模型给通用字典，Manager 接收较明确的 Python 参数；Manager 返回 Task，工具转成模型可读文本。它们不另写一套任务业务逻辑。

注意部分 int 转换发生在工具自身 try 之前，转换异常仍可能往外抛，由统一 invoke_tool 处理。因此“工具中有 except ValueError”不代表它捕获了函数内每一次 ValueError。

### 10.11 WriteFileTool.invoke

读取 path 与 content，检查 `..`，把 content 编成 UTF-8 计算字节大小，超过 1 MiB 返回错误结果；否则创建父目录，用 UTF-8 覆盖写文件，返回写入字节数和路径。

这是有副作用方法：返回成功前文件已改变。文件原先有内容时被覆盖，并非追加，也没有自动 diff 审核或备份。字符数和字节数不同，中文通常占多字节，所以这里先 encode 再判断大小。

### 10.12 ListDirTool.invoke 与局部 _walk

解析路径和最大深度，检查目标存在且是目录，准备 lines 和 count。内部 `_walk(directory, depth, prefix)` 递归遍历，把树形连接符和文件名追加到 lines；nonlocal count 表示所有递归层共享同一个计数。

停止条件包含深度和总条目上限，防止无限大目录树。输出是拼好的字符串，返回后模型再根据路径决定读哪个文件。工具不会自动把目录中所有文件内容读出。

跟踪递归时分别记住三个变量：depth 表示当前层，prefix 决定缩进，count 表示累计条目。它们不是同一个计数器。

### 10.13 BashTool.invoke

解析命令和 timeout，启动 shell 子进程，把 stderr 合并进 stdout，再等待 communicate。内部超时则 kill 当前 proc 并等待输出收尾，返回 timeout 错误；成功取到输出后 decode，做长度处理，检查 returncode 决定 is_error。

proc 是进程句柄，communicate 是等待退出并收集输出的操作，returncode 是退出码。普通命令输出包含单词 error 并不必然表示失败；本工具主要看退出码。反过来，命令不输出文字也可能成功，返回 `[no output]`。

外层调用超时会取消此协程，而内部只明确处理自己 wait_for 的 TimeoutError，所以要分别测试两层取消。清理 shell 句柄还不自动等于清理它创建的全部后代进程。

### 10.14 CoreApp._agent_run_handler 的 S3 变化

移除了 S2 的单 run 拒绝判断，改成创建 task 后加入 `_running_runs` set，并通过 add_done_callback(discard) 在完成时移除。集合持有活跃任务引用，Core 退出时遍历取消并 gather。

这个集合管理生命周期，不提供资源配额、文件锁或业务排序。并发能力来自多个协程被调度，隔离能力要由上下文、事件路由和存储边界另外保证。

### 10.15 LLMStreamBlock.__init__ 与 append_token

创建控件时文本为空。append_token 把新片段追加到 `_text`，调用 update 刷新同一控件。输入 token 是展示片段，不负责解析工具 schema。

S3 没有 S4 的 finalize_markdown；最终 Markdown 渲染属于下一阶段增量。按阶段理解 UI 方法，能看出代码如何逐步增加能力。

### 10.16 ToolCallBlock 的方法组

构造器保存工具名称、参数全文、空输出、耗时和完成标志。compose 产生 summary 与 detail 两个子控件。`_summary()` 根据状态拼短文本；`set_result(output, elapsed_ms, is_error)` 保存完成数据并刷新摘要。

`on_click()` 在未完成时直接返回；完成后切换 expanded 类，需要展开时把完整参数、输出和耗时填到 detail。CSS 根据类决定是否显示。业务数据保存在控件对象，展开收起只是显示状态，不会重新调用工具。

### 10.17 KamaTuiApp 的事件路由

`_append(widget)` 把新控件 mount 到滚动区并滚到末尾；`_break_llm()` 清掉当前流式块引用；`_handle_event(event)` 按 type 分支，token 进入当前文本块，工具 started 创建并登记块，finished/failed 用 tool_use_id 找回更新。

“登记 → 后来按 ID 找回 → 完成后移除”与 SocketClient 的 pending Future 思路相似，只是这里等待的是 UI 状态更新，不是 RPC 返回值。

## 11 两个手工执行练习

**练习一：依赖变化。** 初始任务 2 的 blocked_by=[1]。执行 update(1,status="completed")，依次写出 _load、修改状态、_clear_dependency、_save 的文件副作用。参考结果：任务 2 依赖被删除，任务 1 标 completed；若最后保存任务 1 失败，两份文件就可能不一致。

**练习二：工具块。** 先给 TUI tool.call_started(id=A)，再给 tool.call_started(id=B)，然后先完成 B 再完成 A。参考结果：必须按 tool_use_id 更新对应块，不能用“最后一个块”猜。接着把 A/B 放进两个并发 run，思考是否还需要把 run_id 纳入键。

## 12 本阶段可改进的地方

| 改进 | 修改点与实现思路 | 验收 |
| --- | --- | --- |
| 强制任务依赖 | TaskManager.update 检查前置状态、存在性和环；保留原始依赖 | 阻塞任务不能启动；环被拒绝；完成后可查询原图 |
| 原子任务写入 | 临时文件写好后替换，必要时加版本号 | 写中断不会损坏原任务，旧版本更新被识别 |
| 子进程取消清理 | 统一外层和内部超时；finally 清理进程及子进程 | 超时/取消后无遗留执行者 |
| 工作区与文件冲突 | 每 run 明确 workspace，写入加冲突检测 | 两个任务修改同文件时可检测而非静默覆盖 |
| TUI 并发视图 | token 块按 run_id 管理，支持会话筛选 | A/B 输出交错时仍各自完整 |

先做任务依赖约束适合练算法和状态机；先做事件隔离适合练后端异步系统。不要同时扩展成庞大的调度平台。
