# S4 会话与持久化记忆

基准：`origin/stage/s4`，提交 `9ffbcc4`。S4 在多个 run 之上增加 session，把历史和重要事实带到下一轮，并在 TUI 中增加输入能力。

## 1 为什么不能只复用一个 messages 列表

一个永远增长的内存列表无法方便地关联历史运行、关闭会话、保存重要决策或重建上下文。SessionManager 负责会话操作和并发约束，SessionStore 负责文件，Runner 负责执行当前轮，ExecutionContext 负责本轮运行中的状态。

会话并不等于 TCP 连接。理论上客户端可以断开后重新连接同一会话；但本阶段没有完整实现这一恢复路径，TUI 重连会新建 chat session。

## 2 四类持久化数据

通常目录结构为：

```text
~/.kama/sessions/<session_id>/
  meta.json
  thread.jsonl
  notes.md
  runs/<run_id>/
    events.jsonl
    .tasks/task_1.json
```

| 文件 | 内容 | 主要消费者 |
| --- | --- | --- |
| meta.json | id、mode、status、title、时间、run_ids | SessionManager |
| thread.jsonl | role、content、时间及部分 run_id 元信息 | 下次运行的模型上下文 |
| notes.md | 模型主动保存的重要事实和决策 | system prompt |
| events.jsonl | 运行过程事件 | 前端回放、排错 |

Thread 适合重建模型消息，events 适合解释过程；两者不是同一种日志。比如 UI 的 token 事件很多，但最终 assistant 消息只需保存完整结构。

## 3 核心代码阅读顺序

1. `core/bus/commands.py`：session.create、send_message、get_history、close 的参数和结果。
2. `core/app.py::_session_send_handler`：这一 RPC 等待整轮执行完成。
3. `core/session/manager.py::send_message`：锁、状态、用户消息和 Runner 调用。
4. `core/runner.py::run_and_capture`：读取历史、构建 Context、写回新增消息。
5. `core/session/store.py::read_messages`：恢复消息与修剪不完整尾部。
6. `core/context.py::system_prompt`、`core/tools/builtin/note_save.py`：Notes 如何进入下一轮。
7. `tui/app.py`：会话建立、用户输入、waiting_for_input 的 UI 恢复。

路径相对 `src/kama_claude/`。

## 4 第二轮如何看到第一轮

第一轮用户说“项目采用 JSONL 存事件”，第二轮问“我们刚才选择了什么格式”。第二轮流程如下：

1. SessionManager 找到 session 和对应 Lock。
2. 若锁已占用，返回 `SESSION_BUSY=-32012`；关闭的会话返回 `SESSION_CLOSED=-32011`。
3. 把本轮用户输入先追加到 thread。
4. 生成 run_id，更新 meta.run_ids。
5. Runner 读取整个 thread，读取 notes，将 history 作为 prefill_messages。
6. ExecutionContext 发现有 prefill，直接使用历史，不再次把 goal 追加进去。
7. Loop 运行，增加 assistant 和 tool_result 消息。
8. Runner 用 `context.messages[prefill_len:]` 只保存本轮新增部分，避免历史重复。
9. chat session 进入 waiting_for_input，TUI 重新允许输入。

“先保存用户输入，再读完整历史”与“不要重复追加 goal”是配套设计。只改其中一处可能让用户输入重复或丢失。

`prefill_len` 切片成立的前提是 messages 只在尾部追加。S6 引入压缩后会替换整个列表，这个前提被破坏，后面会重点分析。

## 5 会话状态与并发

Session 有 `one_shot` 和 `chat` 两种模式。`agent.run` 也被改为创建 one_shot session，再调用 send_message；这样单轮执行复用同一套存储。one_shot 运行结束后 closed，chat 运行结束后 waiting_for_input。

同一 session 的 send_message 持有 Lock 直到运行结束，所以两次用户输入不会同时改写它的历史。不同 session 有不同锁，仍然可以并发执行。

不要只按事件名想象状态。代码在 waiting_for_input 时发布 session.resumed，但没有同步把 status 明确改回 active；运行是否忙主要靠 Lock。若外部只读 meta.status 判断忙闲，就可能得到不够准确的状态。改进时需要把状态机与运行锁的语义统一。

## 6 Notes 如何工作

Runner 仅在同时有 session、store、run_id 时注册 `NoteSaveTool`。模型调用 `note_save(content)` 后，工具追加带时间和 run_id 的段落到 notes.md。后续 run 读取它，并由 `system_prompt()` 拼在 Session Notes 部分。

这是显式笔记，不是向量检索或模型自动训练。它不会按相关性检索，也没有去重、过期和冲突解决。Notes 在 run 开始读取一次，当前轮保存的新笔记主要通过工具结果或下一轮加载可见，并非实时刷新整个 system prompt。

例如“用户要求所有生成文件用 UTF-8”适合笔记，“刚才读文件失败，临时重试中”通常更适合历史。保存什么会影响长期上下文质量，因此应让笔记短、具体、有来源。

## 7 孤立工具调用为什么要修剪

假设历史末尾是 assistant 发出 `tool_use id=A`，但进程中断，没有对应 result。直接把这个历史交给模型服务，可能出现消息配对错误。

`_trim_orphan_tool_use()` 维护 pending ID 集合：看到 tool_use 加入，看到对应 tool_result 移除；记录最后一个 pending 为空的位置。扫描结束仍有 pending，就只返回最后平衡位置之前的消息。

这是针对尾部不完整数据的修复，不是严格的全量协议验证。它不会证明任意工具结果都有合法前置请求，也不检查所有交错顺序是否符合服务要求。对损坏 JSON 行，read_messages 会跳过并警告，恢复能力与数据完整性之间有取舍。

## 8 历史存在为什么还不能重启续聊

SessionStore 有 `read_meta()`，但 SessionManager 初始化 `_sessions={}`，`_get_session()` 只查内存，没有从磁盘加载。daemon 重启后，旧 session ID 不在字典中，即使 meta 和 thread 都在，也会返回 not found。

此外，当前 TUI 的连接流程在每次连上后调用 session.create，生成新的 session；所以重连 TCP 后不会自动接回原会话。

这提供了一个非常明确的个人改进题目：补上 session 恢复命令、磁盘加载、运行中断状态和前端恢复流程。比只增加一个“历史列表”按钮更有工程深度。

## 10 面试问题

**Run 和 Session 为什么分开？** 一个 Session 汇集多轮语境，每一轮 Run 保持独立执行 ID、事件和任务记录，便于追踪与重试。

**为什么不只保存最终答案？** 下一轮可能需要工具观测、文件状态和失败原因；保存结构化历史能保留这些信息。

**为何同会话串行？** 并发生成会争用同一历史基线，追加顺序不明确，工具调用与结果也容易混淆。

**已经持久化为什么还说不能恢复？** 持久化是写出数据，恢复还需发现、加载、校验、状态转换和客户端重绑定。

## 11 核心方法逐个精读

### 11.1 Session.to_dict 与 from_dict

Session 记录会话元数据，不保存全部消息。to_dict 把字段转换成普通字典，并复制 run_ids 外层列表；from_dict 从磁盘数据重建对象，将 ID 和时间等转为字符串。

因此 `session.run_ids` 只是一组运行引用。要读取某个 run 的工具输出，还需要进入它的 events 文件；要恢复模型上下文，则读 thread，而不是只看 meta。

### 11.2 SessionStore.__init__ session_dir runs_dir

构造器接收 root，expanduser 后创建根目录。session_dir(sid) 返回 root/sid；runs_dir(sid) 再加 runs。后两个主要是路径计算，不保证指定会话已创建，也不加载元数据。

把路径函数集中起来，能避免调用方分别拼出不一致的目录。未来新增 session ID 的输入校验，也应在明确边界集中处理，而不是每个 handler 自己写一套。

### 11.3 write_meta 与 read_meta

write_meta(session) 创建会话目录，把 session.to_dict 写成带缩进的 UTF-8 JSON。read_meta(sid) 读对应文件、json.loads，再 Session.from_dict。读失败会向上传播，不会自动创建一个空会话。

write_meta 是覆盖写，所以每次写入代表最新元数据快照。它与追加式 thread 的语义不同。两者先后顺序发生故障时，可能出现 meta 说有一个 run、而历史并未完整保存的情况。

### 11.4 append_message

输入 sid、role、content、可选 run_id。先建立一行包含 ts/role/content 的字典，有 run_id 再加入；创建目录，以追加模式打开 thread.jsonl，写 JSON 加换行。

每调用一次增加一条持久化消息。content 可以是普通字符串，也可以是 text/tool_use/tool_result 的内容块列表，存储层不把它们提前压成纯文本。

它不自动发布 session.message_received；那个事件由 SessionManager 发。保存数据与通知观察者是两个明确动作。

### 11.5 append_messages

输入一批模型 messages 和本轮 run_id，逐条调用 append_message。它复用统一行格式，避免在 Runner 中重复序列化逻辑。

这是逐条追加，不是整批事务。中途异常可能只保存前几条。恢复时修剪孤立工具调用能处理一类尾部问题，但不等于所有部分提交都已解决。

### 11.6 read_messages

thread 不存在就返回空列表；存在则逐行解析，跳过空行、坏 JSON 和不认识的 role，只取 role/content 放入模型消息列表，最后调用 _trim_orphan_tool_use。

磁盘行中的 ts、run_id 用来审计，不直接传给模型消息接口。重建消息时筛掉这些字段，是存储模型与请求模型分离的例子。S6 才在这一步之后增加工具结果截断。

### 11.7 _trim_orphan_tool_use

输入完整 messages，维护 pending 集合和 last_balanced 位置。assistant 中 tool_use.id 加入集合；user 中 tool_result.tool_use_id 从集合移除；每当集合为空，就记下当前消息末尾位置。

例如 `[用户目标, assistant调用A, user结果A, assistant调用B]`，扫到结果 A 时平衡位置为 3；最后 B 没结果，就返回前三条。若最终没有 pending，原列表直接返回。

它没有修改原文件，只改变这次加载结果，也没有执行未完成工具。理解这一点，才能区分“让下一次模型请求合法”和“把上次工作恢复完成”。

### 11.8 read_notes 与 append_note

read_notes 找不到文件返回空字符串，否则读取全文。append_note 接收 sid、content、run_id，追加带时间和运行来源的 Markdown 小节。

Notes 保留为便于人读的文本，适合调试和手工查看；它没有结构化主键，因此相同事实可能重复出现。自动去重和修订需要额外设计。

### 11.9 SessionManager.__init__

保存 Store、runner_factory、Bus，建立 `_sessions` 与 `_locks` 两个空字典。runner_factory 是一个可调用对象，每次调用返回新的 Runner；Manager 不在构造时就执行所有未来运行。

这个设计使测试能把 Runner 工厂换成假的。也意味着 S7 将后台注册表放在 Runner 里时，默认每一轮会重新创建一份；理解对象创建位置就能推断生命周期。

### 11.10 SessionManager.create

输入 mode 和可选 title，生成 sess- 开头 ID、当前时间、active 状态 Session，保存到内存字典，建立该会话专用 asyncio.Lock，写 meta，发布 session.created，返回 Session。

它不发用户消息，也不调用模型。用户可以创建空 chat session，之后再 send_message。Lock 作为内存对象不写入 meta，进程恢复时必须重新建立。

### 11.11 SessionManager._get_session

输入 sid，查 `_sessions`。没有就抛 HandlerError(-32010,"session not found")，有则返回 Session 引用。它不会调用 Store.read_meta，因此重建 Manager 后旧文件仍在也查不到。

返回的是管理器持有的对象，不是深复制。send_message 修改 title、run_ids、status，会直接改变内存中该会话状态；write_meta 才把变化同步到磁盘。

### 11.12 SessionManager.send_message 的准备部分

先取 Session 和 Lock；若锁已占用，直接 busy；进入 async with lock 后检查是否 closed。如果之前 waiting_for_input，就发布 resumed。再 append_message 保存原始用户输入，并发 message_received。

然后根据内容补空 title，分配 run_id，添加到 session.run_ids，更新时间并写 meta。这里本轮用户消息已经在 thread 中，所以 Runner 后面读完整历史时能看见它，不需要再追加一次。

### 11.13 SessionManager.send_message 的执行和收尾

调用 runner_factory 得到 Runner，await run_and_capture，传 content、run_id、session、store。等整轮返回后更新时间；one_shot 标 closed 并发 closed；chat 标 waiting_for_input 并发等待事件；写 meta；返回 run_id。

Lock 覆盖整次调用。若中间异常逃出，async with 会释放锁，但后面的业务状态更新不一定发生。这解释了为什么“锁释放正确”与“会话终态正确”仍是两件事。

### 11.14 SessionManager.close 与 get_history

close 先获取会话，若运行中忙则拒绝；拿锁后设 closed、更新时间、写 meta、发布 closed。它不是“立即取消当前运行”的命令，因为忙时直接报错。

get_history 先确认内存中存在会话，再 Store.read_messages，返回适合模型接口的消息列表。它没有直接暴露所有原始 JSONL 元信息，也不是恢复旧 session 的入口。

### 11.15 CoreApp 的四个会话 handler

`_session_create_handler` 校验命令，await create，返回 session_id/status。`_session_send_handler` 校验后 await send_message，整轮完成才返回 run_id。`_session_history_handler` 返回 messages。`_session_close_handler` await close 后返回 closed 状态。

它们是协议适配器：解析字典、调用 Manager、包装结果。业务错误由 HandlerError 经 SocketServer 转成结构化 RPC 错误。

S4 的 `_agent_run_handler` 则先 create one_shot，后台 create_task(send_message)，短响应返回 ID。两个命令虽然都启动 run，等待语义并不相同。

### 11.16 AgentRunner.run_and_capture 的会话分支

有 session/store 时，运行目录改为该 session 的 runs 子目录，读取 history 和 notes；没有时保持独立 runs 路径与单条 goal。记录 prefill_len，构造 Context，注册绑定本会话的 NoteSaveTool，执行 Loop。

结束后把 messages[prefill_len:] 追加到 thread，避免旧消息重复写入。此时只是尾部追加的模型还能成立；S6 换整个列表后必须重新审视这个不变量。

### 11.17 ExecutionContext.system_prompt 与 NoteSaveTool.invoke

system_prompt(base) 在 notes 为空时直接返回 base；不为空则附加 Session Notes 标题、笔记文本和保存重要事实的提示。它返回字符串，不会更新磁盘，也不会自己触发 note_save。

NoteSaveTool 构造时绑定 store/session_id/run_id。invoke 提取 content、strip，空内容返回错误，否则 append_note 并返回 saved。这个绑定避免模型自己指定任意 session 写笔记；会话归属由宿主决定。

### 11.18 S4 的 TUI 输入和显示方法

ChatTextArea._on_key 区分提交与换行，提交时发出控件消息。KamaTuiApp.on_chat_text_area_submitted 读取内容、检查连接与 busy、更新输入框状态、发送 session.send_message。S4 的发送还直接在这个处理方法中等待；S5 才抽到 worker，保证审批交互继续处理。

LLMStreamBlock.finalize_markdown 将累积文本转成最终 Markdown 展示，并通过 finalized 标志避免重复结束。`_break_llm` 调它后清掉引用。`_prompt` 安全查输入控件，`_update_header` 更新状态文字。它们属于 UI 辅助，不参与 Core 的会话锁。

### 11.19 chat CLI 的 _readline 与 _chat_async

_readline 用 run_in_executor 执行阻塞 input，避免用户打字时阻塞 socket 事件循环。_chat_async 建连接、订阅、创建 chat session，再循环读输入和发消息，结束时尝试关闭会话并清理读任务。

把 input 放进线程池只解决“阻塞等待键盘”的问题；若外层输入循环正在 await 一个长 RPC，它仍不会走到下一次 input。这个细节在 S5 审批中很关键。

## 12 按两轮对话核对消息数量

第一轮没有工具：用户 U1 已由 Manager 保存，Runner 的 prefill_len=1；模型新增 A1，结束只追加 `[A1]`。磁盘有 U1、A1。

第二轮用户 U2 先追加，Runner 读到 U1、A1、U2，prefill_len=3；模型发工具调用 T，工具返回 R，模型最终 A2，结束追加 `[T,R,A2]`。磁盘共六条。

若你在 Runner 中再次无条件追加 goal，会出现 U2 重复；若保存整个 messages，会把 U1、A1、U2 再写一遍。亲手数一次，比只记“历史持久化”更容易理解边界。

## 13 本阶段可改进的地方

| 改进 | 具体方向 | 验收 |
| --- | --- | --- |
| 重启恢复 | `_get_session` 加受控加载，新增 resume/list，TUI 选择历史 | 重启后同 session 继续，已保存约定仍可用 |
| 状态机一致性 | running 前设 active；异常 finally 更新 interrupted/failed | busy 与 meta 状态不会互相矛盾 |
| 持久化原子性 | meta 原子替换，历史提交与状态记录有一致的顺序 | 在写入各阶段注入故障仍能识别已提交部分 |
| 消息去重 | 用户输入携带 client_message_id | 网络重试不会启动两次同一消息 |
| 笔记治理 | 内容去重、来源、修订与删除；限制大小 | 旧偏好可被更正，token 不无限增长 |

推荐把会话恢复和事件恢复一起做成 S8，形成“断线、重启后用户回到正确状态”的完整体验。
