# S6 上下文治理与压缩

基准：`origin/stage/s6`，提交 `f4567c1`。本阶段管理长期对话的上下文成本：分层注入记忆、显示水位、截断历史工具输出、压缩对话，并对部分流式网络错误重试。

## 1 为什么上下文会增长

每轮请求通常携带前面的 messages。若执行了很多工具，每次文件内容、命令输出都可能再次进入模型输入。历史越长，输入成本、请求延迟和接近窗口上限的概率就越高。

需要区分三种约束：模型输入与总上下文窗口；单次生成的输出 token 上限；工具和 IPC 的字节或字符上限。它们单位不同，解决的问题不同。把工具输出截到 8000 字符，不等于将整个请求控制在 8000 tokens。

## 2 关键代码和真实默认值

## 3 四类信息怎样进入模型

本阶段的 system prompt 拼接顺序为基础提示、全局 context、项目 context、session notes：

```text
基础提示
~/.kama/context.md
<Core cwd>/.kama/context.md
当前 session 的 notes.md
```

Thread 则作为 messages 单独传入，不属于 system 字符串。

全局 context 适合长期用户约定，项目 context 适合仓库约束，notes 适合当前会话已确认事实，thread 保留具体交互过程。它们都是文本加载，不是向量数据库检索。

这里的“分层”是来源和拼接顺序，代码没有实现严格的冲突解析规则。若全局说一种编码、项目说另一种编码，最终仍依赖模型理解。改进时可以给指令来源和优先级做显式表示。

## 4 上下文水位如何计算

Provider 内部维护模型名到窗口大小的表，当前列出的值及未知模型回退值都是 200000。这个表是仓库实现配置，不代表外部服务当前真实能力。接其他模型时应按实际端点验证并配置。

当前公式：

```text
context_pct = usage.input_tokens / _context_window(model)
```

它只看这次返回的 input_tokens，没有在公式里合并 cache_read_input_tokens、cache_creation_input_tokens，也没有预留下一步工具输出与模型生成预算。对于返回独立缓存用量的服务，它可能低估上下文占用，应明确服务的计数口径。

而且这是调用结束后才知道的水位，无法预防“本次请求已经超限”。更完整的预算器应在请求前估算 system、tools、messages、预留输出，并在响应后用真实 usage 校准。

## 5 工具结果截断的范围

`truncate_tool_results()` 只处理 user 消息里 type=tool_result 且 content 为字符串的 block。其他文本和 assistant 消息不动。超过 limit 时复制这个 block，保留前 keep 字符并加省略说明，其他结构如 tool_use_id 保持不变。

例如 10000 字符输出，在默认配置下变为前 4000 字符和一条“省略 6000 字符”的说明。它不是摘要，不会理解末尾是否有最重要的错误信息；只保留前缀可能恰好丢掉最后的失败结论。

实际调用在 SessionStore.read_messages，意味着它主要影响下一轮加载的历史。本 run 中新获得的大输出仍可能完整进入紧接着的下一步模型调用。配置里虽然有 tool_result_limit/keep，read_messages 调用时未传配置，仍用函数默认值。学习“定义了配置”时要一直追到最终使用点。

函数本身只做内存转换，不覆盖原 thread。工具事件里的 output 保存的是工具返回内容；如果工具自身早已截断，events 里也不会凭空出现未经截断的完整原始数据。

## 6 自动压缩的完整路径

Loop 只有同时满足下列条件才尝试自动压缩：run 还未结束；本步 stop_reason 是 tool_use；有 compactor；阈值大于 0；response 带 usage；context_pct 达到阈值。

位置放在全部工具结果回填之后，有助于避免只留下 tool_use 却没有 tool_result 的不完整配对。压缩器把消息转成文本，要求模型给出六部分：原始目标、已完成步骤、约束与发现、文件现状、剩余任务、关键数据。

摘要调用不带工具 schema，使用单独的静默 EventBus，避免摘要生成 token 混入用户正在看的主对话。成功后 context.messages 替换成：

```json
[
  {"role":"user","content":"六部分摘要正文"},
  {"role":"assistant","content":"Understood, I'll continue from this summary."}
]
```

同时写 summary_<时间>.md，并发布 context.compacted。失败或空摘要时返回 None，保留原上下文。摘要请求本身也会消耗模型资源；输入已很大时摘要调用仍可能失败。

当前没有强制检查摘要是否更短，也没有验证六部分齐全或关键 ID 保留。因此“生成了非空摘要”与“压缩有效且语义完整”是不同标准。

## 7 自动压缩与保存切片的缺口

这是本阶段最值得你亲手复现的问题：S4 Runner 用 `prefill_len` 记住运行前历史长度，结束时保存 `context.messages[prefill_len:]`。S6 压缩会替换整个 messages 列表。

具体例子：运行前有 10 条消息，prefill_len=10；中途压缩只剩摘要和确认两条；之后模型再答一条，列表长度变 3。结束时取 `[10:]` 得到空列表，摘要和最终答案都不会按原切片保存。旧 thread 仍在，下一轮又读回旧历史。

这说明局部 Compactor 测试通过不代表“压缩 → 完成本轮 → 保存 → 下一轮继续”整条链路正确。修复不能只把 prefill_len 改为 0，否则可能把摘要重复追加在旧历史后，仍不能得到真正压缩后的对话。

更合理的是显式区分完整不可变历史和当前有效上下文快照，或者在自动压缩成功时原子写入压缩状态并重新定义增量边界。必须用跨轮测试验收。

## 8 手动压缩与自动压缩不完全相同

TUI 精确匹配 `/compact` 后发 session.compact。SessionManager 先检查会话锁，运行中返回 busy；再读历史，调用 compact_messages，最后 `write_compacted()` 把原 thread 改名为备份，写新的摘要消息对。

手动路径确实替换了持久化 thread，因此下一轮会加载摘要。但它没有走 Compactor.compact 的 summary 文件与 context.compacted 发布流程，TUI 主要根据 RPC 返回展示摘要 token 和 saved_tokens。

当前 TUI 不解析 `/compact 保留接口细节` 这样的焦点参数，尽管协议有 focus 字段。不要把协议能力直接当作界面功能。

文件备份用秒级时间戳，同一秒重复压缩存在名称冲突；先 rename 再写新文件也不是完整事务。应考虑写临时文件、原子切换、版本和恢复流程。

## 9 流式重试与输出上限

S6 Provider 把输出上限设为 8192，并对指定的 httpx 连接、读取、协议异常最多尝试 3 次，实际等待 1 秒、2 秒后重试。它没有对所有异常做统一重试。

为了避免重复显示，仅第一次尝试发布 llm.token。问题是第一次输出一半失败、第二次成功后，最终文本虽然进入 context，TUI 可能只显示第一次的半段，缺少最终完成文本校正事件。正确策略应区分 attempt，并在成功后用完整文本替换或确认展示。

若 stop_reason=max_tokens 且包含工具调用，Loop 不执行可能不完整的参数，而是为每个调用补一个错误 tool_result，保持配对。之后若未达步数上限，可以让模型重新拆解任务。


真实手动实验：先对话几轮，执行 `/compact`，查看 thread 备份和新的两条消息；下一轮询问之前明确记录的约束，检查是否保留。

确定性实验：FakeProvider 第一次返回 usage.context_pct=0.9 的工具调用，摘要请求返回固定文本，下一次返回最终答案；阈值设为 0.8。预置至少 10 条历史，执行后检查下一轮读取到的内容。这直接暴露保存切片问题。

用固定输入比较“原文、前缀截断、摘要”三种策略，测试样例同时把重要信息放在开头和末尾。指标应包含保留率与正确完成任务的比例，不只看 token 减少。

## 11 面试问题

**截断和压缩有什么区别？** 截断按长度删内容，便宜、可预测但可能删关键信息；摘要多一次模型调用，试图保留语义，但有遗漏或编造风险。

**为什么保留工具配对？** 工具调用和结果共同表达一项动作及观测，缺一会破坏消息协议，也会让模型误判执行状态。

**80% 水位一定安全么？** 不一定。计算口径、缓存统计、下一步大工具结果、系统提示和输出预留都会影响实际预算。

## 12 核心方法逐个精读

本节以 S6 为准。先记住这条主线：**加载记忆 → 读取历史并截断 → 正常执行 → 观察用量 → 必要时摘要 → 保存下一轮要用的状态**。前三步、摘要生成和最终保存属于不同模块，不能只看压缩器就判断整个功能正确。

### 12.1 `load_context_file(path)`：把一个文件变成提示文本

定位：`core/memory/loader.py`。输入是路径，返回字符串。方法先展开 `~`，检查文件是否存在，再按 UTF-8 读文本并去掉首尾空白；没有文件时返回空字符串。

例如全局文件不存在、项目文件是“本项目使用 Python 3.12”，最终只有项目文本参与拼接。返回空字符串表示“该来源没有提供内容”，不表示错误，也不代表已经从其他地方检索到替代内容。

这里没有关键词检索、向量相似度或自动更新。修改文件后，要看 Runner 在什么时候重新调用加载器；它不是一个持续监控文件的服务。读源码时区分“启动时加载一次”“每轮加载一次”和“每步加载一次”，它们决定修改何时生效。

### 12.2 `ExecutionContext.system_prompt(base)`：按来源组装 system

定位：`core/context.py`。这是普通实例方法，Loop 用 `context.system_prompt(base)` 调用，base 是传入的基础提示字符串。它把基础提示、全局约束、项目约束、会话笔记依次拼接。空来源不需要生成无意义的内容。

输入除了 base 参数，还包括对象已经保存的字段；输出是发送给 Provider 的 system 文本。它不会把 thread 的全部消息变成 system，也不会改变 `context.messages`。

练习：分别给 global、project、notes 写一条不同约定，打印最终 system，确认顺序。然后让两处写出矛盾约定，观察程序没有主动报“约定冲突”。这说明目前只有文本层面的组织，没有程序层面的冲突检查。

### 12.3 `truncate_tool_results(messages, limit, keep)`：按结构截断

定位：`core/compact/budget.py`。输入是消息列表和两个字符数阈值，返回处理后的列表。执行过程如下：

1. 遍历消息，非 user 消息直接保留。
2. user 的 content 不是列表时直接保留，比如用户输入的一句话。
3. 遍历列表，只处理字符串形式的 tool_result。
4. 超过 limit 才复制这个 block，把正文改成前 keep 个字符加省略说明。
5. 组装新的 user 消息字典和 content 列表，返回结果。

这不是深拷贝：未改的 block、非 user 消息可能仍是原来的对象。因此不能因为返回了新列表，就认为之后任意修改其中所有嵌套对象都不会影响输入。

边界例子：长度恰好 8000 不截，8001 才截；10000 字符保留 4000，省略数是 6000。代码按字符计算，中文字符与 UTF-8 字节不能混用。`tool_use_id` 不变，所以截短文本不应该破坏调用与结果的关联。

### 12.4 `SessionStore.read_messages()`：截断实际接入的位置

定位：`core/session/store.py`。S4 已说明它如何读取 JSONL、转换 role/content、处理未配对尾部；S6 在返回历史前接入上述截断函数。

调用者主要是 SessionManager 和 Runner。关键效果是“磁盘原文 → 读取出来的模型历史”发生变化；函数并不把缩短后的正文重新覆盖磁盘。

追踪一次自定义配置：即使配置写 `tool_result_limit=1000`，也要检查这里有没有传 `limit=配置值`。本阶段没有接线，仍按函数默认 8000/4000 执行。配置文件能解析成功只能证明配置进入了内存，不能证明功能已经使用它。

### 12.5 `_context_window(model)`：查表，不向服务端查询

定位：`core/llm/provider.py`。输入模型名称，返回本地表中的整数窗口大小；未知名称回退 200000。这个函数没有网络请求，不会自动获知外部服务能力变化。

它的输出是水位计算分母。若分母错了，即使 usage 读得对，显示和自动压缩触发点也会错。因此未来应把端点、模型和窗口配置放在可验证的同一处，而不是把回退值当作真实模型承诺。

### 12.6 `AnthropicProvider.chat()`：本阶段新增的重试与用量

定位：`core/llm/provider.py`。基础参数和 tool_calls 解析见 S1；S6 重点看三段。

第一段组装请求：system 和最后一个工具 schema 设缓存标记，`max_tokens=8192`。它限制本次生成长度，不是输入历史长度。

第二段流式尝试：每次清空 `text_parts`；成功读取流后再获取 final_message。指定网络异常触发下一次尝试，最多总共三次。三次尝试只有两次等待，因此定义了 1、2、4 的数组，不代表一定会等待 4 秒。

第三段统计：从 final_message.usage 取输入、输出、缓存用量，发布 `llm.usage`，同时放入返回的 UsageStats。`context_pct` 只用 input_tokens 除本地窗口值。事件供 TUI 使用，返回对象供 Loop 使用，这是同一数据的两条消费路径。

最容易忽略的是：只有第一次尝试发布 token，但成功结果可以来自第二、第三次。`text_parts` 清空保证最终返回的是成功尝试的正文，却不能自动清空已经显示在 TUI 的失败尝试片段。解决内存结果与解决界面结果是两件事。

### 12.7 `AgentLoop.run()`：决定何时压缩

定位：`core/loop.py`。Loop 在正常工具结果回填之后，检查本步是否为 tool_use、是否配置 compactor、阈值是否启用、usage 是否达到阈值，然后调用 `compactor.compact(context, provider)`。

为什么不是看到高水位就立刻压缩？如果模型刚给出 tool_use，工具结果还没回来，摘要会处于“动作发起但结果未知”的中间状态；先补齐这一轮结果，至少保持当前工具对完整。

遇到 `max_tokens` 且带工具调用时，本阶段不直接执行这些调用，而为其生成错误结果。这里担心的是模型输出被截断导致参数不完整；补结果使下一次请求仍有合法配对。步数上限仍然约束整个 Loop，压缩不会把已执行步数自动清零。

### 12.8 `Compactor.__init__()` 与 `CompactionResult`

定位：`core/compact/compactor.py`。构造器保存 bus、session_dir、session_id，供后续发事件和写摘要文件使用；构造对象本身不请求模型。

CompactionResult 保存 summary_text、original_token_estimate、summary_tokens。前者是内容，后两者是评估数字。原始数量用字符近似，摘要数量优先用服务返回的输出 token，所以两者并不是完全相同精度的测量，`original - summary` 只能作为粗略估计。

### 12.9 `_messages_to_text(messages)`：给摘要模型准备阅读材料

该函数遍历消息，为字符串正文加 `[USER]`、`[ASSISTANT]` 等角色标签；遇到 block 列表时，分别把 text、tool_use、tool_result 转成可读文字。

工具调用带 name、id、input，结果带 tool_use_id 和 content，目的是让摘要模型知道“做了什么”和“得到什么”。它不是无损序列化器：没有处理的 block 类型不会自动保留；不能指望把生成的文本再解析回完全相同的消息列表。

具体跟踪：assistant 调用 `read_file(id=c1, path=a.py)`，下一条 user 有 `tool_result(tool_use_id=c1, content=...)`。转换后仍能从 c1 看出二者有关联；如果摘要输出丢掉路径或最终错误，这不是格式转换能保证避免的，需要摘要质量验收。

### 12.10 `Compactor.compact_messages()`：生成候选摘要

输入是 messages、Provider 和可选 focus，返回 CompactionResult 或 None。调用者既可以是自动压缩，也可以是手动压缩。

依次执行：估算原长度 → 转成文本 → 构造六段摘要要求 → 拼入非空 focus → 用无工具的请求调用 Provider → 检查摘要非空 → 返回结果。它使用新建的静默 EventBus，`run_id="compact"`，避免摘要 token 进入主运行展示。

源码注释称它“纯函数式压缩”，应理解为“不直接替换传入消息”，不能理解为数学上的无副作用纯函数：它会调用外部 Provider，可能耗时、失败和产生费用。

模型调用抛普通异常时记录日志并返回 None，空文本也返回 None。非空不等于更短；当前没有比较压缩收益，也没有校验六个标题完整。调用者应区分“生成失败”“质量不达标”“无需压缩”，现实现用一个 None 不能表达这些差异。

### 12.11 `Compactor.compact()`：把候选摘要应用到运行内存

它先调用 compact_messages；None 时直接返回，不替换 context。成功时把整个 messages 字段赋值成两条新消息：用户摘要与助手确认；再写摘要文件、发布 context.compacted，最后返回结果。

注意赋值与追加的区别：`context.messages = [...]` 让字段指向一份新列表，原来基于旧列表长度建立的增量索引不再可靠。S4 的 prefill_len 恰好是这种索引，所以 S6 必须同时考虑 Runner 的保存策略。

它先改内存再写文件，写摘要失败又被内部记录后吞掉，因此不能把 context.compacted 理解成“摘要及对话事务已经可靠提交”。当前事件主要描述运行内存发生了压缩。

### 12.12 `_write_summary()`、`_ts_compact()`、`_now()`：文件与时间

`_write_summary(text)` 确保会话目录存在，再写 `summary_<时间>.md`，异常记录日志。该文件便于人阅读，但 Runner 下一轮主要读 thread，因此只有 summary 文件存在不代表历史已切换。

`_ts_compact()` 输出 UTC 秒级文件名时间；`_now()` 输出 UTC ISO 时间供事件使用。前者便于文件名，后者便于时间记录，都不是可靠的唯一 ID。高频操作应使用版本或 UUID 避免同秒名称碰撞。

### 12.13 `SessionManager.compact()`：手动入口的业务约束

定位：`core/session/manager.py`。它先查会话和互斥状态，获取该会话锁，读历史，检查 Provider，生成候选摘要，然后调用 store.write_compacted 保存。

没有 Provider 返回 `-32020`；压缩结果为 None 返回 `-32021`。错误文案含“not beneficial”，但生成函数没有实际执行收益判断，不能根据错误文案反推存在该判断。

它返回摘要长度和节省量，节省量至少为零；截成零只是展示处理，不是拒绝更长摘要。手动入口没有调用 Compactor.compact，所以不会自动获得后者的事件和独立 summary 文件副作用。

### 12.14 `SessionStore.write_compacted()`：备份后替换 thread

定位：`core/session/store.py`。它把旧 thread 改名为带时间的备份，再写入摘要消息对。返回之后下一轮 read_messages 会读新的 thread，这与仅修改 context.messages 有本质不同。

但两个文件动作之间可以失败。假设 rename 已完成，新 thread 写入前进程退出，下次读取应该怎样发现备份？当前路径没有完整的事务恢复协议。学习文件存储时不要把“有备份”直接等同“所有中间状态都可自动恢复”。

### 12.15 TUI 的 `/compact` 分支、`_do_compact()` 和用量显示

定位：`tui/app.py`。提交文本恰好为 `/compact` 时走压缩分支，启动 worker 调 RPC，避免阻塞输入事件处理；正常文本仍走发送流程。

`_do_compact()` 展示执行提示，等待 session.compact 返回，显示摘要统计并更新 UI。这里传的 focus 为空字符串，没有把斜杠命令后的文字解析成 focus。

用量事件展示的是服务器提供的估计水位；压缩后将显示归零属于 UI 状态重置，不是证明实际上下文为零。摘要、system、工具 schema 仍占用空间。完整方案应让界面区分“上次测量值”“压缩后待重新测量”。

### 12.16 Runner 与 Core handler 怎样把这些方法接起来

`AgentRunner.run_and_capture()` 每轮加载全局和项目 context，放入 ExecutionContext；再构造 Compactor，将会话目录、bus、session_id 绑定进去。构造 AgentLoop 时显式传 `compact_threshold=config.compaction.auto_threshold`，所以配置默认 0 覆盖 Loop 自身默认 0.8。

这说明“一个类的默认参数”并不总是产品实际默认值。调试自动压缩为什么没触发，先查这个装配点和生效配置，再查 usage、stop_reason 与阈值条件。

Core 的 `_session_compact_handler` 校验请求，提取 session_id/focus，委托 SessionManager.compact，包装协议响应。它只负责入口适配，不自己拼摘要或操作 thread。手动和自动共享候选摘要生成，但原版本尚未共享最终提交路径。

## 13 用一张纸演算压缩前后

准备十条历史消息，编号 H1～H10。新一轮 Runner 记住 prefill_len=10，模型生成工具调用 T，工具返回 R，此时列表有十二条。压缩产生 S、ACK 两条，再得到最终回答 A，最终列表只有三条。

分别写下三处状态：

| 时刻 | 运行内存 | 磁盘 thread | 保存时的旧边界 |
| --- | --- | --- | --- |
| 启动 | H1…H10 | H1…H10 | 10 |
| 工具完成 | H1…H10,T,R | 通常仍是已保存历史 | 10 |
| 自动压缩 | S,ACK | 旧历史仍在 | 10 |
| 最终回答 | S,ACK,A | 旧历史仍在 | 10 |
| 结束切片 | `[10:] = []` | 没有追加 S/ACK/A | 已失效 |

本例的重点不是精确模拟所有事件，而是区分“运行中的列表”和“下一轮从磁盘恢复的列表”。你应能解释为什么直接 `prefill_len=0` 也不够：如果把 S/ACK/A 追加到旧 H1…H10 后面，历史仍没有真正切换成摘要。

完成学习的标准：自己画出自动与手动两条调用链，指出共同的摘要生成方法、不同的提交方法，并为两条路径设计同一个跨轮验收。

## 14 本阶段可改进的地方

| 改进 | 实现方向 | 验收 |
| --- | --- | --- |
| 压缩持久化一致性 | 明确原始历史、快照、增量的边界 | 自动压缩后结束，再开下一轮能看到摘要和最终消息 |
| 请求前预算 | 统一统计 system/tools/history，加入输出预留 | 大结果回填后先治理再请求，不靠失败触发 |
| 配置接线 | 将 limit/keep 传入所有需要的调用点，校验 keep<=limit | 自定义阈值改变真实行为 |
| 结果摘要策略 | 保留首尾、错误段、路径与结果引用 | 末尾关键错误不会丢；大正文可按需重新读取 |
| 摘要质量评测 | 固定事实清单、工具配对、任务继续成功率 | 压缩降低成本同时保持关键约束 |
| 流重试一致性 | 增加 attempt 与最终文本确认事件 | 首次中断、重试成功后 UI 与持久化答案一致 |

如果选择上下文治理作为个人主线，应先修跨轮保存，再做预算和评测。只增加一种摘要 prompt，难以证明工程提升。
