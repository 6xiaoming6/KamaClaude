# S0 骨架与协议契约

基准：`origin/stage/s0`，提交 `89e6df4`。本阶段不调用模型，目标是让两个进程使用明确的消息格式完成一次请求和响应。

当前工作树已经补充 S0 的 Windows 前台启动与取消清理，运行方式见仓库 README；本文原始阶段的信号处理说明仍用于对照。学完后可用 [核心自测与面试标准答案](S0-核心自测与面试标准答案.md) 检验掌握程度，其中生命周期答案按修复后代码说明。

## 1 为什么先做协议

假设把模型调用、终端打印和文件操作全部写进 CLI，后续新增 TUI 时必须拆出执行逻辑。S0 提前确定 Core 与客户端的边界，让客户端只发送命令，Core 处理后返回结果。此时业务很简单，方便先排查网络、编码、参数错误，而不是让它们和模型问题混在一起。

这种边界只是一种架构准备。S1 为降低复杂度仍选择在 CLI 内运行 Agent，S2 才让这条协议链路承载执行任务。

## 3 一次 ping 的完整路径

1. 包安装把 `kama` 映射到 `cli.main:main`，把 `kama-core` 映射到 `core.app:run`。
2. Core 载入配置并创建 `SocketServer(host, port)`。
3. `server.register("core.ping", self._ping_handler)` 把方法名绑定到函数。
4. `asyncio.start_server()` 监听 TCP；默认 `127.0.0.1:7437`。
5. CLI 调用 `asyncio.open_connection()`，得到 reader 和 writer。
6. CLI 序列化请求，加 `\n`，`writer.write()` 后 `await writer.drain()`。
7. 服务端 `_read_loop()` 通过 `reader.readline()` 取一帧；`_handle_line()` 解析并分发。
8. `_ping_handler()` 返回版本、启动时长、接收时间。
9. 服务端将业务结果装入 `JsonRpcSuccess` 并写回。
10. CLI 读取一行，校验成功响应和 `PongResult`，打印 pong，然后关闭连接。

示意报文：

```json
{"jsonrpc":"2.0","id":"cli-1","method":"core.ping","params":{"client":"cli/0.0.1"}}
```

```json
{"jsonrpc":"2.0","id":"cli-1","result":{"server_version":"0.0.1","uptime_ms":123,"received_at":"2026-10-15T00:00:00+00:00"}}
```

第二行的数值和时间是教学示例。真正编码时每个 JSON 后都有换行。`id` 把响应关联到请求；`method` 选择 handler；`params` 是业务参数；`jsonrpc` 是协议版本，不是项目版本。

## 4 TCP 为什么还需要 NDJSON

TCP 交付字节流，不保留一次 `write()` 对应一次 `read()` 的消息边界。可能一次读到半条请求，也可能读到两条。NDJSON 规定一行一个 JSON，接收端用换行切帧。

JSON 字符串里的文本换行会被编码成转义序列 `\n`，它不同于帧尾实际的换行字节。不要把“文件内容含换行”误认为一定破坏协议；真正危险的是发送端把未转义的多行文本混进协议流。

`drain()` 用于等待输出缓冲区达到可继续写的状态。它不等价于对方已经完成业务处理。收到 pong 才说明请求走完了服务端 handler。

S0 设置约 1 MiB 的单帧读取限制。它是内存和输入边界的一部分，S7 将其增大到 64 MiB。单纯提高上限不解决慢客户端或大输出的问题。

## 5 两层模型和实际校验边界

`JsonRpcRequest` 校验外层：例如 `jsonrpc` 必须是 `"2.0"`，`id` 在本实现中是字符串。业务模型 `PingCommand` 则描述 ping 的字段。

但 S0 `_ping_handler()` 直接 `params.get("client", "unknown")`，并没有调用 `PingCommand.model_validate()`。因此“定义了类型化协议”不代表每个 handler 都落实了业务校验。后续阶段的运行、订阅命令开始显式调用模型校验。

S0 使用的是 JSON-RPC 风格的受限实现。它没有在入口实现所有可选形态，例如批量请求；不要说成完整协议实现。`CoreStartedEvent` 在此阶段只是已定义的模型，不等于已经构建了完整事件广播链路。

## 6 失败如何被区分

| 输入或故障 | 路径 | 当前响应 |
| --- | --- | --- |
| 非法 JSON | `json.loads()` 失败 | `-32700` |
| 外层字段不符合请求模型 | `model_validate()` 失败 | `-32600` |
| 未注册 method | handlers 查找失败 | `-32601` |
| handler 抛 ValidationError | 参数错误分支 | 当前代码仍返回 `-32600` |
| handler 其他异常 | 内部错误分支 | `-32603` |

虽然定义了 `INVALID_PARAMS = -32602`，S0 对 handler 的参数校验错误没有使用它。这是一个可以很小成本修复的协议一致性问题。

客户端等待 pong 的超时为 10 秒；服务端关闭监听时等待上限为 2 秒。超时不是一个全局值：连接、帧读取、业务处理、关闭连接分别可能需要不同预算。

## 7 配置和生命周期

S0 配置优先级为默认值、全局 TOML、`.env`、系统环境变量。实现先 `load_dotenv(override=False)`，让已有系统环境变量保留，再确定 TOML 路径，最后用环境变量覆盖 dataclass。物理执行顺序与最终优先级不必相同。

启动时先探测端口是否已有监听者，再执行 bind。探测能提供清楚的提示，但检查与 bind 之间仍可能被其他进程抢占，所以实际 bind 错误仍需处理。

`time.monotonic()` 计算 uptime 和延迟，避免系统时钟校正影响时长；UTC 时间字符串用于记录某个事件发生的时间。二者用途不同。

## 9 自测和面试问题

**为什么不用函数调用？** 因为 CLI 与 Core 是不同进程，需要序列化和传输。进程边界换来独立生命周期，同时增加协议和故障处理成本。

**为什么模型和传输分开？** 模型定义消息含义，传输处理连接和字节；后续更换前端或传输时可以复用业务契约。

**端口通了就表示 Core 健康吗？** 不一定。普通 connect 只能证明有进程接受连接；应发送真正的 ping 并验证版本和响应。

**学完标准。** 不看代码，能够画出上述十步，解释三类错误，并指出类型模型在哪一层真正被调用。

## 10 核心方法逐个精读

以下定位都属于 S0。先用本节把每个方法读懂，再用下一节连起来；不要把 main 中已增加 Session 和 MCP 的 CoreApp 当成本节版本。

### 10.1 cli.main.main

这是 `kama` 命令的入口，没有显式业务参数，输入来自命令行。它建立 ArgumentParser，声明 `--version` 和 `ping`，解析后按分支调用具体函数。ping 分支先 get_config、setup_logging，再 cmd_ping；没有有效命令则显示帮助并退出。

它通常返回 None，真正的效果是打印、启动异步调用或设置进程退出码。入口不直接处理 TCP 字节，是为了让参数解析和通信各自可测试。阅读时把 `args.command` 想成字符串开关即可。

### 10.2 cmd_ping 与 _ping

`cmd_ping(config)` 是同步包装层：用 asyncio.run 运行 `_ping(config)`，捕获连接失败并打印错误、退出 1。它接收的 config 已经完成优先级合并，不在这里再次读 TOML。

`_ping(config)` 是真正的异步流程：记录 t0；连接；构造请求；write 和 drain；最多等待 10 秒读一行；记录耗时；关闭连接；解析响应；打印结果。成功时不返回 pong 对象给上层，而是直接输出到终端。

Python 3.12 的 TimeoutError 也是 OSError，因此读取超时会进入这个统一错误分支，却显示成 core not running；JSON 解析或响应模型校验错误则不属于这一捕获范围。关闭连接也没有包住整个流程的 finally。用这种方式读代码，能知道正常路径，也能知道错误提示和清理尚未覆盖哪里。

### 10.3 顶层 run 与 CoreApp.__init__

`core/app.py` 底部 `run()` 是命令行脚本指向的同步入口，用 `asyncio.run(CoreApp().run())` 创建和运行事件循环。类方法 `CoreApp.run()` 与这个同名模块函数不是同一个函数。

`CoreApp.__init__()` 保存启动计时基准；它不绑定端口。创建对象不等于服务器已经启动，真正 I/O 在 run 中进行。

### 10.4 CoreApp.run

调用者是模块级 run。它依次读配置、装日志、创建服务器、注册 ping、await server.start，然后建立 shutdown Event 和信号回调，再 await shutdown.wait。最后 stop 服务器。

可分成三段理解：启动资源、等待工作期间结束、清理资源。没有用户请求时，程序仍停在等待阶段；TCP 连接处理由 asyncio.start_server 的回调推进，不需要在这里写一个手工 accept 循环。

信号回调只做 shutdown.set，实际清理由主协程执行。这使退出动作可以走异步等待，而不是在信号回调里直接做复杂 I/O。

### 10.5 CoreApp._ping_handler

输入 params 是已经从 JSON 解出的字典。该方法读取 client 用于日志，返回 PongResult：版本从包常量取，uptime 用 monotonic 差值算，received_at 用 UTC 当前时间。

返回的是模型对象，不是已发送的网络报文。SocketServer 之后负责 model_dump 和包装成功响应。这样业务函数不必关心请求 ID 和 writer，便于直接测试它的业务字段。

### 10.6 SocketServer.__init__ 与 register

初始化保存 host、port，建立空 handlers 字典，server 句柄先为 None。`register(method, handler)` 将 callable 保存到字典。例如注册后 `_handlers["core.ping"]` 指向一个可调用的异步方法。

函数也是对象，可以被保存和稍后调用；这就是方法分发的基础。register 没有立即执行 handler，同名再次注册会覆盖之前映射。

### 10.7 SocketServer.start

它先尝试连接目标地址。如果连接成功，关闭探测连接并提示已有 Core；若连接拒绝等 OSError，就继续创建 asyncio server。成功时保存 `_server`，返回 `host:port` 字符串，供日志展示。

返回字符串不是服务器对象；真正句柄保存在 self。启动探测不能替代 bind 的最终校验，因为两个进程可能同时探测成功后竞争端口。底层异常仍可能向上冒出。

### 10.8 SocketServer._handle_connection

由 asyncio 服务器在新连接到来时调用，参数是这一连接的 reader 和 writer。它读取 peer 信息用于日志，然后 await `_read_loop`，finally 关闭 writer 并等待关闭。

同一个服务器可为不同连接调用多次这个方法。每次有自己的局部 reader/writer，不应把它们误认为全局唯一。finally 的价值是客户端正常 EOF 或读取途中异常时都尝试释放连接。

### 10.9 SocketServer._read_loop

循环 await reader.readline。返回空字节表示对方关闭连接，return 结束；非空就交给 `_handle_line`。S0 逐条等待 handler 完成，因此同一连接的下一条请求暂时不会被处理。

这一顺序对快速 ping 足够简单；到了 S5 的长任务加审批，它成为等待环的一部分。架构变化不是“异步越多越好”，而是业务等待条件改变了。

### 10.10 SocketServer._handle_line

输入是一整行 bytes；第一关 json.loads 判断语法，第二关 JsonRpcRequest.model_validate 判断外壳，第三关 handlers.get 判断方法是否存在。通过后 await handler(req.params)，把结果包装成 JsonRpcSuccess，用原 req.id 关联请求。

每个失败分支 send 错误后 return，避免继续执行下一层。对业务结果，如果是 BaseModel 就 model_dump，否则保留原对象交给外壳序列化。这个方法同时连接协议校验、业务调度和响应包装，是 S0 最值得逐行读的位置。

### 10.11 SocketServer._send 与 stop

`_send(writer, msg)` 把模型变成 JSON 字符串，再 encode 成字节，加换行写入并 drain。它不做业务判断；所有成功与错误响应复用它，避免各分支忘记加换行。

`stop()` 在未启动时直接返回；已启动则关闭监听并限时等待。关闭监听与结束所有已建立连接、所有业务任务是不同问题，S7 后来补了活跃 writer 跟踪，不能提前算进 S0。

### 10.12 get_config 与两个覆盖函数

`get_config()` 返回 KamaConfig 实例：先建立默认 dataclass，再加载 .env，确定 config_path，读 TOML 并调用 `_apply_toml`，最后 `_apply_env`。只有最后一步完成后才拿到完整生效配置。

`_apply_toml(config, data)` 原地修改传入对象，返回 None。它检查允许的小节和字段类型，未知键会 SystemExit。`_apply_env(config)` 同样原地覆盖；环境变量都是字符串，需要对 port 做 int 转换。

示例：默认端口 7437，TOML 写 8000，系统环境写 9000，结果是 9000。`.env` 写 7000 但系统已经有 9000 时，override=False 让系统值保留。不要把“加载 .env 在前”误解成它优先级最低。

### 10.13 setup_logging 与 make_error

`setup_logging(config)` 配置 root logger、输出格式、stderr handler 和可选滚动文件 handler。它会清空已有 handlers，所以多次调用会替换日志出口；这是进程级副作用，不是局部打印。

`make_error(id, code, message, data)` 只构造 JsonRpcError 与内部错误对象，不发送报文。先构造再统一发送，让每个错误分支少写重复字段。

### 10.14 协议文档生成的三个方法

`scripts/gen_protocol_doc.py::_model_section` 接收模型类型，调用 model_json_schema，遍历 properties 和 required，生成字段表、schema 和可选例子。`generate()` 把选定协议模型的片段拼成整篇字符串。脚本 `main()` 解析是否 --check，决定写文件还是比较当前文件内容。

模型是字段定义来源，但哪些模型要被列出仍需生成脚本接线。新增一个命令类，不代表它自动出现在所有地方：还需要注册 handler、维护 union、更新生成逻辑和测试。

## 11 跟着一个变量做手工执行

在纸上写 `req_id=cli-1`，依次标注它在 CLI 字典、JSON 行、服务端 JsonRpcRequest、JsonRpcSuccess、CLI 响应模型中的位置。你会发现它没有参与 ping 业务计算，而是贯穿运输过程用于关联。

再追踪 `params.client`：CLI 设置它，服务端 handler 用于日志，返回 PongResult 不包含它。这说明并不是所有请求参数都会原样返回。

最后故意把 method 写成不存在的名字，停在 `_handlers.get()`。预期不会调用 ping handler，会回 `-32601`，而且响应 ID 仍对应请求。能提前说出这条路径，才算理解错误处理。

## 12 本阶段可改进的地方

| 改进 | 触发问题与实现方向 | 验收 |
| --- | --- | --- |
| 业务参数校验与错误码 | Ping handler 用模型校验；参数错返回 `-32602` | 错字段、缺字段、合法请求各一例 |
| 跨平台启停 | 信号注册和后台进程管理按平台封装 | Windows 与 Linux 均可启动、ping、退出 |
| 超长帧处理 | 实际读取接口可能把超限表现为 ValueError；统一捕获并关闭该连接 | 超限帧不会使服务异常退出，其他客户端仍可用 |
| 真正健康检查 | 后台 start/status 从仅连端口改为验证 pong | 普通 TCP 占用者不会被当成正确 Core |
| 协议版本协商 | 增加客户端和服务能力字段 | 不兼容客户端收到明确错误 |

适合你的第一个个人提交是“参数校验 + 错误码 + 测试 + 协议文档同步”。它小，但能完整练习工程闭环。
