# S8 中断与恢复链路速查

**先分清：open 用来查看和绑定会话；resume 用来提交恢复决定。打开历史后先显示选择，用户确认后才继续执行。**

本文只讨论绑定检查点的主 Agent 会话，按两条链路阅读：

1. 前端选择历史 → open → 显示恢复按钮 → resume → 继续执行。
2. 发生中断 → Run、Session、工具状态变化 → 保存或重新加载时修正。

## 1. 从前端选择历史，到恢复执行

### 第一步：选择历史会话，拿到 session_id

入口：[TUI._pick_session](../src/kama_claude/tui/app.py#L800)。

TUI 先请求 session.list，显示历史列表。用户选中一个历史会话后，前端拿到它的 session_id，再调用 _open_session → _load_session。

这里选择的是“打开哪个会话”，还没有决定是否继续中断任务。

### 第二步：session.open 返回历史和当前状态

入口：[TUI._load_session](../src/kama_claude/tui/app.py#L831) → [CoreApp._session_open_handler](../src/kama_claude/core/app.py#L139) → [Manager.open](../src/kama_claude/core/session/manager.py#L274)。

后端读取检查点，并调用 recover_orphaned_run 检查遗留状态。识别到中断时的修改规则见第 2 节。返回给前端的关键内容是：

| 字段 | 前端用来做什么 |
| --- | --- |
| messages | 重建已提交的对话与工具结果显示 |
| run.status、run.tools | 判断是否显示恢复面板，以及显示哪个按钮 |
| session.status | 设置会话状态和普通输入框是否可用 |
| running | 判断当前 Core 是否真的有活跃 Task |
| revision | 保存这次看到的版本，用户恢复时带回校验 |

CoreApp 还会把当前 TCP 连接绑定到这个会话的事件订阅。TUI 加载时先缓冲事件，显示快照后再处理水位之后的事件。

**这一步只打开和观察，不创建 Runner，不执行工具。** 如果原 Task 还在当前 Core 中运行，TUI 继续观察它；如果是中断 Run，进入下一步。

### 第三步：前端按工具状态选择恢复按钮

_load_session 先检查 Run：

```python
if run["status"] == "interrupted":
    self._append(RecoveryActions(revision, run))
```

随后 [RecoveryActions.compose](../src/kama_claude/tui/recovery.py#L77) 从后端返回的工具列表中筛选：

```python
unknown = [
    tool for tool in run["tools"]
    if tool["status"] in ("unknown", "executing")
]
```

| 检查结果 | 显示内容 | 点击后发送的 action |
| --- | --- | --- |
| unknown 为空 | “继续任务” | continue |
| unknown 非空 | 未知工具的名称、参数和“核实后重试” | retry_tool |
| 两种情况都提供 | “终止本轮” | abort |

所以，**工具 B 是 unknown 时，前端提供的是“核实后重试”，点击后发送 retry_tool。不会用 continue 绕过确认。**

未完成子 Agent 或未知 spawn_agent 是额外限制：当前只显示限制说明和“终止本轮”。

正常中断会话此时禁用普通输入，等待用户决定。历史里的工具块只是显示，不会重新执行。

### 第四步：用户点击按钮，前端发送 session.resume

入口：[按钮动作映射](../src/kama_claude/tui/app.py#L939) → [TUI._resume_session](../src/kama_claude/tui/app.py#L951)。

```python
session.resume({
    "session_id": 当前会话ID,
    "expected_revision": 打开时看到的检查点版本,
    "action": "continue" 或 "retry_tool" 或 "abort",
})
```

expected_revision 用于防止用户拿着旧页面操作；如果检查点已经变化，后端拒绝，前端重新打开会话刷新。

### 第五步：后端校验决定，保存成功后才启动

入口：[CoreApp._session_resume_handler](../src/kama_claude/core/app.py#L152) → [Manager.resume](../src/kama_claude/core/session/manager.py#L291)。

CoreApp 会先读取当前会话、绑定 Run 的事件归属，再调用 Manager.resume：

```text
检查是否已有活跃 Task
→ 取得会话锁，读取检查点
→ prepare_resume 校验版本、状态和用户选择
→ Manager 保存修改后的检查点
→ continue / retry_tool：创建后台 Task
→ abort：发送结束通知，不创建 Runner
```

[prepare_resume](../src/kama_claude/core/checkpoint/recovery.py#L57) 只检查和修改传入的数据，不保存、不创建 Task。

- continue：必须没有未知工具，原工具状态保持。
- retry_tool：必须存在未知工具，将其改为 pending。
- 两者都将 Run 改为 running、Session 改为 active，并保留原阶段和游标。
- abort：终止原 Run，给未配对的调用补上中断说明。未知工具注明“结果未知”，不能伪称未执行。

继续或重试还要检查工作目录、未完成子 Agent 等条件。保存失败不会启动任务。

### 第六步：新 Task、Runner 加载原状态，交回同一个 Loop

[Manager._run_session](../src/kama_claude/core/session/manager.py#L176) 创建 Runner，调用 run_and_capture(checkpoint=cp)。

[Runner._prepare_context](../src/kama_claude/core/runner.py#L283) 把原 Run 和工作历史装入 Context；组装模型、工具并检查兼容性后，进入 [Loop.run](../src/kama_claude/core/loop.py#L58)：

| 保存的 phase | 从哪里继续 |
| --- | --- |
| ready | 检查预算，开始下一 Step |
| llm | 重新请求当前 Step 的模型，不重复增加 Step |
| tools | 从 tool_index 指向的工具继续，复用已提交结果 |

**新建的是 Python Task 和 Runner，继续的是原 Run。** run_id、Step、预算、工作历史、提示和工具范围沿用检查点，不重复追加用户目标。retry_tool 改回 pending 后，执行前仍要正常检查权限。

resume 返回接受结果后，TUI 再 open 一次刷新最新状态，之后通过事件接收进度；接受恢复不代表模型和工具已经执行成功。

## 2. 发生中断后，各个状态怎么变

正常执行时：Run.status=running，Session.status=active。下面把“Core 仍活着”与“Core 已退出”分开。

### 情况 A：工具返回未知结果，Core 仍然活着

入口：[Loop._run_tools](../src/kama_claude/core/loop.py#L162) → [Runner._finish_run](../src/kama_claude/core/runner.py#L459)。

| 时刻 | Run.status | Session.status | 当前工具 |
| --- | --- | --- | --- |
| 正在执行 | running | active | executing |
| Loop 收到 outcome_unknown 并保存 | interrupted | 暂时仍是 active | unknown |
| Runner 收尾并保存 | interrupted | interrupted | unknown |

```text
Loop 保存未知结果，保留原游标
→ _run_tools 返回 False，Loop 返回
→ Runner 更新 Session 并保存，发送 run.interrupted 事件
→ 当前 Runner、Task 结束，Core 继续运行
→ TUI 收到事件后重新 open，显示“核实后重试”
```

mark_interrupted 只修改 Run；Session 在 Runner 收尾时才更新。未知工具不追加确定的 tool_result，也不推进游标，后面的工具不会执行。

### 情况 B：Core 被强制结束，来不及收尾

假设磁盘最后保存的 Run 仍是 running：

| 时刻 | Run.status | Session.status | 工具状态 |
| --- | --- | --- | --- |
| 最后成功保存 | running | active | pending / awaiting_approval / executing |
| Core 强制退出瞬间 | 磁盘不变 | 磁盘不变 | 磁盘不变 |
| 新 Core 检查遗留状态后 | interrupted | interrupted | executing → unknown；其他状态保持 |

[recover_orphaned_run](../src/kama_claude/core/checkpoint/recovery.py#L27) 的关键判断：

```text
检查点写着 running，但当前 Core 没有对应活跃 Task
→ 将 Run、Session 改为 interrupted
→ executing 工具改为 unknown
→ 保存，等待用户选择
```

这项检查可能在 Core 启动扫描、session.list、session.open 时发生。只有状态需要修正时才保存，不自动执行任务。

重新打开时，pending / awaiting_approval 可以普通继续；unknown 需要核实后重试。即使工具实际上还没开始，只要 executing 已保存，重启后也保守视为 unknown。

Core 强退时来不及发送事件，但 TUI 可以通过 open 返回的快照显示恢复面板，不需要先收到旧中断事件。

### 情况 C：在 Core 终端按 Ctrl+C，有机会正常收尾

```text
Core 进入 finally
→ Manager.shutdown 对业务 Task 调用 cancel()
→ 当前 await 抛出 CancelledError，传到 Runner
→ Runner 标记 Run=interrupted
→ _finish_run 将 executing 工具改为 unknown、Session 改为 interrupted
→ 保存、导出历史、尝试通知，再传播取消
→ Core 等待任务收尾，关闭其他资源并退出
```

最终 Run、Session 都是 interrupted；pending / awaiting_approval 工具保持原状态。下次打开已经保存的中断状态即可，前端仍按有无未知工具选择按钮。

保存失败、强制结束或断电不能保证完成上述收尾，之后以最后成功提交的检查点为准。

## 3. 用户决定后，状态如何变化

| action | Run.status / phase | Session.status | 工具 |
| --- | --- | --- | --- |
| continue | running / 保留原阶段 | active | 沿用原状态；存在未知工具时拒绝 |
| retry_tool | running / 保留原阶段 | active | unknown / executing → pending |
| abort | failed / finished | chat → waiting_for_input；one_shot → closed | 不再执行，补齐中断说明 |

原来已完成的工具不会因为恢复而重跑。后续正常结束时，Run 变为 success 或 failed；Runner 将 chat 会话设为 waiting_for_input，one_shot 设为 closed，然后保存并通知。

## 4. 读代码时记住这几个边界

- **只关闭 TUI：** Core 的业务 Task 继续执行，Run、Session 不会仅因断线变成中断；重连先打开原会话。
- **send_message 拒绝中断会话：** 这是防止新 Run 覆盖旧 Run 的保护。正常恢复先 open，再由用户点击发送 resume。
- **读取和识别遗留状态是两层职责：** CheckpointStore.load 读取校验文件，不改变运行状态；recover_orphaned_run 根据活跃 Task 识别遗留状态，必要时修改并保存。

**如果中断已经保存、会话尚未收尾就强退：** 磁盘可能留下 Run=interrupted、Session=active。重新加载时，recover_orphaned_run 确认没有活跃 Task 后，将 Session 补为 interrupted，保留原中断原因、执行阶段和工具游标。再次打开不重复修改修订号；前端随后根据有无 unknown 工具显示“继续任务”或“核实后重试”。
