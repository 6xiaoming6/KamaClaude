## 一、Python 与异步执行

### B01｜面试官：协程、Task、Future、await 是什么关系？

**标准回答：** async 函数调用通常先产生协程对象；await 驱动或等待可等待对象，Task 让协程由事件循环调度，Future 表示稍后才能得到的结果。项目用 Task 运行接收循环和子任务，用 Future 等待 RPC 响应与用户审批。Future 存在于本进程，收到网络响应后由分发逻辑完成。

#### B01.1｜追问：每个 await 都一定切换到别的协程吗？

**标准回答：** 不一定。等待对象已经就绪时可能直接继续执行；只有实际挂起，其他任务才有机会运行。判断竞态要看真实挂起点，不能只数 await 关键字。项目 Future 尚未完成时，await 才是明确的等待。

#### B01.2｜追问：直接调用 async 函数和 create_task 有何区别？

**标准回答：** 只取得协程对象不会自动把任务执行完；await 会在当前调用链等待它，create_task 则把协程交给循环并发调度。后台任务应保留强引用并处理结束/异常。项目 Task 注册表既承担引用管理，也应承担生命周期管理，后者目前还不完整。

**关联：** [SocketClient](../../src/kama_claude/core/transport/socket_client.py)、[Python Future](https://docs.python.org/3.12/library/asyncio-future.html)。

### B02｜面试官：使用 async 就不会阻塞了吗？

**标准回答：** 不会自动消除阻塞。同步文件读写、time.sleep 或长计算仍能占住事件循环线程。项目 Trace 虽有后台队列，其消费者仍做同步文件写入。我的优化会先测耗时，对阻塞 I/O 考虑线程卸载或分批，对纯 Python CPU 密集工作考虑进程，并保持状态边界清楚。

#### B02.1｜追问：多线程能让 Python 计算利用多核吗？

**标准回答：** 按本项目常规 CPython 3.12 的 GIL 环境，多个线程不能同时执行 Python 字节码，因此纯 Python CPU 计算不自动获得多核并行；I/O 等待或释放 GIL 的扩展另论。不能把这个结论套到所有 Python 版本和构建。

#### B02.2｜追问：把读文件改成 to_thread 就一定安全？

**标准回答：** 它可以避免该同步操作直接占住事件循环，但没有自动提供文件事务、线程安全或强制取消。等待协程取消后，线程操作可能仍继续。共享状态要有所有者，大文件也要限制读取量，不能仅把无界工作移到线程池。

**关联：** [TraceWriter](../../src/kama_claude/core/trace/writer.py)、[GIL FAQ](https://docs.python.org/3.12/faq/library.html#cant-we-get-rid-of-the-global-interpreter-lock)、[事件循环](https://docs.python.org/3.12/library/asyncio-eventloop.html)。

### B03｜面试官：asyncio 单线程为什么还用 Lock？

**标准回答：** 多步业务如果跨等待点，会与其他协程交错，单线程也可能出现逻辑竞争。会话锁保护“追加输入、执行 Run、保存状态”这一业务区间。Semaphore 更适合限制同时在途的模型请求或后台子任务数。asyncio 同步原语不是跨线程、跨进程锁。

#### B03.1｜追问：持锁等待模型是不是设计错误？

**标准回答：** 不一定。若同会话要求消息严格串行，持锁覆盖整轮有明确语义，其他输入应返回 busy 或排队。代价是长任务期间不能同会话并行。审批响应必须走不被该锁阻塞的路径；如果想缩短临界区，就需版本和状态转换来保证一致性。

#### B03.2｜追问：每会话锁能保护两个会话写同一文件吗？

**标准回答：** 不能，两把不同锁没有互斥关系。共享文件需要工作区/路径级协调或版本校验。当前 locked 检查紧接 acquire 的区间也不能不看挂起行为就断定必有竞争；正确性要以具体资源和临界区分析。

**关联：** [SessionManager](../../src/kama_claude/core/session/manager.py)、[同步原语](https://docs.python.org/3.12/library/asyncio-sync.html)。

### B04｜面试官：cancel 与 wait_for 超时能强制终止操作吗？

**标准回答：** 对协程主要是协作式取消，在适当时机投递 CancelledError；能否及时退出取决于是否响应并正确传播。wait_for 超时会尝试取消等待对象并等待其处理，因此可能超过标称时间。清理应写 finally，远端模型与已发生的副作用不会自动回滚。调度取消也不会自动改业务字段：本项目在工具阶段取消独立 Loop 的实验中，Task.cancelled 为真，Context.status 仍为 running、reason 为 None。

#### B04.1｜追问：except Exception 能接住 CancelledError 吗？

**标准回答：** Python 3.12 中不能，CancelledError 继承 BaseException。Loop 的专门捕获只包住 Provider 调用，所以模型等待中的取消会标记 failed/cancelled，工具或审批阶段取消则可能直接传播而不更新 Context。顶层 Runner 在更外层捕获，能为其覆盖的执行路径补收尾；子 Agent 直接运行 Loop，不经过同样的 Runner。需要准确说明取消发生位置和状态所有者。

#### B04.2｜追问：为什么取消后还要 await task？

**标准回答：** cancel 只发出请求，await 用于等待受管任务响应、完成其实际编写的清理并观察结果；它不会凭空补出缺失的 finally、更新业务状态或杀掉外部进程。独立 Loop 的上述实验中，await 已收到取消，Context 仍未更新。因此还要由所有者定义状态收尾、资源清理和期限，外部资源采用独立的终止与回收策略。

**关联：** [Loop](../../src/kama_claude/core/loop.py)、[取消与超时](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)、[异常层级](https://docs.python.org/3.12/library/asyncio-exceptions.html)。

### B05｜面试官：gather 与 TaskGroup 怎样选择？

**标准回答：** gather 用于收集多个结果，默认一个子任务出错不意味着自动取消所有其他子任务；TaskGroup 将子任务放在结构化作用域，普通子异常会引发其他任务取消、等待收尾并组合异常。选哪种取决于任务是否需要共同成败，以及谁拥有生命周期。

#### B05.1｜追问：独立后台子 Agent 应放进父 Run 的 TaskGroup 吗？

**标准回答：** 如果要求它活得比父 Run 更久，就不应被短 Run 的作用域无条件限制。应由 Core 级服务持有并管理，再定义父结束后等待、取消还是移交。结构化并发的价值是所有权清楚，不是所有任务都机械放到同一个作用域。

#### B05.2｜追问：return_exceptions=True 会把业务失败变成功吗？

**标准回答：** 不会，它只是把异常作为返回项，调用者仍要检查。更何况项目 Loop 可能正常返回但 Context 已 failed，这种失败不会成为 Python 异常。并发结果与业务状态必须分别解释。

**关联：** [CoreApp 退出等待](../../src/kama_claude/core/app.py)、[Python 任务组](https://docs.python.org/3.12/library/asyncio-task.html#task-groups)。

### B06｜面试官：drain、close、wait_closed、flush、fsync 有什么区别？

**标准回答：** 网络 drain 管本地写缓冲背压，close 发起关闭，wait_closed 等本地传输关闭；文件 flush 把语言层缓冲交给底层，fsync 请求相应持久化。它们分别属于网络流控、资源释放和文件保存，不是同一种“刷新”。具体崩溃持久性还依赖系统与存储。

#### B06.1｜追问：每条事件都 flush，能否说数据不会丢？

**标准回答：** 不能。flush 不等于断电事务保证，meta/thread/events 也没有一起原子提交。程序崩溃还可能留下部分行或状态不一致。要声明何种故障保证，就要设计相应提交与恢复协议并做故障测试。

#### B06.2｜追问：收到 RPC success 是否证明文件已可靠保存？

**标准回答：** 取决于 handler 的实际提交顺序与保存保证。RPC 只是返回了应用结果，不能凭 success 字段推出 fsync 或事务。当前 run.finished 还先于历史追加，事件结束与提交完成不能混为一谈。

**关联：** [EventWriter](../../src/kama_claude/core/events/writer.py)、[Streams](https://docs.python.org/3.12/library/asyncio-stream.html)、[os 文件操作](https://docs.python.org/3.12/library/os.html)。

### B07｜面试官：exec 和 shell 子进程有什么区别？

**标准回答：** create_subprocess_exec 接收可执行文件与参数，create_subprocess_shell 让 shell 解释命令字符串，支持管道、重定向等，也增加解释和注入风险。项目 MCP stdio 使用 exec 启动服务，BashTool 使用 shell 执行用户授权命令。两者平台行为也要分别验证。

#### B07.1｜追问：只 await proc.wait() 为什么可能卡住？

**标准回答：** 若 stdout/stderr 是 PIPE，子进程输出填满缓冲后会等待读取，而父进程又只等待它结束，便形成等待链。要用 communicate 或持续消费管道。communicate 会收集输出，因此大输出还需有界流式处理，避免只把死锁换成内存问题。

#### B07.2｜追问：kill 父进程能保证清理全部后代吗？

**标准回答：** 不能自动保证。shell 可能启动其他进程，进程树与组的行为因平台而异。需要设计进程组/受管执行边界、终止升级与 wait 回收，并分别验证 Windows 与 Linux。当前工具不能声称具有完整进程树沙箱。

**关联：** [BashTool](../../src/kama_claude/core/tools/builtin/bash.py)、[McpClient](../../src/kama_claude/core/mcp/client.py)、[Python 子进程](https://docs.python.org/3.12/library/asyncio-subprocess.html)。

### B08｜面试官：ClassVar[type[BaseModel] | None] 怎样理解？

**标准回答：** ClassVar 表示类级属性的类型意图；type[BaseModel] 表示一个模型类而非模型实例；`| None` 允许不提供，默认值是 None。工具子类可指定 `params_model = BashParams`，统一入口随后通过这个类调用 model_validate。类型标注本身通常不会自动执行运行时验证。

#### B08.1｜追问：为什么不写 BashParams()？

**标准回答：** 那会试图立刻创建一个参数实例，而工具尚未收到用户参数，必填字段也可能缺失。这里需要保存“以后用什么类解析参数”，所以保存类对象；实际调用时才把具体参数传给它。

#### B08.2｜追问：ClassVar 会禁止通过实例赋值吗？

**标准回答：** 不是通用的运行时禁止机制，主要提供给类型检查器和相关框架理解属性用途。是否限制实例赋值要看类和框架的实现。项目真正的参数检查来自 model_validate，不能把两者归为同一机制。

**关联：** [BaseTool](../../src/kama_claude/core/tools/base.py)、[BashParams](../../src/kama_claude/core/tools/builtin/bash.py)。

### B09｜面试官：Context 里的 dict(m) 是深拷贝吗？

**标准回答：** 不是。它新建外层字典，但其中 content 列表和块字典可能仍引用原对象。新建消息列表也不意味着全部嵌套状态隔离。若后续原地追加工具块，持有相同嵌套对象的其他结构可能一起观察到变化。

#### B09.1｜追问：truncate_tool_results 会把所有块都复制吗？

**标准回答：** 不会。它对需要截断的块做字典复制，对一些容器重新组织，未修改的块或消息仍可能复用引用。因此不能把“返回新列表”当成完整深拷贝。分析时要沿每层对象关系看实际复制位置。

#### B09.2｜追问：Trace 入队时为什么也可能需要快照？

**标准回答：** 记录对象若保存仍在变化的 messages 引用，而真正序列化在稍后的后台消费者中完成，可能记录到入队之后的状态。可在边界序列化、复制必要数据或使用不可变结构，代价是 CPU 与内存；应以时序测试验证，而非无差别 deepcopy 全系统。

**关联：** [Context](../../src/kama_claude/core/context.py)、[budget.py](../../src/kama_claude/core/compact/budget.py)、[copy 文档](https://docs.python.org/3.12/library/copy.html)。

### B10｜面试官：字典查找为什么通常快，注册表为什么还要淘汰？

**标准回答：** 哈希表通过哈希定位候选位置，常见条件下查找平均 O(1)，冲突和扩容等使最坏或单次耗时不同。快查找不代表存储无成本。后台任务若保留完整 Context，记录不断增加仍会占内存，需要容量、过期和运行中任务的保留规则。

#### B10.1｜追问：LRU 怎样做到快速查找与调整顺序？

**标准回答：** 可用哈希表定位节点，双向链表维护使用顺序；命中后移到头，超容量从尾删除，操作平均 O(1)。Python 可借助有序容器实现，但项目当前并没有因此自动获得 LRU。运行中的任务不应被普通结果缓存策略随意淘汰。

#### B10.2｜追问：查不到任务怎样区分未知和已过期？

**标准回答：** 需要协议或元数据明确表达，例如短期保留过期标记、给出结果保留期，或从持久记录查询。简单字典 get 返回 None 无法区分两种历史。当前注册表没有完整过期方案，设计时还需限制跨会话读取。

**关联：** [BackgroundTaskRegistry](../../src/kama_claude/core/subagent/registry.py)、[SocketClient.pending](../../src/kama_claude/core/transport/socket_client.py)。

### B11｜面试官：进程、线程、协程在项目里分别对应什么？

**标准回答：** Core 与 TUI 是不同进程，地址空间分开，通过 TCP 交换数据。进程内线程共享许多资源，各有执行栈。协程由线程内事件循环调度，适合等待 I/O。子 Agent 通常是 Core 内协程任务；stdio MCP 服务另起进程，BashTool 也会启动命令进程。

#### B11.1｜追问：子 Agent 能自动利用多个 CPU 核吗？

**标准回答：** 当前没有自动把 Python 子 Agent 计算分到多核，它们主要并发等待网络和工具。真正计算可能由外部服务或子进程完成；同一个事件循环中的纯计算仍会互相阻塞。并发数量与 CPU 并行能力不能等同。

#### B11.2｜追问：其他线程能直接完成 asyncio Future 吗？

**标准回答：** asyncio Future 通常不是线程安全对象，应通过所属事件循环的线程安全调度入口，例如 call_soon_threadsafe，将更新交回该循环。跨进程更不能直接共享这个 Future；项目审批是先用 RPC 传数据，再在 Core 内完成 Future。

**关联：** [子 Agent](../../src/kama_claude/core/subagent/tool.py)、[Future 线程安全说明](https://docs.python.org/3.12/library/asyncio-future.html)、[事件循环](https://docs.python.org/3.12/library/asyncio-eventloop.html)。

### B12｜面试官：死锁的四个条件是什么，项目里怎样对应？

**标准回答：** 经典资源死锁的必要条件是互斥、占有并等待、不可剥夺和循环等待。项目审批问题最直接的解释是控制流等待环：读取循环等长 handler，handler 等审批，审批响应却等读取循环继续读。分析时应画等待关系，而非机械声称一定存在两把互斥锁。

#### B12.1｜追问：没有显式 Lock 就不会死锁吗？

**标准回答：** 仍可能永远等待。Future、消息、管道和任务完成都能形成等待环。具体系统未必逐项对应经典资源模型，但可以通过等待图找到无法推进的依赖。项目旧式串行请求读取就是没有两把锁也会卡住的例子。

#### B12.2｜追问：把所有请求并发执行能消除所有等待问题吗？

**标准回答：** 只能破除特定读取等待链，新的共享状态仍可能产生锁顺序冲突或资源耗尽。应同时设计业务锁、限额、超时、任务所有权与清理，检查审批路径不被同会话执行锁阻塞。

**关联：** [SocketServer._read_loop](../../src/kama_claude/core/transport/socket_server.py)、[PermissionManager](../../src/kama_claude/core/permissions/manager.py)。

## 二、网络与可靠执行

### B13｜面试官：TCP 为什么通常三次握手，关闭通常四次？

**标准回答：** 以普通客户端主动连接为例：客户端发 SYN，序号 x；服务端回 SYN+ACK，序号 y、确认 x+1；客户端回 ACK，确认 y+1。前两步让客户端得到服务端初始序列号及对自己 SYN 的确认；第三步让服务端知道自己的 SYN 也被对端确认，完成双向序列号同步。只有两步时，服务端无法据此确认对端收到自己的 SYN；对延迟旧 SYN，最终确认还可避免把没有有效对端确认的尝试当成完整连接。关闭时两个方向独立结束，FIN 与确认可能分开或合并，因此常见四步但不是固定四包。这是简化的正常流程，实际还会有重传等情况。

#### B13.1｜追问：TCP 是消息流还是字节流？

**标准回答：** 字节流。应用需要自己恢复消息边界；项目使用序列化单行 JSON 加换行。TCP 负责传输顺序，不知道一段字节表示一个 RPC 还是两个事件，readline 才按应用约定切出帧。

#### B13.2｜追问：半关闭意味着什么？

**标准回答：** 一个方向已经发送完，不代表反方向也必须立即结束；应用可停止发送后继续读取。项目多数客户端采用完整关闭流程，不能从一端 EOF 自动推出对端所有业务任务已结束。

**关联：** [Socket 传输](../../src/kama_claude/core/transport/)、[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

### B14｜面试官：TCP 可靠，工具是不是就恰好执行一次？

**标准回答：** 不是。服务完成工具操作后响应丢失，客户端无法确定结果，重连重试可能再次执行。TCP 的有序可靠传输不提供业务事务。JSON-RPC ID 主要关联请求响应，当前没有与副作用一起提交的持久去重记录。

#### B14.1｜追问：用一个 UUID 去重就能保证所有外部操作恰好一次吗？

**标准回答：** 还取决于去重记录与副作用能否原子提交。如果先执行外部操作再记 UUID，中途崩溃会重复；先记成功再执行又可能漏执行。需要下游支持幂等键、可查结果或事务协调；无法保证时要呈现结果未知，避免虚构 exactly-once。

#### B14.2｜追问：文件写入与追加、扣费能用同一种幂等语义吗？

**标准回答：** 不能笼统处理。写相同内容覆盖同一路径与重复追加的副作用不同，扣费又依赖外部系统的操作键和查询机制。应为每种工具定义重试与去重能力，当前统一 runtime_error 重试需要收紧。

**关联：** [invoke_tool](../../src/kama_claude/core/tools/invocation.py)、[SocketClient](../../src/kama_claude/core/transport/socket_client.py)。

### B15｜面试官：TIME_WAIT、CLOSE_WAIT、RST 怎样帮助排查？

**标准回答：** TIME_WAIT 与连接终止后的旧报文处理和最后确认有关；CLOSE_WAIT 表示收到对端关闭而本地尚未完成关闭；RST 表示连接重置。状态归属取决于关闭时序，不是固定客户端/服务端角色。大量 CLOSE_WAIT 可提示检查本地资源释放。

#### B15.1｜追问：Core 提示端口占用一定是旧 Core 吗？

**标准回答：** 不一定。当前探测主要尝试建立 TCP 连接，其他程序监听同端口也可能被当作已有 Core。应该核对端口与进程，并用应用层 ping 验证服务身份；探测与真正绑定之间也仍有竞争，绑定失败要正确报告。

#### B15.2｜追问：TUI 频繁重连应该先查什么？

**标准回答：** 先区分连接拒绝、服务主动关闭和接收任务异常，再对照 Core/TUI 日志与 TCP 连接状态。检查配置端口、Core 是否存活、帧解析与回调是否出错。不能看到 disconnected 就直接认定模型 API 故障。

**关联：** [SocketServer.start](../../src/kama_claude/core/transport/socket_server.py)、[TUI](../../src/kama_claude/tui/app.py)、[TCP 状态](https://www.rfc-editor.org/rfc/rfc9293.html)。

### B16｜面试官：WebSocket 与 SSE 怎样选？

**标准回答：** WebSocket 适合连接内双向消息；SSE 的 EventSource 适合服务端事件流，用户命令可以另走 HTTP。要结合认证、代理、重连与交互频率选择。它们有各自帧/事件格式，当前项目的 NDJSON 不能直接当作两者使用。

#### B16.1｜追问：浏览器为什么不能直接连项目的裸 TCP？

**标准回答：** 普通网页没有通用裸 TCP Socket API，需要服务提供浏览器支持的协议入口。可以用 WebSocket 网关或 HTTP 加事件流，把业务方法与事件映射过去；这不要求重写 Loop，但要补身份和连接管理。

#### B16.2｜追问：SSE 自动重连是否等于任务自动恢复？

**标准回答：** 不等于。事件 ID 可帮助客户端带游标重连，但服务要保留可回放数据、处理重复和缺口，还要恢复会话状态。传输重建与业务执行恢复是不同层次，项目当前没有因为实现 TCP 重连就具备这些保证。

**关联：** [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)、[WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

### B17｜面试官：重试、退避、幂等和熔断是什么关系？

**标准回答：** 重试处理可能暂态的失败；退避与抖动减少集中重试的冲击；幂等约束重复副作用；熔断在持续故障时暂时阻止调用并探测恢复。当前有工具有限重试和部分 Provider 网络重试，没有完整熔断、总重试预算与全工具幂等框架。

#### B17.1｜追问：429、参数错误和执行后超时分别怎样处理？

**标准回答：** 429 可在可重试与总预算内遵守服务提示等待；参数错误应修改输入；执行后超时属于结果可能未知，先查询或用业务幂等机制，不能直接重复写操作。HTTP 状态只是线索，还要看具体服务语义与已经发生的副作用。

#### B17.2｜追问：为什么必须限制整条链路的重试预算？

**标准回答：** Provider、SDK、工具与外层任务可能各自重试，叠加会放大请求数和时长；异常没有匹配也可能完全进不了某层重试。当前本地 Anthropic SDK 使用 httpx2 并可包装连接异常，项目外层却捕获 httpx，不能直接按“三次”推算真实请求数。要记录实际尝试、SDK 版本与异常，设置总 deadline 和预算，再明确由哪层重试。外层请求次数上限也不等于底层 HTTP 请求次数上限。

**关联：** [Provider](../../src/kama_claude/core/llm/provider.py)、[invoke_tool](../../src/kama_claude/core/tools/invocation.py)。

## 三、持久化、模型与工程验证

### B18｜面试官：JSONL 能代替数据库事务吗？

**标准回答：** JSONL 方便追加和逐行处理，但不会自动保证 meta、thread、notes、事件与外部副作用一致。单文件也可能有部分行和并发写问题。项目文件方案适合观察机制，若要求跨实体原子提交，需要显式协议或事务存储。

#### B18.1｜追问：临时文件加原子替换解决哪些问题？

**标准回答：** 可减少读者看到半写新快照的风险：先在同文件系统写好并校验临时文件，再替换目标。还要考虑必要同步、备份和平台差异。它不自动保证多个文件同时提交，也不把远端工具副作用纳入事务。

#### B18.2｜追问：当前 write_compacted 的风险在哪里？

**标准回答：** 它先把旧 thread rename 成备份，再创建并写新文件；中途失败可能没有完整的新权威文件。应定义备份发现与恢复、快照版本和提交顺序，并测试磁盘满、写失败和进程中断。保留备份有帮助，但不等于已有自动恢复协议。

**关联：** [SessionStore.write_compacted](../../src/kama_claude/core/session/store.py)、[os.replace/fsync](https://docs.python.org/3.12/library/os.html)、[SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)。

### B19｜面试官：有界队列、背压和事件顺序怎么设计？

**标准回答：** 消费慢于生产时，队列必须选择等待、合并、采样、拒绝或断开等策略。无限队列把延迟变成内存风险。对客户端可使用独立缓冲，按 Run 序号检测重复与缺口；关键状态事件与可合并 token 应有不同策略。当前 Trace 无界、广播串行等待，尚未实现完整隔离。

#### B19.1｜追问：队列满时直接丢所有事件行不行？

**标准回答：** 不行。丢 token 可能影响展示，丢审批或结束事件可能让流程无法推进。应保留权威业务状态与可查询结果，对高频展示做合并，并明确事件缺口如何补。不能让一个通用丢弃策略承担全部语义。

#### B19.2｜追问：消费者崩溃后 queue.join 为什么可能等不完？

**标准回答：** join 等的是所有已入队任务被 task_done 标记完成，不是只看队列空。消费者退出后若没有继续处理或完成标记，等待者可能一直挂起。关闭需先管理生产者，再监督消费者错误、排空和超时，并对失败记录给出结果。

**关联：** [TraceWriter](../../src/kama_claude/core/trace/writer.py)、[广播器](../../src/kama_claude/core/transport/ipc_broadcaster.py)。

### B20｜面试官：Token、Attention、KV Cache、Prompt Cache 有何区别？

**标准回答：** Token 是模型分词单位，不等于字数；缩放点积 Attention 的基本式为 `softmax(QKᵀ/√d_k)V`，d_k 是键向量维度。KV Cache 在自回归生成时复用历史键值；API Prompt Cache 复用服务支持的提示前缀处理。二者不替代会话数据库，也不会自动缩短活动历史；缓存内容仍属于模型输入上下文。当前 context_pct 对缓存输入的计算有口径缺口，不能理解为缓存命中后这些 token 不占上下文。厂商规则与价格需按实际版本核对。

#### B20.1｜追问：为什么不能用字符数除以四做精确预算？

**标准回答：** 分词随语言、模型和内容变化，中文与代码也没有固定的字符/token 比。项目摘要采用除以四的粗估，不是 tokenizer 结果。我会用对应分词器或服务估算，并纳入 system、工具 Schema 和输出预留；调用后还要按 Provider 正确解释 usage。即使 token 数来自真实响应，若漏加 Anthropic 缓存输入或使用错误窗口，比例依然会错。

#### B20.2｜追问：工具顺序或系统提示改变为何可能影响缓存？

**标准回答：** 前缀缓存与实际内容和顺序有关，改动可能减少可复用前缀，但命中要看 usage，不能凭 cache_control 判定。Anthropic 的总输入为 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`；当前只用第一项计算窗口占比，可能低估。其他 Provider 要核对口径，不能机械套加法，例如已包含缓存的总输入再加缓存会重复计数。缓存需要存储与处理，也不证明所有任务成本下降；固定价格和命中率都不应凭空填写。

**关联：** [UsageStats 与窗口计算](../../src/kama_claude/core/llm/provider.py)、[Transformer 原论文](https://arxiv.org/abs/1706.03762)、[KV Cache](https://huggingface.co/docs/transformers/en/cache_explanation)、[Prompt Cache](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

**统计依据：** [Anthropic 总输入与缓存字段](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance)，与 P34.2 使用相同统计口径；当前代码尚未因此获得修复。

### B21｜面试官：如果给项目增加 RAG，需要补什么？

**标准回答：** 需要文档解析与切块、来源和权限元数据、索引、检索、可选重排、上下文构建、引用和评测。RAG 解决从外部知识取什么，历史压缩解决已有交互怎样变短。当前 Markdown 注入与 note_save 没有这些检索模块，所以这是拓展设计。

#### B21.1｜追问：精确错误码与语义问题用同一种检索合适吗？

**标准回答：** 可以建立混合基线：关键词匹配照顾精确标识符，向量检索补语义相似，再融合/重排。是否提升要用标注依据的任务集比较，也要检查中文分词和切块。不能看到向量库返回结果就认定召回正确。

#### B21.2｜追问：文档更新、删除和权限怎样保持一致？

**标准回答：** 给文档与 chunk 稳定 ID、版本与归属，更新时提交新索引版本，删除时同步清理检索和缓存。权限应约束实际检索与引用，不能检索完全部私密内容后仅让模型自觉不说。先定义一致性窗口，再按要求设计事务或任务补偿。

**关联：** [现有 Memory](../../src/kama_claude/core/memory/loader.py)、[RAG 原论文](https://arxiv.org/abs/2005.11401)。

### B22｜面试官：单元测试、集成测试与 Agent 评测有何区别？

**标准回答：** 单元测试检查局部确定行为，集成测试验证组件或真实进程接线，Agent 评测检验模型驱动任务的产出与约束。用假 Provider 验证工具配对，不代表真实模型必然正确调用；任务演示成功也不证明错误与取消路径可靠。三者互补。

#### B22.1｜追问：怎样写自动压缩漏存的测试？

**标准回答：** 构造长历史，假 Provider 产生 tool_use 和 usage，使自动压缩触发，再产生后续回复；Runner 保存后重新加载并启动下一轮，断言摘要工作历史和新增消息符合预期。原代码应在跨轮断言失败，再用修复后通过证明覆盖了故障。

#### B22.2｜追问：为什么不能只让另一个模型打分？

**标准回答：** 自动评判也会受提示、模型偏差和同类错误影响。可核验产出优先用脚本、测试和标注依据；语义判断用明确标准并人工抽查。报告样本、失败分类与评判版本，避免把一个主观分数直接叫业务成功率。

**关联：** [tests/unit/](../../tests/unit/)、[tests/integration/](../../tests/integration/)。

### B23｜面试官：若改用数据库，你怎样建模？

**标准回答：** 可按 session、run、message、event、approval、background_task 建实体，明确外键、消息顺序、状态、版本与归属。同库事务维护相关记录，唯一操作键支持去重；外部工具不会自动参加事务。对本地项目可先评估 SQLite，只有需求达到时再考虑远程数据库。当前未实现这个方案。

#### B23.1｜追问：重启时数据库里还是 running 怎么办？

**标准回答：** 数据库状态不等于活协程。单机启动可将未完成记录识别为 interrupted；多执行者还需租约或心跳和所有者。是否允许重试由工具副作用与检查点决定，不能见 running 就无条件重放全部任务。

#### B23.2｜追问：可以开一个事务包住整个模型调用吗？

**标准回答：** 通常应避免长时间持有数据库事务和锁等待外部网络。先短事务登记状态与版本，执行外部调用，再短事务校验并提交结果，明确中途失败恢复。数据库事务只能保证它管理的修改，不能自动回滚模型费用和 shell 副作用。

**关联：** [当前 SessionStore](../../src/kama_claude/core/session/store.py)、[SQLite 提交机制](https://www.sqlite.org/atomiccommit.html)。

### B24｜面试官：怎么写稳定的异步测试？

**标准回答：** 用 Event/Future 表达就绪与完成，避免固定 sleep 猜时序；每次等待有合理上限，finally 中取消并 await 自己创建的任务。使用临时目录、隔离环境与假网络服务；断言业务状态、落盘和事件，不只断言函数被调用。Core 集成测试用就绪探测并输出失败日志。

#### B24.1｜追问：先找空闲端口、释放后让 Core 绑定有竞争吗？

**标准回答：** 有，另一进程可能在间隙抢占。测试可以采用由服务绑定端口零后报告实际端口等方式减少竞争，或对冲突明确重试；当前 fixture 不应被描述为完全消除此风险。启动慢也需区分真失败与固定超时太短。

#### B24.2｜追问：如何确认没有 pending task 泄漏？

**标准回答：** 跟踪测试创建的任务集合，在结束时请求取消并等待，检查其完成/异常状态；必要时开启异步调试并比较受管任务基线。不要把 pytest 自身任务一起取消。对于子进程还要单独 wait 和检查退出，Task 清空不证明进程树已清空。

**关联：** [conftest.py](../../tests/conftest.py)、[CoreApp 测试](../../tests/unit/test_core_app.py)、[Python 协程与任务](https://docs.python.org/3.12/library/asyncio-task.html)。
