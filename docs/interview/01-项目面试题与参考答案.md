## 一、项目开场与架构

### P01｜P0：请用 90 秒介绍项目，不要从 S0 开始背章节

**考察：** 是否理解问题背景与整体结构。

**参考答案：** 这是基于开源阶段项目学习和改进的本地 Coding Agent。Core 常驻，TUI 通过本地 TCP 发 JSON-RPC 命令并接收运行事件。Core 为每条消息组织一次 AgentLoop，模型决定工具调用，程序做参数与权限检查、执行并回填结果。会话历史、笔记和上下文治理支持连续任务，S7 扩展 Skill、子 Agent 与 MCP。我的具体改动是实际做过的适配与验证；当前还不是生产服务，已识别自动压缩保存和后台任务跨轮等边界。

**连续追问：** 用户是谁？为什么要常驻 Core？你具体写过哪部分？

**证据：** [CoreApp](../../src/kama_claude/core/app.py)、[Runner](../../src/kama_claude/core/runner.py)。不要用“完整自主智能平台”替代机制说明。

### P02｜P0：这个项目是你独立做的吗？哪些是你的贡献？

**考察：** 真实性、责任边界与工程参与程度。

**参考答案：** 明确说明开源基础与来源，再挑两三项自己能解释到代码的适配、测试或故障定位。举例：Provider 内部消息转换；Windows 不支持同样信号注册后的 finally 清理；S6/S7 合并时保留压缩工厂和 MCP 退出。用提交 diff、复现步骤、测试支持。仅发现问题就说定位，未修复不能说优化完成。

**连续追问：** 不看 AI 输出，你能解释某段修改吗？如果去掉你的改动，哪个场景会失败？

**证据：** git log、具体 diff、失败前后日志。学习注释和文档也是工作，但不等同于原创架构。

### P03｜P0：为什么分成前端与 Core 两个进程？

**参考答案：** 分开界面生命周期与任务运行，CLI/TUI 可以复用协议和业务入口，Core 集中管理工具、权限和事件。代价是协议版本、断线、取消与状态归属更复杂。当前连接断开不会天然停止任务，TUI 重连也会创建新 session，不能声称已实现可靠断线续跑。

**追问：** 单进程能不能做？Core 崩溃后恢复什么？为何没采用浏览器前端？

**证据：** core/app.py、tui/app.py、core/transport/。

### P04｜P0：我输入“读取文件并生成报告”，完整请求链路是什么？

**参考答案：** TUI 提交 → SocketClient 发送请求 → SocketServer 按 method 路由 → SessionManager 检查会话锁并先保存用户输入 → 工厂创建 Runner → 加载历史和三层背景、组装工具表与 Provider → AgentLoop 请求模型 → invoke_tool 校验审批并执行 → tool_result 回填 → 模型继续或结束 → Runner 保存新增消息 → 会话等待输入。事件旁路实时展示；session.send_message 当前等待整轮结束才响应。

**追问：** 哪一步落盘？哪一步可能重复？执行到一半取消会发生什么？

**证据：** session/manager.py、runner.py、loop.py。能画出控制流与事件流两条线。

### P05｜P1：为什么自己写循环，不直接用 LangGraph 等框架？

**参考答案：** 学习项目用较小循环暴露状态、工具与协议机制，便于定位问题；不能据此证明框架不合适。若需要复杂分支、持久检查点、可恢复长工作流，要评估成熟框架或执行引擎。比较应基于任务形态、恢复需求、维护成本与评测，不是“自研一定更快”。

**追问：** 当前循环表达不了什么？迁移时哪些接口可保留？

**证据：** loop.py；工具、Provider、存储接口可以作为适配边界。

### P06｜P0：这是 ReAct、Plan-and-Execute，还是固定工作流？

**参考答案：** 当前主循环是模型决策、工具执行、观察结果再决策，可视为 ReAct 风格的工具循环，并没有要求展示模型隐式推理全文。orchestrate Skill 用提示引导规划/执行/审查，未用程序强制每个节点与顺序。固定工作流更可控，开放式循环更灵活但需要终止、预算与结果验证。

**追问：** 反复调用同一个工具怎么办？审查永不通过怎么办？

**答到这里再加分：** 设总步骤/时限、重复状态检测、失败升级与人工介入，不靠无限重试“等模型成功”。

### P07｜P0：session、run、step、清单 Task、asyncio.Task 有什么区别？

**参考答案：** session 关联多轮对话；run 处理一条用户消息；step 是主循环的一次模型请求及后续处理；任务工具的 Task 是磁盘工作清单；asyncio.Task 是调度协程的对象。它们不是一一对应。摘要请求、网络重试也可能带来额外 API 调用，所以 step 数不等于请求总数或成本。

**追问：** 子 Agent 是新 session 吗？新 Runner 是新进程吗？

**证据：** context.py、runs.py、task/、subagent/；回答应指出“都不是自动等同”。

## 二、传输、事件与可观测性

### P08｜P0：为什么用 TCP，不用 WebSocket、HTTP 或 Unix Socket？

**参考答案：** 当前客户端是本地 Python 终端，用 loopback TCP 便于跨平台并保留长连接双向通信；自定义分帧与错误处理仍由项目承担。WebSocket 在浏览器与跨代理场景更自然，HTTP 命令加 SSE 也是可选方案。Unix Socket 适合部分本地部署，但 Windows、权限和路径语义需要额外评估。选型依据场景，不宣称裸 TCP 必然简单或更快。

**追问：** 浏览器能直接连接裸 TCP 吗？切成 Web 前端要改哪层？

**证据：** transport/socket_client.py、socket_server.py。协议路由与业务应尽量独立。

### P09｜P0：JSON-RPC、JSON、NDJSON、TCP 各解决什么？

**参考答案：** JSON 是数据表示；JSON-RPC 定义调用方法、参数、ID、结果/错误的消息约定；NDJSON 在本项目用换行划分 JSON 消息边界；TCP 提供可靠有序字节流。它们处在不同层。标准 JSON-RPC 无 id 的请求是通知、不应回复；本项目 kind=event 是自定义推送封装，不能冒称完整标准通知实现。

**追问：** JSON-RPC 标准允许什么参数形式，本项目限制了什么？

**资料：** [JSON-RPC 2.0](https://www.jsonrpc.org/specification)。本项目主要按对象参数与注册 handler 使用，未实现所有 batch 等能力。

### P10｜P0：TCP 粘包、半包怎么处理？JSON 字符串里有换行怎么办？

**参考答案：** 一次 write 不对应对端一次 read。项目序列化成单行 JSON 后追加真正的换行，以 readline 累积并切帧；字符串内部换行由 JSON 编码转义，不能自行拼接未转义的多行 JSON。需要处理帧长度、缺失分隔符、EOF、解析失败。64 MiB 上限也不等于合理内存预算。

**追问：** 能否用长度前缀？巨大帧与恶意客户端如何限流？

**证据：** 两个 Socket 文件的 write/readline。TCP 字节流事实参见 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

### P11｜P0：同一连接既有响应又有事件，如何匹配？

**参考答案：** SocketClient 按请求 id 建 pending Future。唯一接收循环识别响应后完成对应 Future，识别事件封装则调用本地回调。响应可能乱序，但按 id 关联。断线要终结等待对象，超时和晚到响应要清理。tool_use_id、run_id、session_id 与 RPC id 分别服务不同业务关联。

**追问：** 两个协程同时 reader.readline 会怎样？没有超时会积累什么？

**证据：** transport/socket_client.py。不能让每个 RPC 自己和统一接收循环抢读。

### P12｜P0：S5 为什么把服务器 await handler 改成 create_task？

**参考答案：** 同连接的 session.send_message 等待整轮，整轮又可能等待 permission.respond。若读循环必须等前一个 handler 结束，就读不到审批决定，形成循环等待。独立 Task 让读循环继续。它只增加并发处理，不自动解决任务登记、上限、异常回收和关闭取消。

**追问：** 事件循环没阻塞，为什么业务还能死等？能否允许任意数量 Task？

**证据：** socket_server.py。这里不是“await 会冻结整个进程”，而是当前连接的控制流程没继续读。

### P13｜P0：writer.drain 能保证对方收到并处理了吗？

**参考答案：** 不能。write 把数据交给缓冲，drain 参与流量控制，在需要时等待缓冲下降；不代表远端业务执行或落盘。应用完成需要响应或业务确认。慢客户端的 drain 还可能拖慢广播，应定义每客户端队列、上限、超时与丢弃/断连策略。

**追问：** close、wait_closed、flush、fsync 分别在哪一层？

**资料：** [Python Streams](https://docs.python.org/3.12/library/asyncio-stream.html)。证据：广播器和 _send。

### P14｜P0：TUI 的 while True 会不会疯狂创建连接？断线能续聊吗？

**参考答案：** 外层循环负责重连，正常连接期间 await 接收任务，不会进入下一轮；失败或断线后清理并等待再连。内层循环负责同一连接的连续消息。当前重连重新创建 session，磁盘有旧历史也不等于自动恢复旧会话，更不保证旧运行已经取消。

**追问：** 重连后如何定位最后收到的事件？怎样防止重复展示？

**证据：** tui/app.py 的 _socket_loop。恢复方案需 session 关联、事件序号和运行状态，而不只重新 connect。

### P15｜P0：EventBus 是消息队列吗？订阅是并发处理吗？

**参考答案：** 当前是进程内订阅者列表，publish 按顺序 await 每个 handler，不是持久化 MQ，也不是默认并发扇出。慢订阅者会增加发布耗时，异常可能影响后续处理。若解耦，应明确有界队列、顺序、背压、错误隔离和关闭排空；不能只改成 gather 就称可靠消息系统。

**追问：** 多个 publish 协程之间还有全局严格顺序吗？为什么？

**证据：** [events/bus.py](../../src/kama_claude/core/events/bus.py)。多个发布者可能在 await 处交错，单次顺序不等于全局顺序。

### P16｜P1：事件写文件是否已经按 run 隔离？有没有泄漏？

**参考答案：** 当前 EventWriter 直接订阅共享总线，handle 没按 run 过滤；同时运行时可能写到不属于该 run 的事件。退出只关闭文件，没有从总线移除绑定方法，长期运行会积累订阅者。关闭后的 handler 会早退，但对象引用和分发开销仍在。要设计订阅 token、unsubscribe 与明确父子事件归属。

**追问：** 子 bus 桥接父 bus，哪些事件应写父文件？怎样测试不串流？

**证据：** [events/writer.py](../../src/kama_claude/core/events/writer.py)。这属于已定位问题，不是已修复优化。

### P17｜P0：events、Trace、普通日志与 thread 分别记录什么？

**参考答案：** thread 是模型上下文历史；events 是运行生命周期与工具进度；Trace 记录协议、模型请求响应等调用观察；普通日志用于程序排错。它们的覆盖与持久化保证不同。TraceWriter 用队列但后台仍同步写文件、队列无界，不能称完全非阻塞；文件编码、隐私脱敏和异常后队列排空也要检查。

**追问：** 为什么 UI 正常但结果没保存？如何按 session/run/tool id 关联排查？

**证据：** trace/writer.py、trace/provider.py、logging_setup.py、session/store.py。

## 三、模型适配、工具与审批

### P18｜P0：OpenAI 和 Anthropic 消息适配改了什么？

**参考答案：** 本项目内部使用 assistant 的 tool_use 与 user 的 tool_result。OpenAI 适配把调用转成 assistant.tool_calls，结果转成 role=tool 并关联 tool_call_id，还要合并流式参数片段、映射结束原因和用量。system 要包含动态记忆。thinking 块与签名是特定格式，不能原样发送给任意后端。当前转换边界以类代码为准，不代表所有 API 版本均兼容。

**追问：** 一次返回多个调用怎么配对？参数 JSON 流到一半断开怎么办？

**证据：** [llm/provider.py](../../src/kama_claude/core/llm/provider.py)。只描述已做转换，不把所有后端重试和截断行为说成一致。

### P19｜P0：有 input_schema，为什么还需要 params_model？

**参考答案：** schema 告诉模型怎样构造参数，不保证实际数据正确。后端 Pydantic 模型做运行时验证，再进入权限与执行。params_model: ClassVar[type[BaseModel] | None] 保存可选模型类，注解本身不执行校验。当前 MCP 包装器为 None，没有自动获得完整 JSON Schema 校验；白名单也不能代替参数验证。

**追问：** model_validate 返回值是否真正传给工具？默认转换和严格校验有何区别？

**证据：** tools/base.py、invocation.py、builtin/bash.py。目前入口校验后仍传原字典，各工具可能再次解析。

### P20｜P0：如何处理工具失败与模型接口失败？

**参考答案：** 工具错误转 ToolResult 回给模型，执行循环只对指定类型有限重试；schema、拒绝、超时不会同样重试，未知工具在重试前早退。模型流重试是 Provider 另一层逻辑，不等于工具重试。对副作用操作、部分成功和客户端超时，要先定义幂等与执行状态，不能统一重跑。

**追问：** 前台子 Agent 返回 runtime_error，重试是否会重复创建子任务？

**证据：** invocation.py、llm/provider.py、subagent/tool.py。当前工具最多首次加两次重试，2/4 秒退避；不要概括为所有失败都三次。

### P21｜P0：人工审批怎样让执行暂停再继续？

**参考答案：** PermissionManager 创建 Future，用 tool_use_id 登记后发 permission.requested；协程 await Future。TUI 的 Decided 是本地消息，App 再发 permission.respond RPC；Core 找到 Future 并 set_result，原协程恢复。审批超时、重复或晚到响应、断线和取消都要清理。当前 cancel_session 已定义但没有完整接入断线流程。

**追问：** 为什么先登记再发事件？RPC Future 与审批 Future 是同一个吗？

**证据：** permissions/manager.py、tui/app.py。Future 的桥接作用参见 [Python Futures](https://docs.python.org/3.12/library/asyncio-future.html)。

### P22｜P0：始终允许的作用范围与策略优先级是什么？

**参考答案：** 当前会话缓存按 session+工具名，持久化缓存按工具名。always 类决定同时更新两者并尝试落盘，所以跨会话也可能生效。bash 的显式拒绝正则优先，疑似越出工作目录强制 ASK，然后才看缓存、允许模式和默认。evaluate 静态函数不是运行主链，check_and_wait 有自己的完整判断，存在重复维护风险。

**追问：** 始终允许一次写文件，是允许哪个文件还是所有同名工具？写策略失败怎样反馈？

**证据：** permissions/policy.py、manager.py、storage.py。当前是粗粒度授权，文件保存失败不会回滚内存决定。

### P23｜P0：你怎样限制危险操作？这是不是沙箱？

**参考答案：** 当前有工具范围、参数模型、部分路径检查和人工审批，但不是完整沙箱。只排除路径里的 .. 不能阻止绝对路径、符号链接和 shell 绕过，Unix 风格正则也不能覆盖 Windows。改进要明确工作目录边界、解析真实路径、限制服务权限与凭据、隔离进程，并防止文件内容提示注入让模型扩大授权。

**追问：** 本地端口只监听 loopback 就安全了吗？恶意本地进程能提交审批吗？

**证据：** builtin/read_file.py、write_file.py、permissions/。当前没有完整客户端身份与多租户授权，应据实说明。

### P24｜P0：thread、notes、全局/项目 context 是长期记忆吗？与 RAG 有何不同？

**参考答案：** thread 保存详细对话；notes 是会话内主动笔记；全局/项目 Markdown 每轮读取并注入 system。它们是文件驱动的上下文构造，没有向量检索、召回或重排，不能称已实现 RAG。长期记忆还要解决提取、更新、冲突、权限、检索和遗忘，而不只是把内容持续拼进去。

**追问：** 哪些文件自动创建？note_save 会更新当前 run 的 notes 快照吗？

**证据：** memory/loader.py、context.py、runner.py、note_save.py。项目路径基于 Core cwd，笔记主要在下一 run 重新加载。

## 四、会话、持久化与上下文治理

### P25｜P0：既然 thread 已落盘，Core 重启为什么不能直接续聊？

**参考答案：** 文件持久化不等于恢复流程。SessionManager 启动时内存索引为空，_get_session 主要查内存；TUI 连接后新建 session。恢复需要加载元信息、修正中断状态、关联客户端、重建可恢复任务与事件游标。活动协程不能只靠反序列化历史恢复。

**追问：** 上次写文件已经执行，但模型结果没保存，重启后还要执行吗？

**证据：** session/manager.py、store.py、tui/app.py。方案必须区分业务副作用、模型历史和执行检查点。

### P26｜P0：为什么保存历史要记录 prefill_len？

**参考答案：** 用户输入先由 Manager 写入，Runner 又加载已有历史。如果结束时把整个 messages 追加，会重复旧内容。记录开始长度，只追加后缀能避免重复，但前提是旧历史一直保持为列表前缀。它不是通用增量日志算法，压缩、编辑、修复历史后必须重新定义保存策略。

**追问：** 为什么不能每轮清空后全量写？如何处理失败和并发？

**证据：** runner.py。可以从消息序号/ID、版本化快照、追加日志中选择，不应把下标当稳定身份。

### P27｜P0：_trim_orphan_tool_use 有什么问题？

**参考答案：** 它扫描调用 ID 与结果 ID，返回最后一个配对完整的位置之前的消息。它只修剪读取结果，未修复磁盘。如果旧未配对调用一直存在，后来追加的新问题仍可能被裁掉。应在新输入前恢复有效历史，或补充明确的中断结果；保留原始记录，验证后续两轮都能读取。

**追问：** 已执行但结果丢失的工具能否直接重跑？已完整的其他工具结果是否也被裁？

**证据：** session/store.py。当前是截断整个不完整尾部，不是精细移除单个 block。

### P28｜P0：超长工具结果在哪里截断？参数真的生效了吗？

**参考答案：** 当前在 SessionStore.read_messages 处理已保存历史，超过默认 8000 字符保留前 4000，加省略说明，不直接改写磁盘。本轮新结果不会立刻走这次读取。config 里的 limit/keep 虽被解析，当前入口仍用函数默认值，尚未接通。字符数不是 token 数，保留前缀也可能丢关键尾部。

**追问：** 错误信息在末尾怎么办？如何让模型按需取回完整数据？

**证据：** compact/budget.py、session/store.py、config.py。改进可用摘要、首尾保留、结果引用与分页，而不是一律扩大上限。

### P29｜P0：对话摘要要保留什么，如何验证没忘需求？

**参考答案：** 保留目标、已做事项、约束、文件状态、剩余任务和关键数据。当前通过提示要求六类内容，仅检查调用成功和摘要非空，没有严格收益或保真验证。可构造带唯一约束的多轮样本，比较压缩前后任务完成、约束遵守、摘要长度与额外成本；关键字段可用结构化状态保护。

**追问：** 摘要更长怎么办？摘要服务本身超限怎么办？

**证据：** compact/compactor.py。不要把“发了总结提示”说成“保证不会遗忘”。

### P30｜P0：自动与手动压缩怎样触发，保存到哪里？

**参考答案：** 自动在主 Loop 工具结果追加后、本轮继续且 usage 达阈值时调用 compact，替换内存 messages、写 summary 文件并发事件；默认阈值 0 关闭。手动 /compact 调 session.compact，在会话锁下读历史、调用共享摘要方法、备份并覆盖 thread，再返回统计。手动没有走 compact 包装方法，两条路径事件与保存不同。

**追问：** 为什么等工具结果？summary 文件会在下轮自动读取吗？

**证据：** loop.py、compactor.py、session/manager.py。当前不会自动用 summary 文件替代 thread。

### P31｜P0：自动压缩后为什么可能漏存消息？你准备怎样修？

**参考答案：** 开始时 prefill_len=10，压缩后列表只有两条，再生成回答变三条，结束仍取 messages[10:] 就为空。当前 run 后续请求得到缩短，但新输出可能漏存，下轮还读旧历史。修复可显式标记历史重写：发生压缩时原子保存当前快照，未压缩时增量追加；只清零再 append 会变成旧历史加摘要，并未缩短。

**追问：** 取消时快照如何保存？两次压缩怎么办？备份失败、工具未配对怎么办？

**证据：** runner.py 与 Compactor.compact。当前是已定位、尚未完成修复的问题；验收必须包括压缩后继续两个 run。

### P32｜P1：context_pct 为什么不是准确 token 预算？

**参考答案：** 它来自上一模型请求的用量与代码窗口映射，未知模型有默认值，之后工具结果还会增长。缓存用量口径、system、工具 schema、输出预留也需统一。因此应在每次发送前预算并预留输出，必要时调用后端计数接口或保守估算。实际窗口与价格应按使用版本核对，不能背一个值适用于所有模型。

**追问：** 工具列表太多怎样减少提示成本？如何避免摘要调用也超限？

**证据：** llm/provider.py、UsageStats、AgentLoop 的阈值条件。

## 五、Skills、子 Agent 与 MCP 深挖

### P33｜P0：/review 参数最后真的进入模型了吗？

**参考答案：** SkillLoader 会替换模板里的 $ARGUMENTS，Manager 把渲染结果给 goal，但也先保存原始斜杠输入。Context 优先采用非空历史，override 仍是原始模板，因此模板参数与实际消息没有完全对齐。应明确将渲染结果放 user 还是 system，保留审计用原始输入而不重复发送。测试应断言 Provider 的实际入参。

**追问：** 只输入 / 会怎样？未知 Skill、项目覆盖、解析失败怎样反馈？

**证据：** skills/loader.py、session/manager.py、context.py。仅测试 render_prompt 字符串替换不足以验证端到端。

### P34｜P0：Skill 白名单、角色白名单与权限有什么区别？

**参考答案：** Skill 控制主运行的提示和工具注册，Profile 控制子任务的角色和子工具表；权限在一次调用时再判断是否放行。当前空工具列表被当作无限制，不等于全部禁止。角色 model 字段仅解析，未自动切换 Provider。审查角色允许 bash，也不能靠自然语言保证所有命令只读。

**追问：** 白名单只允许 spawn_agent，能否间接扩大能力？

**证据：** Runner._build_registry、SpawnAgentTool._build_child_registry。需要明确父子能力是否可扩张与如何继承。

### P35｜P0：子 Agent 具体创建了什么，隔离了什么？

**参考答案：** 创建 child_run_id、新 Context、总线、工具表和 AgentLoop，前台 await 或后台 Task 执行。复用 Provider 与权限管理器，仍在同一 Core 进程，未自动继承父历史、三层记忆、全部 MCP 工具和压缩能力。prompt 必须带足背景；共享文件系统与模型额度仍可能竞争。

**追问：** 是同一个模型实例吗？新的 Runner 还是只创建 Loop？

**证据：** subagent/tool.py。上下文独立、协程并发、进程隔离是三个不同概念。

### P36｜P0：前台和后台子任务怎样把结果交给父模型？

**参考答案：** 前台运行结束把最终文本包装为 spawn_agent 的 ToolResult；后台先登记 Task/Context 返回 ID，父模型再调用 agent_result 查询。完成事件给界面，不会自动成为父 messages。父模型若不查询，就不一定得到后台结果。前台整个工具调用还受外层超时影响，不能只依赖子 max_steps。

**追问：** 父任务结束后后台还在运行怎么办？失败重试会重复派生吗？

**证据：** subagent/tool.py、tools/invocation.py。

### P37｜P0：为什么新一轮 agent_result 查不到旧任务？

**参考答案：** BackgroundTaskRegistry 是 Runner 的实例属性，每轮新 Runner 意味着新表。注释写共享不等于 Core 级共享，也没有磁盘恢复。可把注册表提升到会话/Core 服务并注入，加入任务归属、取消、过期与持久状态。后台协程正常结束还需检查 Context.status，不能只看 task.exception 为 None。

**追问：** ID 被别人猜到可以查询吗？已完成记录何时清理？

**证据：** subagent/registry.py、AgentRunner.__init__、AgentResultTool.invoke。这是适合作为个人改进的真实缺口。

### P38｜P1：多个子 Agent 修改同一个文件怎样避免覆盖？

**参考答案：** 当前没有完整文件隔离与提交协议。可以给任务分配独立 worktree/临时目录，返回补丁后由协调者校验合并；或以资源锁、文件版本和冲突检测控制写入。不能只让模型“不要冲突”。还需明确命令执行、MCP 远程写入等跨边界副作用，记录谁产生了什么变更。

**追问：** 两个补丁都通过测试但语义冲突怎么办？审查者能否看到未提交改动？

**证据：** 当前子任务共享 cwd。以上是设计候选，不是已有分布式锁或 worktree 调度功能。

### P39｜P1：多 Agent 为什么可能更慢、更贵？怎样控制不收敛？

**参考答案：** 每个子任务都有提示与调用开销，规划审查可能重复探索；并发不缩短所有串行依赖。设父子总 token/费用/时间预算、最大任务数和深度、重复状态检测，以及失败升级规则。只有对可独立子任务做评测后才能说多 Agent 更有效。当前嵌套深度有限，不代表整体并发和成本已受控。

**追问：** reviewer 一直不通过怎么办？同一 Provider 是否会被限流？

**答法：** 给验收条件与重试上限，保留失败证据并请求人工处理，不无限循环修补。

### P40｜P0：一次 MCP 工具从发现到调用的链路是什么？

**参考答案：** Core 创建管理器 → 连接服务 → initialize 请求、initialized 通知 → tools/list 读取定义 → McpTool 用服务名前缀适配 BaseTool → Runner 按白名单注册 → 模型返回工具调用 → invoke_tool 审批 → client.tools/call 用原始工具名转发 → 结果转 ToolResult → 回填主模型。server.py 是连接管理器，不是实现外部服务端。

**追问：** 一个 client 对几个工具？模型还是 Core 发网络请求？

**证据：** [mcp/](../../src/kama_claude/core/mcp/)。生命周期概念参见 [MCP 生命周期，2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)。

### P41｜P0：你支持的 MCP TCP 是标准 HTTP 传输吗？

**参考答案：** 本项目实现 stdio 与自定义的 TCP 换行 JSON-RPC 流，未实现 Streamable HTTP。以官方 2025-06-18 规范为例，列出的标准传输是 stdio 和 Streamable HTTP，并允许自定义；仓库初始化固定旧版本字符串，不能直接声称兼容所有新服务。版本、传输、能力协商需逐项核对。

**追问：** 为什么把 HTTP URL 填进 host 不能用？连接成功等于协议兼容吗？

**资料：** [指定版本的官方传输说明](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)。这里明确版本，不把某份历史规范说成永远最新。

### P42｜P0：McpClient 为什么加锁，与 SocketClient 有什么区别？

**参考答案：** MCP _call 由发起者直接写请求并循环读取响应，锁覆盖发送到接收，所以同连接串行。SocketClient 则是统一接收循环按 id 完成多个 Future。要扩展 MCP 并发，需要 ID 分发、超时清理与通知/服务端请求处理，不能简单删锁让多个协程抢读。

**追问：** 不匹配 ID 的响应去哪了？通知不断到来，总调用超时还能保证吗？

**证据：** mcp/client.py。当前 30 秒约束是单次 readline 等待，不是严格请求总截止时间。

### P43｜P0：MCP 返回 result 就一定成功吗？

**参考答案：** 不一定。顶层 JSON-RPC error 与工具结果里的 isError 是两层错误。当前 _call 处理前者，call_tool 未检查后者且只拼 text，可能误判工具失败，其他内容类型也未完整传递。MCP params_model=None，展示 schema 也不等于本地已经验证参数。

**追问：** read timeout、无权限、工具参数错误应不应该同类重试？

**资料与证据：** [MCP 工具与错误机制，2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)、mcp/tool.py、client.py。

### P44｜P1：MCP stdio 为什么要读取 stderr？连接失败怎样清理？

**参考答案：** stdout 用于协议，stderr 持续消费日志，避免缓冲区满阻塞子进程。退出取消日志读取，终止并等待服务，必要时 kill。当前初始化或工具发现失败的客户端可能尚未登记，stop_all 无法覆盖；要用明确的资源所有权与 finally 清理。stdout 非 JSON 被容忍也不等于日志可以随意污染协议。

**追问：** kill 后为何还要 wait？TCP 超时重连后工具列表是否仍有效？

**证据：** McpServerManager.start_all、McpClient.close。子进程管道行为可核对 [Python subprocess](https://docs.python.org/3.12/library/asyncio-subprocess.html)。

## 六、工程验证与个人改进

### P45｜P0：Windows 适配具体改了什么，为什么 Ctrl+C 原来有问题？

**参考答案：** Windows 的事件循环信号支持与 Unix 不同，不能无条件注册同样的 add_signal_handler。当前区分平台，依赖 asyncio.run 对 Ctrl+C 的主任务取消，并把服务、MCP、Trace 收尾放 finally。同步入口处理 KeyboardInterrupt。还要核对默认编码、shell 命令、后台 PID 管理，不能把前台退出适配说成全部跨平台功能都完成。

**追问：** 为什么关闭 TUI 不等于停止 Core？GBK、UTF-8、ensure_ascii 是什么关系？

**证据：** CoreApp.run、tests/unit/test_core_app.py；运行版本固定 Python 3.12。

### P46｜P0：你怎么证明它能工作？270 项测试说明什么？

**参考答案：** 分层验证纯逻辑、假 Provider 的执行链、真实子进程 IPC 和手工 TUI。项目此前一次合并检查记录了 270 项单元/权限回归通过、类型检查通过及无密钥启动的真实 IPC；不是所有集成场景，更不是模型业务成功率。本次资料整理未重新宣称跑完它们。需要保留命令、环境与日期，并单独测真实模型和故障。

**追问：** Mock 掩盖了什么？为什么测试都过，自动压缩保存还会错？

**证据：** test_stage_provider_compat.py、test_core_app.py、test_spawn_agent_tool.py。测试覆盖断言，不覆盖所有设计性质。

### P47｜P0：如果写“性能提升、成本降低”，数据怎么测？

**参考答案：** 当前没有足够基准数据就不写提升比例。设计固定任务集与验收、模型版本、提示、工具环境、重复次数和并发；记录完成率、约束违规、TTFT、整轮耗时、工具/摘要次数、token 用量及按实际计价计算成本。报告样本数与分位数，区分本地 IPC 压测和模型端到端评测，不把 ping QPS 当 Agent 吞吐。

**追问：** 超时任务计不计分母？缓存与随机性怎样控制？p95 如何计算？

**答到这里再加分：** 保留失败样本与 raw 记录，让他人能重复得到同口径结果。

### P48｜P0：如果只给你一周，你会做哪个 S8 改进？

**参考答案：** 优先选一个真实、可复现且能验收的缺陷，例如自动压缩历史重写，或会话级后台任务注册。先给失败用例，定义消息/任务状态与保存边界，完成最小实现，再覆盖取消、重启或后续多轮。不同时堆 RAG、Redis、集群。以修改前后同一组回归和任务表现证明价值，没有数据就不报百分比。

**追问：** 为什么是这个问题？替代方案是什么？最小验收与回滚是什么？

**证据：** 见 P31、P37。模拟文档给出了改进验收模板。

## 七、相关八股：必须能落回项目

### B01｜P0：协程、Task、Future 与 await 是什么关系？

**参考答案：** 调用 async 函数得到协程对象，不表示已完成执行。Task 调度并驱动协程；Future 表示稍后产生的结果，适合把回调结果桥接给 await。await 在需要等待时让出执行权，但不是每个 await 都必然发生切换。项目用 Task 跑后台子任务，用 Future 等 RPC 和审批。

**追问：** create_task 后不保存引用可能有什么问题？Task.done 能否证明业务成功？

**资料：** [Future](https://docs.python.org/3.12/library/asyncio-future.html)、[协程与任务](https://docs.python.org/3.12/library/asyncio-task.html)。

### B02｜P0：async 就不会阻塞吗？CPU 密集任务怎么办？

**参考答案：** 同步文件 I/O、time.sleep、长 CPU 循环仍能占住事件循环。可对阻塞 I/O 用线程执行器，对纯 Python CPU 重活考虑进程等方案。按本项目 CPython 3.12 的常规 GIL 环境谈，多线程不等于 Python 字节码多核并行；释放 GIL 的扩展另论，不能将该结论套到所有 Python 版本/构建。

**追问：** Trace 有异步队列，为什么仍可能阻塞？

**资料：** [Python GIL FAQ](https://docs.python.org/3.12/faq/library.html#cant-we-get-rid-of-the-global-interpreter-lock)、[事件循环](https://docs.python.org/3.12/library/asyncio-eventloop.html)。

### B03｜P0：单线程 asyncio 为什么还需要锁？Semaphore 有什么用？

**参考答案：** 逻辑操作跨 await 时会与其他协程交错，需要锁保护会话运行或资源更新。Semaphore 可限制同时在途模型请求或子任务数。asyncio.Lock 面向同事件循环协程，不是跨线程/进程锁。当前 locked 检查到 acquire 没有其他显式等待，不应不看执行语义就断言必有竞态；通用正确性仍基于完整临界区设计。

**追问：** 持锁调用模型的优缺点？每会话锁能保护多个会话共同写文件吗？

**资料：** [asyncio 同步原语](https://docs.python.org/3.12/library/asyncio-sync.html)。答案是不能自动保护跨会话资源。

### B04｜P0：Task.cancel 与 wait_for 超时会真的停掉操作吗？

**参考答案：** 取消是向协程协作式投递 CancelledError，不是强杀进程。wait_for 会尝试取消等待操作并等待清理，总耗时可能超过名义超时。清理写 finally，通常完成后传播取消；CancelledError 属于 BaseException。远端模型、线程或外部副作用可能已经继续发生，客户端取消不证明远端取消或不收费。

**追问：** 审批 Future 取消后 pending 清了吗？子进程是否仍存在？

**资料：** [取消与超时](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)、[异常层级](https://docs.python.org/3.12/library/asyncio-exceptions.html)。

### B05｜P1：gather 与 TaskGroup 有什么区别？

**参考答案：** gather 便于汇总结果，默认一个子任务出错不等于自动取消所有兄弟任务；取消 gather 自身又是另一种情况。TaskGroup 将任务生命周期限制在作用域，普通子异常会取消其余任务并等待收尾，之后组合异常。后台长任务应由更高层所有者管理，不能放在短 run 的结构化作用域里却期待无条件脱离生命周期。

**追问：** 父 run 退出时应等待、取消还是移交子任务？

**资料：** [Python TaskGroup 与 gather](https://docs.python.org/3.12/library/asyncio-task.html#task-groups)。

### B06｜P0：close、wait_closed、drain、flush、fsync 各保证什么？

**参考答案：** 网络 drain 管缓冲背压，close 请求关闭，wait_closed 等本地关闭过程；都不等于业务已完成。文件 flush 将用户态缓冲交给底层，fsync 请求持久化，具体故障保证依赖系统与存储。EventWriter 每条 flush，不代表断电事务安全。不要把客户端与服务端各自 close 误认为关闭同一个 Python writer 两次。

**追问：** 消息发送成功、TCP 确认、RPC 成功、业务提交之间有什么区别？

**资料：** [Streams](https://docs.python.org/3.12/library/asyncio-stream.html)、[os 文件操作](https://docs.python.org/3.12/library/os.html)。

### B07｜P0：exec 与 shell 子进程有什么区别，怎样避免管道死锁？

**参考答案：** create_subprocess_exec 按可执行文件与参数启动，shell 会解释命令字符串、重定向和变量，需额外防注入与跨平台差异。stdout/stderr 为 PIPE 时要持续消费；只 wait 而不读可能因管道写满卡住。超时要定义 terminate/kill 并 await wait，必要时处理子孙进程。MCP stderr 消费就是具体应用。

**追问：** Windows shell 与 Bash 是否等价？杀父进程能否保证杀掉所有子进程？

**资料：** [asyncio 子进程](https://docs.python.org/3.12/library/asyncio-subprocess.html)。

### B08｜P0：ClassVar[type[BaseModel] | None] 怎样解释？

**参考答案：** ClassVar 声明类级属性，type[BaseModel] 表示模型类而非实例，| None 表示可以不提供，=None 是默认值。子类写 params_model=BashParams，执行时调用模型类的 model_validate。Python 类型标注通常不自动执行运行时验证，和框架根据名称找处理方法也是不同机制。

**追问：** 为什么不是 BashParams()？不同工具如何提供不同参数模型？

**证据：** BaseTool、BashTool。不要把 ClassVar 说成运行时禁止实例赋值的强制保护。

### B09｜P1：dict(m) 是深拷贝吗？嵌套工具块会不会共享？

**参考答案：** 不是，它只复制外层字典，内部列表和字典可能仍是同一对象。若随后原地修改嵌套 tool_result，可能影响其他引用。选择不可变数据、按需复制或 deepcopy，考虑性能和语义；不能因为列表是新建就认为全部历史彻底隔离。

**追问：** Context 初始化与 truncate_tool_results 哪些对象被复制？

**资料：** [浅拷贝与深拷贝](https://docs.python.org/3.12/library/copy.html)。

### B10｜P1：字典为什么平均 O(1)？缓存为什么还需要淘汰？

**参考答案：** 哈希定位与较低装载下查询平均接近 O(1)，冲突、扩容和极端输入使单次或最坏行为不同，不能说永远 O(1)。缓存还要控制容量、过期与归属。后台注册表无限保留已完成 Context 可能占用内存；LRU 可用哈希表加双向链表，查找与移动平均 O(1)。

**追问：** run_id 结果多久失效？过期与正在运行状态如何区分？

**落点：** BackgroundTaskRegistry、pending、长期策略缓存；具体容量策略当前未完整实现。

### B11｜P0：进程、线程、协程共享哪些资源？

**参考答案：** 进程有独立地址空间等资源；线程共享进程地址空间与很多资源，各有执行栈；协程是用户态可挂起的执行单元，通常由线程中的事件循环调度。项目 Core/TUI 是不同进程，子 Agent 通常是同 Core 的协程任务，stdio MCP 服务是另一个进程。不能用一个“异步”词概括三者。

**追问：** 子 Agent 能否利用多核？线程间 Future 能直接 set_result 吗？

**答法：** 明确同步原语与事件循环线程边界，跨线程调度需要相应线程安全入口。

### B12｜P0：死锁四个必要条件是什么，项目中怎样对应？

**参考答案：** 互斥、占有并等待、不可剥夺、循环等待。项目审批示例更直接体现控制流循环等待：发送任务的 handler 不结束，读循环不读审批，而任务又依赖审批。它不一定是两个 mutex 的经典示例。破除等待依赖、拆分接收与执行，同时管理任务生命周期。

**追问：** 没有锁就不会死锁吗？异步流程怎样画等待图？

**证据：** P12。背四个条件后必须解释本项目是哪条等待链。

### B13｜P1：TCP 为什么需要三次握手，关闭为什么可能分成四次？

**参考答案：** 建连需要双方同步各自初始序列号并确认对端的信息，第三步完成对服务端 SYN 的确认，不能仅用“确认能收发”解释全部。两个方向可独立关闭，FIN 与其确认可能分开发送，也可能合并，所以四次是常见序列，不是每次抓包都恰好四个包。

**追问：** 历史重复连接请求会带来什么问题？半关闭是什么意思？

**资料：** [TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

### B14｜P0：TCP 可靠传输能否保证工具恰好执行一次？

**参考答案：** 不能。可靠有序字节流不提供应用事务语义。服务执行成功后响应丢失，客户端重连重试可能再次执行；RPC id 通常只用于关联，并非服务端持久幂等键。要定义业务操作 ID、重复检测与结果记录，并分析它和外部副作用能否原子提交。不能轻率承诺端到端 exactly-once。

**追问：** 写文件、扣费 API、模型请求能否使用同一种去重方案？

**落点：** 工具重试、前台 spawn_agent 重试、MCP 重试。回答应讨论不确定完成状态。

### B15｜P1：TIME_WAIT、CLOSE_WAIT、RST 分别提示什么？

**参考答案：** TIME_WAIT 与终止连接后处理最后确认、旧报文生命周期有关；CLOSE_WAIT 说明已收到对端关闭但本地还未完成关闭，过多时可检查资源回收；RST 是重置而非正常有序关闭。谁进入哪个状态依赖具体时序，不能简单映射“客户端总是 TIME_WAIT”。

**追问：** 为什么本地端口占用可能让 Core 启动失败？频繁重连怎样观察？

**资料：** TCP 状态定义见 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。结合 socket 与进程状态定位。

### B16｜P1：浏览器前端选 WebSocket 还是 SSE？

**参考答案：** WebSocket 支持双向消息，SSE 的 EventSource 适合服务端到客户端事件流，用户命令可另走 HTTP。选择看双向交互、重连、代理、认证与生态，而不是只看“流式”两个字。标准 WebSocket 有帧，项目 NDJSON 自己分帧；SSE 的事件格式也不是任意 JSON 加换行。项目当前并未采用两者。

**追问：** SSE 重连游标是否自动恢复业务状态？为什么浏览器不能直接复用裸 TCP？

**资料：** [WebSocket RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)、[WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

### B17｜P0：重试、退避、幂等与熔断是什么关系？

**参考答案：** 重试应对部分暂态失败，退避和抖动减少同步冲击，幂等控制重复副作用，熔断在持续故障时停止无效调用并探测恢复。当前项目有限重试不等于已实现完整熔断。还需总时限、重试预算和分类；参数错误、授权拒绝、确定性业务失败不应盲目重试。

**追问：** 429、连接断开、500、执行后超时如何分别处理？

**答法：** 先判断可恢复性和结果是否确定，再考虑次数；不要只背指数公式。

### B18｜P0：JSONL 能代替数据库事务吗？怎样安全替换历史？

**参考答案：** 不能自动提供多文件原子更新。meta、thread、notes 与工具副作用可能不一致。安全替换可使用同文件系统临时文件、写入校验与必要同步、原子替换，并定义备份与恢复；重命名的原子性不等于所有崩溃持久性保证。并发写、磁盘满、部分 JSON 行和跨平台覆盖行为都要测试。

**追问：** write_compacted 先 rename 后写，新文件写失败怎样恢复？

**资料：** [Python os.replace/fsync](https://docs.python.org/3.12/library/os.html)、[SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)。当前项目没有因此获得事务保证。

### B19｜P1：有界队列、背压与顺序怎样设计？

**参考答案：** 队列满时要明确等待、丢弃、采样或断开，而不是无限增长。按会话/run 编号可检测重复与缺口，但不能凭一个 seq 自动实现恢复。慢客户端应有独立缓冲，关键业务事件与可合并 token 采用不同策略。关闭时先停止生产再排空，消费者失败也要使等待方能结束。

**追问：** Trace drain 任务崩了，queue.join 会不会一直等？

**落点：** 当前 Trace 无界队列、EventBus 顺序等待和 broadcaster 写流；这些不是已经完成的可靠性机制。

### B20｜P1：Token、Attention、KV Cache、Prompt Cache 有何区别？

**参考答案：** token 是模型分词单位；Attention 根据输入表征计算关联，基本形式为 softmax(QKᵀ/√d)V。KV Cache 在生成时复用历史键值，减少重复计算；API Prompt Cache 复用兼容的提示前缀处理，具体规则依厂商/版本。缓存不会自动缩短活动历史或成为业务长期记忆，命中需看实际 usage，不凭 cache_control 标记认定。

**追问：** 工具列表顺序变化为什么可能影响前缀缓存？缓存占用是否为零？

**资料：** [Transformer 原论文](https://arxiv.org/abs/1706.03762)、[Hugging Face KV Cache](https://huggingface.co/docs/transformers/en/cache_explanation)、[Claude Prompt Cache](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。不背当前价格。

### B21｜P2：如果增加 RAG，需要补哪些模块？

**参考答案：** 文档解析和切块、元数据与权限、索引、检索、可选重排、上下文构建、引用和评测。检索回答“从知识库取什么”，压缩回答“已有历史怎样变短”，两者可组合。要用召回与最终任务指标验证，不是接一个向量库就完成。本项目当前没有这些模块，notes 不是向量 RAG。

**追问：** 精确标识符与语义问题如何检索？文档更新、删除和权限怎么同步？

**资料：** [RAG 原论文](https://arxiv.org/abs/2005.11401)。混合检索、重排属于可选设计，不能伪装成项目已实现。

### B22｜P0：单元测试、集成测试与 Agent 评测有什么区别？

**参考答案：** 单元测试验证边界逻辑，假 Provider 集成验证接线与状态，真实 IPC 验证进程协议，真实模型任务评测验证效果。后者要有可核验产出、固定约束和失败分类。Mock 不覆盖模型格式漂移、真实限流和文本保真；人工观察也应结构化记录，不只截图“看起来成功”。

**追问：** 怎样构造自动压缩后漏存的最小失败用例？

**落点：** 保存旧历史，强制假模型触发压缩，再续聊并断言新消息可读；不能只测摘要文件存在。

### B23｜P2：如果换数据库，你会怎样建模？

**参考答案：** 可按 session、run、message、event、approval、background_task 分实体，明确 ID、顺序、状态与版本。用事务维护同库内部关联更新，用唯一键支持操作去重；外部模型或文件副作用不自动参与事务。SQLite 可适合本地持久化，是否换成远程数据库取决于并发、恢复和运维需求，不是工具越多越好。

**追问：** 如何恢复 running 状态？事务能否包住耗时模型调用？

**资料：** [SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)。项目没有实现此数据库方案。

### B24｜P1：你怎样避免异步测试不稳定？

**参考答案：** 用 Event/Future 明确同步就绪与完成，少用固定 sleep 猜时序；为所有等待设合理上限，finally 取消并 await 后台任务，隔离环境和文件目录。用 AsyncMock 区分“调用过”和“实际 await 过”，并验证状态、磁盘与事件结果。测试 Core 启动应轮询就绪且输出错误诊断，而不是只扩大所有超时。

**追问：** 随机端口先释放再绑定有竞争吗？取消后是否还有 pending task？

**落点：** tests/conftest.py、test_core_app.py、test_stage_provider_compat.py。已有 3 秒 fixture 时限是具体可复现边界。
