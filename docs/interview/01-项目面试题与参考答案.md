## 一、项目介绍与运行入口

### P01｜面试官：用一分钟介绍这个项目。

**标准回答：** 我做的是一个本地 AI Agent。用户在 TUI 输入目标，常驻 Core 管理会话，调用模型，由模型决定是否使用读写文件、执行命令等工具。程序完成参数校验、权限审批和实际执行，再把结果交回模型，循环到结束。前后端通过 TCP 通信，执行事件实时推送到界面。项目还包括对话历史、笔记、上下文压缩、Skill、子 Agent 和 MCP 工具接入。我的设计重点是让执行、交互、记录与扩展职责清晰；当前仍有历史压缩保存和后台任务管理等待完善的可靠性问题。

#### P01.1｜追问：它和一个聊天接口包装有什么区别？

**标准回答：** 聊天接口主要把输入发给模型再显示回复；我的项目会维护多步执行状态，接收模型提出的工具调用，执行真实操作并回填结果。比如读取项目后修改文件，需要多次模型调用、权限检查和工具执行。执行能力也带来副作用、超时、取消和历史一致性等额外问题。

#### P01.2｜追问：它能保证任务完成吗？

**标准回答：** 不能。当前 `success` 表示模型返回 `end_turn`，不是独立验收器证明目标完成。模型也可能给出错误结论。我会针对具体任务增加可验证的产物检查，例如测试是否通过、文件是否符合约束，并把过程状态与业务验收分开。

**代码依据：** [CoreApp](../../src/kama_claude/core/app.py)、[Loop](../../src/kama_claude/core/loop.py)。

### P02｜面试官：你怎样划分整个系统的职责？

**标准回答：** 我按交互、协议、业务执行和外部能力分层。TUI 负责展示和收集输入；Socket 层负责传输和请求分发；CoreApp 组织共享服务；SessionManager 管会话；Runner 组装一次运行；Loop 驱动模型与工具；Provider 适配模型接口；Registry 和 invoke_tool 管工具；EventBus 连接广播与记录。这样修改界面或模型适配时，可以沿清楚的接口边界定位影响。

#### P02.1｜追问：哪些组件是长期存在的，哪些每轮创建？

**标准回答：** CoreApp 中的总线、广播器、SessionManager、PermissionManager 和 MCP Manager 随 Core 存活。会话对象保存在 SessionManager 内存里。每条用户消息通过工厂创建新 Runner，再创建 Context、工具表、TaskManager 和 Loop。后台任务注册表目前也在 Runner 中，这是跨轮查询失败的原因。

#### P02.2｜追问：这些分层是不是已经完全解耦？

**标准回答：** 还没有。Context 采用偏 Anthropic 的消息块，Provider 要负责转换；Runner 同时负责组装与保存，也容易出现压缩与保存逻辑不一致。分层提供了改造入口，但接口边界是否合理仍需用具体故障验证，不能仅凭目录划分认定完全解耦。

**代码依据：** [app.py](../../src/kama_claude/core/app.py)、[runner.py](../../src/kama_claude/core/runner.py)。

### P03｜面试官：为什么把 TUI 和 Core 放在两个进程？

**标准回答：** 我希望界面生命周期与任务执行分开，CLI/TUI 共用同一业务入口，模型、工具和权限统一在 Core 管理。代价是增加连接、协议、状态归属和退出清理的复杂度。当前只是本地双进程系统，单个 Core 并不是分布式集群，进程分离也不会自动提供重启恢复。

#### P03.1｜追问：单进程能不能实现？

**标准回答：** 能。小工具用单进程会更直接，函数调用也减少 IPC 成本。我的选择主要服务于多客户端入口和职责边界。若没有常驻执行需求，单进程也是合理方案；不能宣称双进程在所有情况下都更优。

#### P03.2｜追问：关闭 TUI，任务一定会停止吗？

**标准回答：** 不一定。TCP 断开会使界面失去连接，但任务在 Core 内运行。当前没有完整的“连接关闭即取消所属任务”规则。两者生命周期需要显式关联；即便发出取消，外部命令或远端请求是否已产生副作用也要单独处理。

**代码依据：** [CoreApp](../../src/kama_claude/core/app.py)、[SocketServer](../../src/kama_claude/core/transport/socket_server.py)。

### P04｜面试官：我输入“读取文件并总结”，完整链路是什么？

**标准回答：** TUI 先连接、订阅事件并创建 Session。用户输入经 SocketClient 的 `session.send_message` 发到 SocketServer，再由 CoreApp 的 handler 转给 SessionManager。后者获得会话锁、保存用户消息，创建 Runner。Runner 读取历史和背景记忆，组装 Context、Provider、工具表与记录器，然后调用 Loop。Loop 请求模型，执行其工具调用并追加结果，直到结束。Runner 发布结束事件并保存本次新增消息，SessionManager 更新会话状态；事件沿广播器持续返回 TUI。

```text
控制流：TUI → SocketClient → SocketServer → CoreApp → SessionManager → Runner → Loop
执行流：Loop → Provider → 工具调用 → invoke_tool → ToolResult → Context → 下一步模型
反馈流：执行组件 → EventBus → IpcEventBroadcaster → TCP → TUI
```

#### P04.1｜追问：用户输入什么时候保存？

**标准回答：** SessionManager 在调用 Runner 之前把用户输入追加进 `thread.jsonl`。Runner 随后读取历史，因此历史已经包含本轮输入。模型与工具产生的新增消息在 Runner 的结束保存路径中追加。它不是每个模型 token 都实时写入完整对话文件。

#### P04.2｜追问：RPC 响应和任务进度谁先返回？

**标准回答：** `session.send_message` 等待本次 Run 完成后才响应，但事件会在中途推送。`agent.run` 则创建后台任务，先返回 Run ID，再通过事件观察完成。因此不能把“还没有收到最终 RPC 响应”理解成“Core 没有开始执行”。

**代码依据：** [SessionManager](../../src/kama_claude/core/session/manager.py)、[Runner](../../src/kama_claude/core/runner.py)、[TUI](../../src/kama_claude/tui/app.py)。

### P05｜面试官：Session、Run、Step、Task 分别是什么？

**标准回答：** Session 是连续会话；一条用户输入通常触发一个 Run；Run 内每调用一次模型并处理其回复构成一个 Step。TaskManager 的 Task 是模型维护的待办清单条目；`asyncio.Task` 是 Python 调度协程的运行对象，两者不是同一概念。Session 可以包含多个 Run，Run 可以包含多个 Step。

#### P05.1｜追问：一次 AgentLoop 是整个多轮聊天吗？

**标准回答：** 不是。当前主链路每条输入创建一个 Runner/Loop，Loop 可包含多次模型与工具交互。用户下一次输入会开启另一个 Run/Loop；之前内容通过 SessionStore 读取后放进新 Context，而不是靠旧 Loop 一直保留。

#### P05.2｜追问：一个 Step 能调用多个工具吗？

**标准回答：** 能。一条模型回复可以包含多个 `tool_use`。当前 Loop 用 `for` 逐个 `await invoke_tool`，所以这些工具默认顺序执行。一次模型回复有三个工具调用，仍然是一个 Step，并不是三个 Step。

**代码依据：** [Loop](../../src/kama_claude/core/loop.py)、[Task 模型](../../src/kama_claude/core/task/model.py)。

### P06｜面试官：Core 怎样启动，配置优先级是什么？

**标准回答：** `kama-core` 进入 `asyncio.run(CoreApp().run())`。Core 加载配置、初始化日志和 Trace、创建权限与广播服务、建立 SessionStore 和 MCP 连接，再创建 SessionManager、注册 RPC 并启动 TCP 服务。配置总体是默认值 → 全局 TOML → 项目 TOML → 环境覆盖；`.env` 先加载到环境但不覆盖已有系统变量。显式指定 `KAMA_CONFIG` 时只读取该 TOML 路径，不再自动叠加默认两个文件。

#### P06.1｜追问：项目运行路径是什么？

**标准回答：** 相对路径基于进程当前工作目录，不是 Python 源文件所在目录。`.env`、`.kama/config.toml`、项目记忆和工具相对路径都会受影响。用户级会话、日志等路径通过 `~` 指向用户主目录；手工启动时建议从目标项目目录执行。

#### P06.2｜追问：为什么设置了 DeepSeek key 仍可能失败？

**标准回答：** Runner 默认创建 DeepseekProvider，但配置默认模型仍是 Anthropic 示例。key 正确不代表模型名和接口匹配；还需显式设置对应模型。当前没有统一的 Provider 环境配置开关，我会增加工厂和启动校验，避免平台、模型与依赖不一致。

**代码依据：** [config.py](../../src/kama_claude/core/config.py)、[app.py](../../src/kama_claude/core/app.py)、[runner.py](../../src/kama_claude/core/runner.py)。

### P07｜面试官：后台启动和 Windows 退出怎样实现？

**标准回答：** CLI 的 `core start` 先尝试连接端口，失败时用当前 Python 的 `-m kama_claude.core` 启动子进程，重定向输出并写 PID。代码传入 `start_new_session=True`，其调用 `setsid()` 分离会话的语义属于 POSIX，不能当作 Windows 已具备同样后台隔离的保证。打印 started 也不代表服务已就绪。前台 Core 在非 Windows 注册信号处理；Windows 默认由 `asyncio.run` 将首次 Ctrl+C 转为主任务取消。进入等待退出阶段后，Core 的 `finally` 才负责清理已跟踪运行、MCP、服务器和 Trace；这不覆盖所有启动中断与强制终止情形。

#### P07.1｜追问：后台 stop 与前台 Ctrl+C 的保证一样吗？

**标准回答：** 不一样。CLI stop 先用 `_running_pid()` 读取 PID，再调用 `os.kill(..., SIGTERM)`。其中 `os.kill(pid, 0)` 在 POSIX 常用于存活/权限检查，但 Windows 的零信号不具有相同保证：按 Python 文档，它属于走 `TerminateProcess` 的其他信号值，可能直接终止进程；SIGTERM 在 Windows 也不能当作协作式清理。PID 还可能过期或被复用。因此当前后台管理有平台缺陷，我会增加安全的存活与身份检查、应用层关闭和就绪确认。不能用真实重要进程调用零信号来做探活实验。

#### P07.2｜追问：为什么中文 JSON 会乱码？

**标准回答：** 编码链路不一致时会乱码。`ensure_ascii=False` 只是让 JSON 保留中文，不规定文件如何编码。SessionStore 显式使用 UTF-8，但 TaskManager、Trace 等仍有默认编码读写，需要逐处统一；终端显示编码和子进程输出编码还要独立检查。

**代码依据：** [CLI Core 命令](../../src/kama_claude/cli/commands/core.py)、[CoreApp](../../src/kama_claude/core/app.py)、[TaskManager](../../src/kama_claude/core/task/manager.py)。

**平台依据：** [Python os.kill](https://docs.python.org/3.12/library/os.html#os.kill)、[Popen 的 start_new_session](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen)。以上平台语义来自官方说明，本次未对真实进程执行零信号测试。

## 二、通信、事件与前端

### P08｜面试官：为什么选择 TCP，而不是 WebSocket 或 HTTP？

**标准回答：** 我当前的客户端是 Python CLI/TUI，本地 TCP 接入直接，也便于跨平台复用。WebSocket 适合浏览器双向消息，HTTP 加 SSE 也可以实现命令与事件。选择 TCP 后，我需要自己处理分帧、响应关联和重连。WebSocket 解决的是另一层连接/帧协议，并不会替我实现 Session、工具审批和任务恢复。

#### P08.1｜追问：为什么不用 Unix Domain Socket？

**标准回答：** 本地 IPC 可以使用它，且可结合文件权限管理访问。我的项目选择回环 TCP 以统一客户端连接方式和跨平台使用。端口冲突与访问控制是相应代价；不能说 Unix Socket 做不了双向通信。

#### P08.2｜追问：改成 Web 前端，要全部重写吗？

**标准回答：** 业务组件原则上可以保留，增加 HTTP/WebSocket 适配层，将命令映射到现有业务入口，将事件转换为相应推送格式。仍需补认证、连接归属、取消与恢复，不能把裸 TCP 直接暴露给普通网页作为现成接口。

**代码依据：** [transport/](../../src/kama_claude/core/transport/)。

### P09｜面试官：JSON、JSON-RPC、NDJSON、TCP 各解决什么？

**标准回答：** JSON 表示数据；JSON-RPC 规定方法调用、ID、结果和错误结构；NDJSON 用换行区分连续 JSON 消息；TCP 提供有序字节流。比如 `session.create` 的方法名属于 RPC，序列化后追加 `b"\n"` 是分帧，`writer.write` 是写入传输流。这几个概念不相互替代。

#### P09.1｜追问：事件推送是标准 JSON-RPC notification 吗？

**标准回答：** 当前不是。项目事件信封是 `{"kind":"event","event":...}`；标准 JSON-RPC notification 仍是请求结构，只是不带 ID。文档应准确描述为 JSON-RPC 请求/响应加自定义事件信封，而非所有消息都严格是 JSON-RPC notification。

#### P09.2｜追问：实现了 JSON-RPC 2.0 就完整兼容规范吗？

**标准回答：** 不能这样说。项目请求模型要求字符串 ID，参数主要是对象，没有完整支持规范允许的批量请求、无 ID 通知等情况。它采用了规范中的核心请求/响应形式，支持范围仍以代码为准。

**代码依据：** [envelope.py](../../src/kama_claude/core/bus/envelope.py)、[JSON-RPC 规范](https://www.jsonrpc.org/specification)。

### P10｜面试官：TCP 的粘包、半包怎样处理？

**标准回答：** TCP 不保留应用消息边界，一次写入可能被拆开，多次写入也可能一起到达。项目把一条完整 JSON 序列化后追加换行，接收端 `readline()` 等到一行再解析。它利用换行恢复消息边界，不依赖一次读取恰好对应一次写入。当前还设置了较大的读取行限制。

#### P10.1｜追问：JSON 内容本身有换行，会不会拆错？

**标准回答：** 正常 JSON 序列化会把字符串里的换行转义成反斜杠和 n，只有帧尾换行是真正分隔符。发送端必须使用单行序列化，不能把带格式缩进的多行 JSON 当作同一 NDJSON 帧直接发送。

#### P10.2｜追问：有行长限制就已经可靠了吗？

**标准回答：** 还不够。Python 3.12 的 StreamReader.readline 会把底层超限情况包装为 `ValueError`，已用小读取上限和超长行的内存实验确认。当前服务端只捕获 `LimitOverrunError`，因此这个路径不会按预想发送 Request too large，而可能直接退出连接处理；客户端同时捕获 ValueError，有不同处理。MCP 的读取也存在同类覆盖缺口。还要验证畸形帧、慢速发送和资源回收；64 MB 单帧限制不代表总体内存和并发数已受控。

**代码依据：** [SocketServer](../../src/kama_claude/core/transport/socket_server.py)、[SocketClient](../../src/kama_claude/core/transport/socket_client.py)。

### P11｜面试官：同一条连接怎么区分事件和请求响应？

**标准回答：** 客户端只用一个接收循环读取该 StreamReader。`send_command` 生成 UUID，把 Future 存进 `_pending[id]`，发送请求后等待 Future。接收循环将带 `jsonrpc` 的响应按 ID 找到 Future，设置结果或异常；`kind=event` 则交给事件回调。请求等待方和事件处理方共用接收入口。

#### P11.1｜追问：为什么必须先启动接收循环再发命令？

**标准回答：** `send_command` 自己不读取响应，只等待 Future。如果没有接收循环，就没有代码把收到的响应填进 Future，调用会一直等待。先启动接收任务，再发送订阅和创建会话，能建立完整的响应分发链。

#### P11.2｜追问：取消请求会不会泄漏 pending？

**标准回答：** 当前发送路径没有完整的单请求超时/取消 `finally` 清理。响应到达会 pop，整个接收循环退出也会取消并清空 pending；但若请求取消后一直没响应而连接仍保持，条目可能滞留。我会给请求设置截止时间并保证单条清理，迟到响应忽略即可。

**代码依据：** [SocketClient.send_command / run_event_loop / _dispatch](../../src/kama_claude/core/transport/socket_client.py)。

### P12｜面试官：服务端为什么为每条请求 create_task？

**标准回答：** 因为长请求可能等待用户审批。如果读循环直接 `await` 整个 `session.send_message`，就无法继续读取同一连接上的 `permission.respond`，而长请求又等着审批才能结束，形成循环等待。独立 Task 让接收循环继续读，审批请求可以被并发处理。

#### P12.1｜追问：这样同一 Session 会并行执行两个 Run 吗？

**标准回答：** 网络请求可以并发，但 SessionManager 用每会话锁和 busy 检查保护业务执行；同一会话已有 Run 时，新的发送请求返回 busy。审批响应不走这把会话执行锁，因此能在 Run 运行中被处理。并发接收与业务串行是两个层次。

#### P12.2｜追问：create_task 后就没有问题了吗？

**标准回答：** 仍需登记 Task、设置限额、处理异常和关闭时回收。当前请求 Task 没有完整统一管理，快速发送大量请求可能积压。我的改进会让连接级任务有所有者，并区分取消 RPC 等待与取消实际 Run，避免断连后状态不明。

**代码依据：** [SocketServer._read_loop](../../src/kama_claude/core/transport/socket_server.py)、[SessionManager.send_message](../../src/kama_claude/core/session/manager.py)。

### P13｜面试官：writer.drain() 到底保证什么？

**标准回答：** `write()` 把数据交给本地写缓冲，`drain()` 配合高低水位控制背压：缓冲过多时等待，有空间后继续。它不保证远端业务已读取、执行或落盘。项目发送响应和广播事件都会调用它，防止生产者无限快地写入慢连接。

#### P13.1｜追问：ping 客户端和服务端为什么都 close？

**标准回答：** 它们关闭的是两个进程各自持有的连接端点，不是同一个 Python writer。客户端不再使用时释放自己的资源；服务端在连接处理退出的 finally 中释放自己的资源。一次 TCP 连接对应双方资源，双方都需要正确管理。

#### P13.2｜追问：close 与 wait_closed 有什么区别？

**标准回答：** `close()` 请求关闭写流，`wait_closed()` 等待本地传输关闭完成。它们都不是远端业务成功的证明。项目部分清理路径有等待和超时保护，部分只发起关闭，因此要具体看路径，不能笼统声称所有连接都已经可靠排空。

**代码依据：** [SocketClient](../../src/kama_claude/core/transport/socket_client.py)、[SocketServer](../../src/kama_claude/core/transport/socket_server.py)、[Python Streams](https://docs.python.org/3.12/library/asyncio-stream.html)。

### P14｜面试官：TUI 怎么实现，为什么 socket_loop 有 while True？

**标准回答：** TUI 是 Textual 实现的终端前端，组件展示消息、工具和审批。外层 while 管理连接与重连：建立客户端、启动接收任务、订阅和创建 Session，然后 `await loop_task` 保持当前连接；连接失败或退出后等待两秒再重试。它不会在连接正常时持续创建新客户端。真正持续读消息的是 SocketClient 的内层读取循环。

#### P14.1｜追问：post_message 为什么能调用 on_permission_select_decided？

**标准回答：** PermissionSelect 发布自定义 `Decided` 消息，Textual 根据消息类型、处理器命名约定和消息传播规则查找对应方法。App 的 `on_permission_select_decided` 是框架分发目标，通常不需要我再手工注册普通回调。这个本地 UI 消息之后才被转换成 `permission.respond` RPC。

#### P14.2｜追问：重连会恢复原 Session 吗？

**标准回答：** 当前不会，重连会重新 `session.create`，断开时还会清空本地 Session ID。事件回放只补执行记录，不等于恢复会话对象与任务。要实现续聊，还需保存选中会话、恢复服务端索引、重新绑定并同步状态。

**代码依据：** [TUI 的 _socket_loop、PermissionSelect、on_permission_select_decided](../../src/kama_claude/tui/app.py)。

### P15｜面试官：事件系统有什么用，是消息队列吗？

**标准回答：** EventBus 是 Core 内存中的发布/订阅组件。执行逻辑发布模型 token、步骤、工具、审批等事件，广播器和记录器订阅处理，减少执行逻辑对界面与文件的直接依赖。当前 publish 按注册顺序逐个 await handler，没有持久消息队列、消费确认和重试语义。

#### P15.1｜追问：一个订阅者慢，会影响其他订阅者吗？

**标准回答：** 会影响同次 publish 后面的订阅者，也会使发布它的协程等待。若订阅者抛异常且没有自己处理，还可能使 publish 失败。我会按需求隔离订阅者错误和慢消费者，但不能简单无限 create_task，否则会丢失顺序并积压任务。

#### P15.2｜追问：顺序 await 就代表所有事件全局有序吗？

**标准回答：** 不代表。不同发布协程能在 await 处交错，只有一次 publish 内的调用顺序明确。要跨 Run 比较顺序、检测漏事件，需要定义序号、归属与持久化位置；时间戳也不能自动形成可靠的全局提交顺序。

**代码依据：** [EventBus](../../src/kama_claude/core/events/bus.py)、[事件类型](../../src/kama_claude/core/bus/events.py)。

### P16｜面试官：Core 怎样把事件广播给前端？

**标准回答：** Core 启动时把 `IpcEventBroadcaster.handle` 注册到 EventBus。客户端发 `event.subscribe`，Core 取得当前请求的 writer，把 writer、topics、scope 存进广播器。事件发布后，广播器按事件 type 的 glob 和 `global` / `run:<id>` 范围过滤，封装事件、写入匹配连接并 drain。断连会移除该连接的广播订阅。

#### P16.1｜追问：handler 怎么知道请求属于哪个 writer？

**标准回答：** SocketServer 在执行 handler 前把 writer 放进 ContextVar，订阅 handler 通过 `get_connection_writer()` 取出。ContextVar 提供任务上下文隔离，适合并发请求携带连接信息；它不是把所有请求共享到一个普通全局 writer 变量里。

#### P16.2｜追问：events.jsonl 是否也按 Run 过滤？

**标准回答：** 当前 EventWriter 没有像广播器那样过滤 Run，也没有在结束时从 EventBus 退订。共享总线上同时打开的 Writer 可能记录其他 Run 的事件，关闭后的订阅也会累积。我会给订阅可释放句柄，并明确主子 Run 和会话事件的归档规则，再加入归属过滤测试。

**代码依据：** [广播器](../../src/kama_claude/core/transport/ipc_broadcaster.py)、[ContextVar](../../src/kama_claude/core/transport/socket_server.py)、[EventWriter](../../src/kama_claude/core/events/writer.py)。

### P17｜面试官：events、Trace、普通日志和 thread 分别记录什么？

**标准回答：** `events.jsonl` 记录任务业务事件；Trace 记录 IPC、事件与模型请求/响应链路，载荷受配置控制；普通日志用于程序诊断；`thread.jsonl` 保存用于后续模型对话的消息。它们有交集但用途不同。比如工具调用事件便于看进度，模型请求 Trace 便于查看实际发送的上下文。

#### P17.1｜追问：TraceWriter 用了队列，写文件就不阻塞了吗？

**标准回答：** 没有。emit 快速入队，将写入交给后台协程；后台仍执行同步 open/write/flush，慢磁盘仍可能占用事件循环。队列无界时还可能消耗内存；消费者失败后，未完成记录会让 join 等待。因此需要有界策略、错误通知和实际耗时测量。

#### P17.2｜追问：记录完整模型输入有什么代价？

**标准回答：** 存储量更大，也可能记录文件内容或其他敏感数据。当前有 include payload 开关，但完整可观测性还需脱敏、保留策略和访问控制。入队引用可变消息时也要注意快照语义，避免写出被后续修改后的内容；Trace 不是可靠事务日志。

**代码依据：** [trace/](../../src/kama_claude/core/trace/)、[logging_setup.py](../../src/kama_claude/core/logging_setup.py)、[SessionStore](../../src/kama_claude/core/session/store.py)。

## 三、Agent 循环与模型适配

### P18｜面试官：Runner 和 ExecutionContext 各负责什么？

**标准回答：** Runner 是一次 Run 的依赖组装与结果收尾入口，负责历史、记忆、工具、Provider、事件文件和压缩器。ExecutionContext 是运行状态，包含 messages、step、status、reason、result 等，并组合系统提示。Loop 消费和更新 Context，不负责整个 Core 的启动或会话列表。

#### P18.1｜追问：_runner_factory 是从哪里来的？

**标准回答：** CoreApp 创建 SessionManager 时传入 `lambda: AgentRunner(...)`，SessionManager 存为 `_runner_factory`。每次调用会得到新 Runner，同时注入 Core 共享总线、权限和 MCP 管理器。它是一个保存起来的可调用对象，不是必须在类内找到同名方法。

#### P18.2｜追问：Context 已有 goal，为什么还要 prefill_messages？

**标准回答：** goal 表达本次任务目标，prefill 是实际要回放的已有消息。Context 初始化优先使用非空 prefill；没有历史才用 goal 构造用户消息。因此“改了 goal”不一定等于“改了发给模型的当前用户消息”，这也是 Skill 参数路径要检查的原因。

**代码依据：** [Runner](../../src/kama_claude/core/runner.py)、[Context](../../src/kama_claude/core/context.py)、[CoreApp](../../src/kama_claude/core/app.py)。

### P19｜面试官：AgentLoop 的核心循环怎样结束？

**标准回答：** 每步增加 step、发布开始事件，调用 Provider，再追加回复。`tool_use` 时逐个执行工具并回填；`end_turn` 时保存最终文本并成功；否则达到 max_steps 会失败，同一步满足两者时 end_turn 优先。Loop 只在调用 Provider 的 try 中把普通 Exception 标为 llm_error、把 CancelledError 标为 cancelled 后重抛。取消若发生在工具执行、审批或其他等待处，会向外传播，却不一定由 Loop 更新 Context。顶层 Runner 的外层捕获能补部分收尾；直接运行子 Loop 没有同样保证。

```text
while context.status == running:
    step += 1
    response = await provider.chat(messages, tools, system)
    append_assistant(response)
    execute_and_append_tool_results_if_needed(response)
    decide_end_turn_or_max_steps()
    compact_if_needed_and_still_running()
```

#### P19.1｜追问：它属于 ReAct 还是固定工作流？

**标准回答：** 它是模型决定下一步工具、程序执行并反馈观察的循环，具有 ReAct 式交互特征。没有强制模型输出显式 Thought，也没有硬编码的完整规划 DAG。Skill 提示或清单工具可以引导计划，但不等于系统已经实现严格 Plan-and-Execute 调度器。

#### P19.2｜追问：输出 token 到上限、工具参数没生成完怎么办？

**标准回答：** 当前 Loop 对 `max_tokens` 且有工具调用的响应，不执行不完整调用，而是补错误 tool_result 维持配对，再根据步数继续或结束。OpenAI Provider 则会把非 stop/tool_calls 的结束原因视为不完整响应并抛错，两家路径并未完全统一。

**代码依据：** [Loop](../../src/kama_claude/core/loop.py)、[Provider](../../src/kama_claude/core/llm/provider.py)。

### P20｜面试官：add_tool_result 为什么有合并逻辑？

**标准回答：** 项目内部使用 Anthropic 风格的消息块：assistant 消息包含 `tool_use`，其结果放进 user 消息的 `tool_result`，通过 `tool_use_id` 对应。同一模型回复可以提出多个工具调用，Context 把这些结果放进一条 user 消息的数组，避免每个结果都单独制造一个 user 回合。

#### P20.1｜追问：它会把真实用户输入也合进去吗？

**标准回答：** 正常不会。只有最后一条是 user、content 是非空列表、且列表里全是 tool_result 时，才向其中追加。最后一条是普通字符串或混合内容时会新建消息。这些条件就是为了区分工具结果集合与其他用户内容。

#### P20.2｜追问：工具失败为什么也要回填结果？

**标准回答：** 模型需要知道调用失败，才能修正参数、换方法或解释原因；同时要保持 tool_use 与 tool_result 的关联。失败结果带 is_error 和错误内容，但不意味着所有错误都应无限交给模型重试。取消和进程崩溃也可能打断配对，需要历史修复策略。

**代码依据：** [ExecutionContext.add_tool_result](../../src/kama_claude/core/context.py)、[Loop](../../src/kama_claude/core/loop.py)。

### P21｜面试官：AnthropicProvider 怎样把流式调用变成统一结果？

**标准回答：** 我先发布模型选择事件，构造 system、messages、工具与输出限制，调用 SDK 的流接口。文本片段产生 token 事件，流结束后取得完整消息，提取 tool_use、thinking、停止原因和 usage，返回统一 LlmResponse。Loop 因而不用直接处理 SDK 类型。thinking 与 signature 按收到的值保留，但不能据此说当前请求主动启用了所有 thinking 功能。

#### P21.1｜追问：网络断流后怎么重试？

**标准回答：** 代码只捕获 `httpx.RemoteProtocolError`、`httpx.ReadError`、`httpx.ConnectError`；只有实际异常匹配时，外层才最多尝试三次，失败后的两次等待是一秒、两秒。本地 Anthropic 1.15.0 使用 httpx2，其对应异常不是 httpx 异常的子类；连接建立失败还可能包装成 APIConnectionError，由 SDK 自身策略处理。关闭 SDK 重试的无网络实验中，连接失败只发起一次请求便外抛。因此“三次”是该外层循环的条件上限，不能保证所有网络失败都会进入它。

如果用假流注入可匹配的 httpx.ReadError，外层确实会重试，但它仅在首次尝试发布 token。实验得到“返回完整重试文本、发布的 token 仅有首次片段”；当前 TUI 没有从 run.finished 补回全文，该事件也不带最终文本。所以需要修复重试与流式展示的契约，而不是声称已经可靠恢复显示。

#### P21.2｜追问：cache_control 表示一定命中缓存吗？

**标准回答：** 不表示。代码在 system 和最后一个工具上附加缓存标记，是否支持、命中和计费由实际服务规则决定。必须看 usage 中的缓存统计。缓存不等于删除消息，也不替代会话历史保存；未知模型还使用固定窗口回退值，不能把它当作精确容量。

**代码依据：** [AnthropicProvider.chat](../../src/kama_claude/core/llm/provider.py)。这里描述的是仓库行为，不承诺厂商当前缓存政策。

### P22｜面试官：OpenAI 和 DeepSeek 分别怎样接入？

**标准回答：** OpenaiProvider 在一个文件内转换消息和工具：tool_use 转成 assistant.tool_calls，tool_result 转成 role=tool，工具 Schema 包装为 function。流式工具参数按 index 累积，结束后解析 JSON 并校验结束原因，再统一为 LlmResponse。DeepseekProvider 则继承 AnthropicProvider，只用自己的 key 和兼容 endpoint 初始化客户端，复用其 chat。

#### P22.1｜追问：为什么不直接把内部消息发给 OpenAI？

**标准回答：** 两家的工具结果角色、字段和 Schema 包装不同。内部 user/tool_result 不能原样作为 OpenAI 的工具回复。转换必须保留调用 ID、名称和参数，多个流片段也要拼完整再解析；OpenAI 转换当前还会拒绝某些不支持的块，不能说所有消息类型无损通用。

#### P22.2｜追问：三家重试、模型和依赖是否完全统一？

**标准回答：** 没有。DeepSeek 继承同一段 Anthropic chat 代码，也继承其异常类型匹配和流式展示的限制，不能据此保证实际断流一定重试。OpenAI 类没有同样的显式循环；两类 SDK 自身重试要与项目外层重试分别统计，并核对安装版本。默认 Runner 固定 DeepSeek，模型默认值却需覆盖；OpenAI SDK 延迟导入且未在默认依赖中安装。统一工厂、配置和异常契约是后续改进，当前依赖未锁定也会影响复现。

**代码依据：** [provider.py](../../src/kama_claude/core/llm/provider.py)、[pyproject.toml](../../pyproject.toml)、[config.py](../../src/kama_claude/core/config.py)。

## 四、工具与权限

### P23｜面试官：怎样增加一个新工具？Schema 与 params_model 为什么都有？

**标准回答：** 实现 BaseTool 的名称、描述、input_schema 和 async invoke，按需要提供 Pydantic 参数模型，然后注册进 Runner 的 ToolRegistry。Schema 给模型看，params_model 在本地验证实际参数。Registry 向模型导出 Schema，执行时按名称查实例；模型声称调用了工具，不代表它能直接运行任意 Python 方法。

#### P23.1｜追问：参数验证后的对象传给工具了吗？

**标准回答：** 当前 invoke_tool 调用 model_validate 检查合法性，但没有把规范化后的模型对象传下去，而是继续传原参数字典。内置工具通常再解析一次。因此不能声称统一入口已完成一次解析后全链路复用；默认值与转换行为要检查工具内部。

#### P23.2｜追问：MCP 工具为什么 params_model 可以是 None？

**标准回答：** MCP 的 Schema 来自外部发现，并没有自动生成本地 Pydantic 类，所以 wrapper 不走这层模型校验。Schema 仍会展示给模型，但不是本地强校验已经完成的证明。后续可增加动态 Schema 验证，并保留服务端校验与错误处理。

**代码依据：** [BaseTool](../../src/kama_claude/core/tools/base.py)、[Registry](../../src/kama_claude/core/tools/registry.py)、[McpTool](../../src/kama_claude/core/mcp/tool.py)。

### P24｜面试官：工具调用怎样处理超时、失败和重试？

**标准回答：** invoke_tool 先发布开始事件、查工具、校验参数、检查权限，再用 wait_for 限时调用。它显式处理未知工具、Pydantic ValidationError、拒绝审批，以及尝试循环内的超时和多数普通调用异常；进入循环且归类为 runtime_error 或 rate_limited 的失败最多额外重试两次，等待二秒、四秒。未知工具等前置返回不重试，超时、参数错误和拒绝也不走该重试。不是所有异常都会变成 ToolResult：审批检查及部分事件发布在捕获范围外，订阅者抛错可以直接外传；取消同样需单独传播与清理。顶层 Runner 可把捕获到的普通异常标为失败，不能把此保证套到所有子 Loop 或 BaseException。

#### P24.1｜追问：工具默认 120 秒是否包括审批等待？

**标准回答：** 当前不包括。审批在进入 tool.invoke 的 wait_for 之前完成，PermissionManager 有独立等待配置。重试退避和多次尝试也会增加总时长，120 秒不是整条调用的严格总截止时间。要限制总耗时，应在更外层定义 deadline。

#### P24.2｜追问：对写入或命令执行统一重试安全吗？

**标准回答：** 不一定。命令可能已执行部分操作后返回错误，再次调用会重复副作用。前台 spawn_agent 的失败也可能触发重新派生。我的改进是声明工具的重试能力、区分确定失败与结果未知，并按需要使用业务操作 ID；当前没有完整的幂等执行框架。

**代码依据：** [invoke_tool](../../src/kama_claude/core/tools/invocation.py)、[工具错误类型](../../src/kama_claude/core/tools/errors.py)。

### P25｜面试官：读文件、写文件、目录和命令工具怎么实现？

**标准回答：** 文件工具用 Path 读写，目录工具遍历并组织文本输出；BashTool 用异步 shell 子进程执行命令，合并 stdout/stderr，等待 communicate，超时 kill 后回收。工具结果统一交回 Loop。当前读文件先读全内容再截取，命令也先收集输出再截取，返回长度限制并不等于峰值内存已受严格控制。

#### P25.1｜追问：BashTool 在 Windows 一定是 Bash 吗？

**标准回答：** 不是。名字叫 bash，但 create_subprocess_shell 使用平台的 shell 机制，不能假设语法、变量和编码等同于 Linux Bash。Windows 前台 Core 可运行，不代表任意 Unix 命令也可运行。我会明确 shell 配置，并为命令与输出编码做平台测试。

#### P25.2｜追问：当前文件路径检查能禁止工作区外访问吗？

**标准回答：** 不能完整保证。部分工具只拒绝路径里的 `..`，没有统一解析后验证绝对路径、符号链接是否在工作区。描述里写“相对路径”也不是执行约束。我会传入 workspace root，统一解析与审批；命令执行仍需单独的隔离与策略。

**代码依据：** [内置工具](../../src/kama_claude/core/tools/builtin/)，重点看 read_file.py、write_file.py、list_dir.py、bash.py。

### P26｜面试官：四个 Task 工具与普通工具有什么区别？

**标准回答：** 它们围绕一个共享 TaskManager 操作清单：create 创建条目，get 读取，list 返回列表，update 修改状态和依赖。每个 Run 在自己的 `.tasks` 下保存 task_N.json；完成一个任务时，Manager 清理其他条目对它的 blocked_by 引用。这提供了可观察的计划记录，但不是自动运行任务的调度器。

#### P26.1｜追问：有 blocked_by 就能自动保证任务顺序吗？

**标准回答：** 当前不能。依赖是数据，代码没有因此建立完整的可执行 DAG 调度与状态约束。任务是否开始仍依赖模型调用；更新依赖也没有完整的环检测。若要强约束，需要校验状态转换、依赖有效性与有环情况，再设计调度器。

#### P26.2｜追问：模型为什么有时一个 Task 都不创建？

**标准回答：** 工具可用不代表强制使用。当前 Loop 没有规定先建清单，模型可能认为简单任务直接执行即可。若产品需要可见计划，我会明确提示或增加程序层计划阶段，并验证额外调用的成本；不能把没有调用清单工具直接判为模型故障。

**代码依据：** [TaskManager](../../src/kama_claude/core/task/manager.py)、[task 工具](../../src/kama_claude/core/tools/builtin/)。

### P27｜面试官：人工审批怎样暂停和恢复工具执行？

**标准回答：** invoke_tool 调 PermissionManager.check_and_wait。需要询问时，Manager 按 tool_use_id 保存 Future，发布 permission.requested 事件并等待。TUI 展示选项，用户决定后发 permission.respond，Core handler 调 Manager.respond，按 ID 完成 Future。原协程恢复，根据允许或拒绝继续；等待期间事件循环还能处理其他请求。

#### P27.1｜追问：为什么不用 while 循环轮询用户有没有决定？

**标准回答：** Future 可以让等待方挂起，由响应主动唤醒，避免定时轮询和额外状态检查。Future 不是进程间共享对象，它只在 Core；跨进程传回的是 RPC 数据，再由 Core 更新对应 Future。

#### P27.2｜追问：超时、断连和取消都处理完整了吗？

**标准回答：** 没有。已有审批超时和 cancel_session，但断连与所有权没有完整接线。Manager 先保存 pending Future，再发布审批事件，等待与超时处理的 try 在发布之后；实验中订阅者抛 RuntimeError，异常直接逃出 check_and_wait 和 invoke_tool，pending 仍有一项。等待中取消也缺少统一 finally 清理，timeout=0 更不能依赖超时兜底。我会把登记、发布和等待纳入同一生命周期清理，保留迟到决定的安全忽略；同时区分顶层 Runner 收尾与子 Loop 状态。

**代码依据：** [PermissionManager](../../src/kama_claude/core/permissions/manager.py)、[invoke_tool](../../src/kama_claude/core/tools/invocation.py)、[TUI](../../src/kama_claude/tui/app.py)。

### P28｜面试官：权限策略、缓存和持久化的优先级是什么？

**标准回答：** 当前运行时先检查 bash 的 deny_patterns，再检查工作区外操作启发式；后者强制走询问，不被缓存绕过。否则依次查询会话 always 缓存、持久 always 缓存、bash allow_patterns 和工具默认决策。默认 ASK 才创建 Future。policy 定义规则与静态评估，storage 读写策略文件，Manager 负责运行时状态。

#### P28.1｜追问：evaluate 为什么看起来没被调用？

**标准回答：** 静态 evaluate 只计算规则层决策，实际 invoke_tool 调用的是 check_and_wait。后者为缓存和异步等待重新组织了检查逻辑，没有直接复用 evaluate。因此它不是运行必经入口，重复实现也存在漂移风险，应抽出共享的规则计算并保留明确的优先级测试。

#### P28.2｜追问：always_allow 只对本次会话有效吗？

**标准回答：** 当前不是。它同时更新会话缓存和按工具名保存的持久缓存，再尝试写 policy.toml，所以可能影响后续会话。作用范围比用户直觉更广，保存失败也主要记录日志。我会拆分会话/项目/全局授权并提供撤销，不能把现有 always 说成细粒度参数授权。

**代码依据：** [policy.py](../../src/kama_claude/core/permissions/policy.py)、[manager.py](../../src/kama_claude/core/permissions/manager.py)、[storage.py](../../src/kama_claude/core/permissions/storage.py)。

### P29｜面试官：如何应对危险工具和提示词注入？

**标准回答：** 当前以参数校验、工具白名单、权限规则和人工审批控制调用。文件和工具输出可能带恶意指令，模型不能作为最终授权边界。真正执行前仍要由程序限制可用工具、路径和权限。当前没有操作系统沙箱，也没有完整身份认证；我会明确这些限制，避免把提示词要求当作安全保证。

#### P29.1｜追问：提示里写“不要删除文件”不够吗？

**标准回答：** 不够。提示只能影响模型行为，恶意上下文或模型错误仍可能产生危险调用。程序必须在执行边界检查实际参数，必要时拒绝或要求审批。对于 shell 等强能力工具，还应减少权限并定义隔离环境，而非只增加提示文字。

#### P29.2｜追问：监听 127.0.0.1 就能防止其他人调用吗？

**标准回答：** 它限制直接网络可达范围，但不证明调用者身份。同机其他进程仍可能访问，订阅 scope 也只是过滤条件。若需要安全边界，我会增加连接认证、会话归属和审批响应授权，并检查日志、密钥和本地文件访问权限。

**代码依据：** [权限模块](../../src/kama_claude/core/permissions/)、[SocketServer](../../src/kama_claude/core/transport/socket_server.py)。

## 五、会话、记忆与上下文治理

### P30｜面试官：为什么 Session 有 active、waiting_for_input、closed？

**标准回答：** 状态表达会话的使用阶段。创建时 active；chat 的一次 Run 结束后进入 waiting_for_input，下一条输入时发布恢复事件；one_shot 结束后 closed。closed 会话不能继续发送。同一会话能否正忙，当前主要还靠锁判断，不应仅看 status 文本；代码也没有在每个位置把它更新成完整的执行状态机。

#### P30.1｜追问：为什么一轮结束不直接关闭 chat？

**标准回答：** chat 的用途就是在同一 Session 中保留历史继续交互，等待输入与关闭有不同语义。waiting 表示可以继续，closed 表示不再接收普通输入。one_shot 才是在一次任务后结束会话；这与 Run 自己成功或失败又是不同维度。

#### P30.2｜追问：会话文件都在，重启后为什么找不到？

**标准回答：** SessionManager 的索引从空字典开始，_get_session 只查内存，没有扫描或按需恢复元数据。因此文件存在不等于 RPC 可访问。我会重建会话索引和锁，把执行中的状态改成中断，并提供 TUI 选择旧会话；恢复历史不意味着重启原协程。

**代码依据：** [SessionManager](../../src/kama_claude/core/session/manager.py)、[Session 模型](../../src/kama_claude/core/session/model.py)。

### P31｜面试官：每轮 Runner 都是新的，历史怎么保留？

**标准回答：** 历史属于 SessionStore，不依赖 Runner 常驻。SessionManager 先保存本轮输入，Runner 从 thread.jsonl 读取消息作为 prefill，记录历史长度；本轮结束再追加新增的 assistant 和 tool_result。新 Runner 因而能从文件构建新的 Context，续用同一会话的历史。

#### P31.1｜追问：为什么不把整个 Context 再追加一次？

**标准回答：** Context 包含已经在磁盘的旧消息和本轮输入，全量追加会重复历史。未压缩时用 prefill_len 分界很直接。但这个办法依赖消息列表只在尾部追加，一旦中途替换或删除，就必须重新设计保存边界。

#### P31.2｜追问：run.finished 代表历史已经提交了吗？

**标准回答：** 当前不能。Runner 先发布 RunFinished，再执行 append_messages；如果保存失败，前端可能已看到结束。我要区分“执行结束”和“历史提交完成”，在提交成功后发相应事件，失败时让客户端能知道保存未完成。

**代码依据：** [Runner.run_and_capture](../../src/kama_claude/core/runner.py)、[SessionStore](../../src/kama_claude/core/session/store.py)。

### P32｜面试官：_trim_orphan_tool_use 为什么裁掉后面的消息？

**标准回答：** 它扫描 assistant 的 tool_use ID 与 user 的 tool_result ID，用 pending 集合追踪未完成配对，并记住最后一个 pending 为空的位置。扫描结束仍有未配对调用，就返回此前的平衡前缀，避免把末尾不完整工具交互送给模型。这是读取时的防御，不是磁盘修复。

#### P32.1｜追问：后续再追加合法用户输入就能恢复吗？

**标准回答：** 不一定。原孤立 ID 仍在磁盘，后面没有相应结果时 pending 一直非空，新的消息也可能被同样裁掉。所以用户看到文件增长，不代表新增内容进入模型；要修复或归档坏片段，不能永久依赖前缀截断。

#### P32.2｜追问：你会怎样修，才能不伪造执行结果？

**标准回答：** 我会先保留原始记录，定位中断点，按明确边界重建可用工作历史。可以用显式“工具被中断，结果未知”的记录完成关联，但必须与真实成功区别开；或者归档损坏回合再保留后续合法消息。修复过程要可重复、有版本与失败恢复测试。

**代码依据：** [SessionStore._trim_orphan_tool_use](../../src/kama_claude/core/session/store.py)。

### P33｜面试官：全局记忆、项目记忆、笔记和历史有什么区别？

**标准回答：** 历史保存在 thread.jsonl，按 user/assistant 消息回放；notes.md 保存模型通过 note_save 主动记录的会话事实；`~/.kama/context.md` 与当前项目 `.kama/context.md` 是人工维护的背景文本。Runner 加载后三者，由 Context 加进 system prompt。当前是文件加载与文本注入，没有向量检索或自动知识筛选。

#### P33.1｜追问：note_save 本次调用后立刻改变 system 吗？

**标准回答：** 当前工具将内容写进文件，Runner 开始时读入的 session_notes 字符串不会因此自动刷新。本次工具结果可进入消息，但新的 system 笔记通常要等下一次 Runner 重新加载。文件已更新与内存 Context 已更新要分开看。

#### P33.2｜追问：背景文本很多怎么办，是否永远越多越好？

**标准回答：** 不是。它会占窗口与成本，陈旧或冲突事实也会影响回答。我会给记忆明确来源、范围、长度和更新机制，按任务选择注入内容。若需要大量知识检索再增加 RAG；仅把所有 Markdown 拼进 system 不等于解决了长期记忆管理。

**代码依据：** [memory/loader.py](../../src/kama_claude/core/memory/loader.py)、[Context](../../src/kama_claude/core/context.py)、[note_save.py](../../src/kama_claude/core/tools/builtin/note_save.py)。

### P34｜面试官：工具输出截断与 context_pct 怎样工作？

**标准回答：** SessionStore 加载历史后调用 truncate_tool_results，对超过 8000 字符的字符串结果保留前 4000 字符并附提示，主要影响下一轮读取的内存历史。context_pct 由 Provider 用输入 token 除以代码中的窗口值计算，供 UI 与自动压缩判断。两者都不是精确的调用前总 token 预算。

#### P34.1｜追问：配置里的 tool_result_limit 改了就生效吗？

**标准回答：** 当前配置字段虽然被解析，但读取历史时没有完整传入截断函数，仍使用默认参数。因此不能根据配置对象存在就认定功能已接线。我要沿“加载配置 → 构造组件 → 调用函数”检查，并写修改配置确实改变结果的测试。

#### P34.2｜追问：为什么上下文比例可能不准确？

**标准回答：** 首先，Anthropic 的总输入为 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`；input_tokens 只是未从缓存读取或写入缓存的那部分。当前 AnthropicProvider 仅用 `usage.input_tokens / window`，缓存命中或创建时会低估。比如普通输入 50、缓存读取 100000、窗口 200000，代码显示 0.025%，按总输入应约 50.025%。OpenAI 的 prompt_tokens 本身是总输入，cached_tokens 属于其中，不能再加一次；DeepSeek 兼容接口也应按实际 usage 核对。此外未知窗口回退、刚追加工具输出和输出预留都会影响预算。我会按 Provider 归一化统计，再做下一次调用前的容量检查。

**代码依据：** [budget.py](../../src/kama_claude/core/compact/budget.py)、[SessionStore](../../src/kama_claude/core/session/store.py)、[Provider](../../src/kama_claude/core/llm/provider.py)。

**统计依据：** [Anthropic 缓存输入统计](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance)、[OpenAI Chat Completions 缓存统计示例](https://developers.openai.com/cookbook/examples/prompt_caching_201)。示例只解释统计差异，不代表当前已修复 context_pct。

### P35｜面试官：自动压缩与手动压缩有什么区别？

**标准回答：** 自动压缩在 Loop 中检查：Run 未结束、刚处理 tool_use、有 usage、阈值大于零且占比达到阈值时触发。它生成摘要，替换 Context 为摘要与确认消息，写 summary 文件并发 ContextCompacted。手动 `/compact` 走 session.compact，在会话空闲、持有会话锁时读取历史，生成摘要，备份并重写 thread。自动阈值默认零，即关闭。

#### P35.1｜追问：为什么自动压缩放在工具结果追加之后？

**标准回答：** 先让 tool_use 与结果配对，再总结一个完整交互片段，减少留下不完整工具消息的风险。压缩请求不提供工具，用独立的静默 EventBus，避免摘要生成 token 混入普通前端输出。它仍会消耗模型调用和 token。

#### P35.2｜追问：手动压缩也写 summary 文件并发同样事件吗？

**标准回答：** 当前没有复用自动 compact 包装方法，而是直接 compact_messages 加 write_compacted，所以不天然具有相同 summary 文件和事件路径。摘要为空或模型异常返回失败；代码也没有严格校验摘要一定更短。不能只凭错误文案有“not beneficial”就说做了收益判定。

**代码依据：** [Compactor](../../src/kama_claude/core/compact/compactor.py)、[SessionManager.compact](../../src/kama_claude/core/session/manager.py)、[Loop](../../src/kama_claude/core/loop.py)。

### P36｜面试官：自动压缩为什么存在跨轮保存缺陷？

**标准回答：** Runner 记录的是压缩前 prefill_len，而 Compactor 会替换消息列表。例如历史 10 条，压缩为 2 条，后面再产生 3 条，结束时 `[10:]` 是空的，新增消息就漏存。同时自动摘要只改内存和 summary 文件，不重写 thread；下一轮仍读取原始历史。压缩当前调用与持久化下次状态没有形成一致的提交协议。

#### P36.1｜追问：直接把 prefill_len 改成 0 可以吗？

**标准回答：** 不足以修复。如果仍向旧 thread 全量追加摘要与后续消息，会把旧长历史和新摘要混在一起，可能重复且越变越长。我会区分原始审计记录与模型工作历史，用明确的快照版本或消息提交游标保存压缩后的权威状态。

#### P36.2｜追问：怎么证明你的修复正确？

**标准回答：** 用假 Provider 强制经历“长历史 → 工具调用 → 自动压缩 → 后续消息 → 新 Run”，断言新消息不漏、不重复，下一轮确实读到新工作历史；再覆盖多次压缩、写入失败、取消与重启。只断言 summary 文件存在不能证明跨轮保存正确。该方案当前仍待实施。

**代码依据：** [Runner 的 prefill_len 与 append_messages](../../src/kama_claude/core/runner.py)、[Compactor](../../src/kama_claude/core/compact/compactor.py)。

## 六、Skills、子 Agent 与 MCP

### P37｜面试官：Skill 是怎么被发现和执行的？

**标准回答：** SkillLoader 按项目 `.kama/skills`、用户 `~/.kama/skills`、内置目录的顺序找 Markdown，支持平铺文件与目录中的 SKILL.md。解析名称、描述、提示正文和工具列表。SessionManager 识别斜杠命令，渲染参数，向 Runner 传目标、系统提示覆盖与白名单。它主要配置一次 Run，不是新的 Python 可执行工具。

#### P37.1｜追问：渲染过的参数一定进入模型了吗？

**标准回答：** 当前不能保证预期替换完整。原始斜杠输入已写进历史，Context 优先使用历史；传入的系统覆盖还是未渲染模板。rendered goal 因而可能没有成为实际消息。我要捕获 Provider 收到的 system/messages 做断言，统一渲染结果的注入位置，而不是只测 render_prompt 返回值。

#### P37.2｜追问：未知 Skill、空斜杠和坏文件怎样处理？

**标准回答：** 未找到 Skill 会沿普通目标路径继续；空 `/` 的拆分索引缺少稳健保护，同名高优先级坏文件也可能直接返回 None，不能保证自动回退到内置版本。我会对命令语法与配置错误给出明确反馈，并定义是否允许回退，避免静默改变行为。

**代码依据：** [SkillLoader](../../src/kama_claude/core/skills/loader.py)、[SessionManager](../../src/kama_claude/core/session/manager.py)、[Context](../../src/kama_claude/core/context.py)。

### P38｜面试官：Skill 白名单、角色配置与权限审批是什么关系？

**标准回答：** 白名单决定哪些工具注册并暴露，角色 TOML 提供子 Agent 的提示和工具范围，权限审批决定某一次实际调用是否允许。工具被暴露不代表调用无需审批，不被暴露也应在执行查找时被拒绝。AgentProfileLoader 同样按项目、用户、内置优先级读取，角色模型字段当前读取后尚未用于独立选型。

#### P38.1｜追问：空白名单表示不允许任何工具吗？

**标准回答：** 当前不是。代码按列表真值构造 allowed，空列表与 None 都变成无限制语义。这不利于表达明确的空权限。我会区分 None 代表继承默认、空集合代表不注册，并对未知工具和配置拼写错误增加验证。

#### P38.2｜追问：父 Agent 限制的工具，子 Agent 能获得吗？

**标准回答：** 当前子工具表主要按自己的角色重新构建，没有通用的父子白名单交集，因此可能扩大范围。我会把有效权限作为显式上下文传递，取父级能力与子配置的交集，同时保留调用时审批。仅靠 prompt 说“不要越权”不能修复注册边界。

**代码依据：** [Runner._build_registry](../../src/kama_claude/core/runner.py)、[角色加载器](../../src/kama_claude/core/agents/loader.py)、[子工具表](../../src/kama_claude/core/subagent/tool.py)。

### P39｜面试官：spawn_agent 实际创建了什么？

**标准回答：** 它创建新 Run ID、只带子任务提示的 Context、新 EventBus、工具表、Loop 和事件目录。子总线通过 bridge 把事件转发到父总线。它直接创建 Loop，没有完整走一遍 Runner，所以不会自动继承父完整历史、笔记、所有 MCP 工具和压缩组件。Provider 与 PermissionManager 等依赖则复用传入对象。

#### P39.1｜追问：独立上下文是否等于进程隔离？

**标准回答：** 不等于。子 Agent 通常仍在同一 Core 进程、同一个事件循环里，使用同一工作区。它们的消息列表和任务清单可以分开，但 CPU、内存、文件副作用和部分服务依然共享。不能把子 Agent 描述成已经实现的容器或独立进程。

#### P39.2｜追问：父任务的关键信息如何传给孩子？

**标准回答：** 当前主要通过 spawn_agent 的 prompt 显式传递，父历史不会全量复制。这样能减少噪声和输入量，但要求任务描述完整。我会让父模型提供目标、约束、文件位置与验收方式，必要时附受控摘要；权限不能由这段文本自行决定。

**代码依据：** [SpawnAgentTool.invoke / _build_child_registry](../../src/kama_claude/core/subagent/tool.py)。

### P40｜面试官：前台与后台子 Agent 怎样返回结果？

**标准回答：** 前台直接 await 子 Loop，成功后把子结果作为 spawn_agent 的 ToolResult，父模型下一步即可读取。后台用 create_task 启动，登记 Task 与 Context，立即返回 Run ID，父模型需调用 agent_result 查询。SubagentFinished 事件供界面观察，不会自动变成父模型的 tool_result。

#### P40.1｜追问：父模型什么时候真正知道后台任务完成？

**标准回答：** 当前要靠后续 agent_result 调用得到 running 或最终结果。界面收到完成事件与模型消息更新是两条路径，没有自动唤醒父模型继续规划的完整机制。如果父 Run 已结束，下一轮又会遇到注册表生命周期问题，因此不能承诺后台完成后自动续跑。

#### P40.2｜追问：前台子任务也受超时和重试影响吗？

**标准回答：** 是。spawn_agent 经过 invoke_tool，外层 wait_for 限制每次工具执行尝试，不包含此前的审批等待；前台子任务业务失败被映射成 runtime_error，还可能触发重新派生。取消发生在 Provider 等待时，子 Loop 会标记 failed/cancelled；发生在子工具或审批等待时，独立 Loop 的 Context 可能仍为 running，已用内存实验确认。子 Agent 没走完整 Runner，不能指望父 Runner 替它更新状态，取消还可能跳过完成事件。我会统一子任务收尾与取消传播，区分业务失败和可重试错误。

**代码依据：** [subagent/tool.py](../../src/kama_claude/core/subagent/tool.py)、[invoke_tool](../../src/kama_claude/core/tools/invocation.py)。

### P41｜面试官：为什么下一轮 agent_result 可能查不到上一轮子任务？

**标准回答：** BackgroundTaskRegistry 是 Runner 的成员，每轮新 Runner 得到新字典。上一轮任务即使还在执行，新工具引用的新注册表也不知道它。注释说“跨 run 共享”不等于生命周期确实跨 Run。我要由 Core 持有共享服务，记录 Session 与父子 Run 归属，再注入各 Runner。

#### P41.1｜追问：Task.done() 能说明子任务成功吗？

**标准回答：** 不能。Loop 可能把 Context 标记 failed 后正常返回，Task 没有 Python 异常。当前 agent_result 检查 cancelled、exception 后直接返回 context.result，没有完整判定业务 status，可能把失败表述成 completed。我会明确 running、success、failed、cancelled 等状态和失败原因。

#### P41.2｜追问：改成全局字典就修完了吗？

**标准回答：** 还需会话所有权、并发上限、取消并等待、结束记录过期与退出清理。重启后只恢复持久元数据和结果，不能恢复 asyncio.Task 对象；未完成记录应标为 interrupted。否则共享字典会带来越权查询和内存长期增长。

**代码依据：** [BackgroundTaskRegistry](../../src/kama_claude/core/subagent/registry.py)、[AgentResultTool](../../src/kama_claude/core/subagent/tool.py)、[Runner](../../src/kama_claude/core/runner.py)。

### P42｜面试官：多个 Agent 怎样协作，怎么控制冲突和成本？

**标准回答：** 当前通过父任务分解、子 prompt、工具结果与事件桥接协作，工具层限制注册的嵌套能力，但没有完整的并发总量、共享预算和文件冲突控制。多 Agent 会增加调用和协调开销，不保证比单 Agent 更快。我会先让子任务只读分析、父任务统一改文件，再用评测决定是否增加并行写入。

#### P42.1｜追问：为什么同一会话锁保护不了子 Agent 改文件？

**标准回答：** 会话锁串行的是顶层 send_message，已经启动的后台任务仍可能与其他任务并行，同一文件还可能被其他 Session 修改。需要按文件或工作区约束写入，例如路径锁、写前版本校验或隔离 worktree；三者成本和合并方式不同。

#### P42.2｜追问：限制嵌套深度为什么不够？

**标准回答：** 深度限制控制树高，不控制每层分支数、总 token、总时长和并行任务数。当前注册逻辑使顶层可创建孩子，孩子可再创建下一层，后续不继续暴露 spawn；还需全局/会话并发额度和预算。额度耗尽时要定义拒绝、排队或取消，而非无限等待。

**代码依据：** [SpawnAgentTool 深度检查与子工具注册](../../src/kama_claude/core/subagent/tool.py)。

### P43｜面试官：MCP 工具从发现到执行的完整过程？

**标准回答：** Core 根据配置让 McpServerManager 建立连接；Client 发送 initialize、接收响应、发送 initialized 通知，再 tools/list。Manager 将发现的定义包装成 McpTool，Runner 把它们放进 Registry。模型看到 Schema 后返回调用，经 invoke_tool 的统一执行路径进入 wrapper，再由 Client 发 tools/call，结果转成 ToolResult 回填模型。

#### P43.1｜追问：为什么要包装成 BaseTool？

**标准回答：** 统一名称、描述、Schema 和 invoke 接口后，Loop 不必区分本地实现与远端 MCP 调用，两者都经过同一注册与审批路径。名称加 `server__tool` 前缀减少冲突。但 wrapper 不自动补齐外部 Schema 校验和所有 MCP 返回类型。

#### P43.2｜追问：接入 MCP 后，工具会自动出现在所有子 Agent 吗？

**标准回答：** 当前不会。顶层 Runner 从 MCP Manager 取工具，子 Agent 自行构建工具表，没有完整复用这一步。是否开放给孩子要结合角色和父级权限设计，再显式注入；不能只看到 Core 已连 MCP 就认为所有执行层都继承。

**代码依据：** [McpServerManager](../../src/kama_claude/core/mcp/server.py)、[McpTool](../../src/kama_claude/core/mcp/tool.py)、[Runner](../../src/kama_claude/core/runner.py)。

### P44｜面试官：你的 MCP 传输和并发模型是什么？

**标准回答：** 当前支持 stdio 子进程和自定义 TCP NDJSON。stdio 从进程管道收发，TCP 连接已有服务；它没有实现 Streamable HTTP。Client 的 _call 用同一把锁包住发送与读取响应，一次只处理一个在途调用，读到相同 ID 才返回。它与普通 SocketClient 的独立读循环加 pending 字典不同。

#### P44.1｜追问：TCP 能直接接一个 MCP HTTP URL 吗？

**标准回答：** 不能。HTTP 有请求方法、头、路径、流式响应等语义，裸 TCP NDJSON 不会自动说 HTTP。代码握手还固定声明旧版本，未完整做版本能力协商。对照 2025-06-18 规范时可区分 stdio 与 Streamable HTTP，但不能把固定版本当作当前所有服务的通用兼容承诺。

#### P44.2｜追问：把锁去掉就能并发调用吗？

**标准回答：** 不行。多个协程争用一个 reader，可能消费别人的响应；要改成单读循环加按 ID 分发的 Future 表，并设计取消、通知、错误和限额。当前每次 readline 都重新计 30 秒，等待锁、写入和多次通知没有统一总 deadline；外层工具的限时也不覆盖所有初始化路径。此外 Python 3.12 的 readline 超限会抛 ValueError，而 MCP _read_line 只捕获 LimitOverrunError，不能保证转成预期的 McpServerUnavailableError；工具 wrapper 的通用捕获可能兜底，但初始化等路径不同。这是异常映射缺口，不是行长限制不存在。

**代码依据：** [McpClient](../../src/kama_claude/core/mcp/client.py)、[指定版本的传输规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)。

### P45｜面试官：MCP 返回 result 就能判断调用成功吗？

**标准回答：** 不能。RPC 顶层 error 是协议/调用错误，result 里面还可能有工具业务错误标志 isError。当前 Client 处理顶层 error，却主要拼接 result.content 的文本，没有完整传递嵌套 isError，也忽略非文本内容。因此业务失败可能被包装成成功文本，这是待修问题。

#### P45.1｜追问：stdio 为什么要一直读 stderr？

**标准回答：** stdout 用于协议，stderr 用于服务诊断。若 stderr 是 PIPE 且无人消费，子进程可能因管道缓冲写满而卡住，继而无法响应协议。Client 的后台 drain 任务消费它；同时要避免把日志写入 stdout 污染 JSON 帧。

#### P45.2｜追问：服务启动失败时怎样避免进程泄漏？

**标准回答：** 当前 initialize 或 tools/list 失败时，客户端可能尚未进入 Manager 注册表，后续 stop_all 无法清理它；close 的 kill 分支也应等待进程回收。我会用明确所有权和 try/finally 关闭未注册资源，测试握手失败、断连与发现失败，并让 close 可重复调用。

**代码依据：** [McpClient](../../src/kama_claude/core/mcp/client.py)、[McpServerManager](../../src/kama_claude/core/mcp/server.py)、[MCP 工具错误语义](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。

## 七、验证与改进

### P46｜面试官：你怎么证明这个项目能工作？

**标准回答：** 我分层验证：单元测试检查消息、状态和策略；假 Provider/工具测试执行接线；真实 TCP 与子进程测试检查 IPC；TUI 测试与手工操作验证交互；真实模型任务另做效果验收。此前提交检查中有 270 项单元/权限集成测试通过与类型检查通过的记录，但不是所有场景覆盖，也不是模型任务成功率。文档编写本身不新增测试通过记录。

#### P46.1｜追问：测试过了为什么还有压缩和后台任务问题？

**标准回答：** 测试只能验证实际断言覆盖的行为。只测摘要生成、单次子任务查询，不会发现“压缩后跨轮保存”或“新 Runner 查询旧后台任务”的组合问题。我要用业务不变式组织跨组件场景，并把每个真实故障变成回归测试。

#### P46.2｜追问：测试假模型有什么价值和盲区？

**标准回答：** 它能确定性地产生工具调用、失败和压缩响应，适合验证控制流与数据一致性，运行快且无需付费。它不证明真实模型会遵守 Schema、正确选工具或得到正确答案，也不覆盖实际服务的限流与格式变化；这些要由契约测试和真实任务评测补充。

**代码依据：** [tests/unit/](../../tests/unit/)、[tests/integration/](../../tests/integration/)、[测试 fixture](../../tests/conftest.py)。

### P47｜面试官：如何衡量成功率、性能与成本？

**标准回答：** 我会固定任务集、验收脚本、模型/提示/工具版本、并发和重复次数，记录完成率、约束违规、首 token 延迟、整轮耗时、token 与工具/压缩次数，保留失败样本。当前没有足够真实基准数据，所以不报提升百分比。IPC ping 吞吐、单模型请求延迟、完整 Agent 任务耗时必须分开测。

#### P47.1｜追问：超时和异常要放进成功率分母吗？

**标准回答：** 应按预先定义的有效任务集计入，不能事后剔除失败样本。环境无效样本的排除规则要事先写明并报告数量。延迟既应报告成功样本分布，也应单列失败/超时，避免只展示幸存任务。

#### P47.2｜追问：如何判断一次改进真的有效？

**标准回答：** 在相同条件下做前后对照，尽量每次只改变一个因素，记录冷/热缓存、随机性和重复次数。比如历史修复先比较漏存/重复的确定性结果，检索或提示优化再比较任务表现。LLM 自动评判需要人工抽查，不能把一次截图当统计证据。

**代码依据：** [UsageStats](../../src/kama_claude/core/llm/types.py)、[Trace](../../src/kama_claude/core/trace/)、[测试目录](../../tests/)。

### P48｜面试官：下一步最优先改什么，为什么？

**标准回答：** 我优先改历史一致性，因为它影响多轮任务是否能继续，且有清晰复现：旧历史长度与压缩后消息列表不再对应。之后补重启会话恢复与后台任务共享服务，把一次执行扩展成连续可用的体验。先完成失败用例、状态与提交设计、最小实现、TUI 接入和验收，而不是一次加入很多无关组件。

#### P48.1｜追问：为什么不马上加入数据库或 RAG？

**标准回答：** 数据库可能帮助事务与索引，但不能替我定义哪份历史是权威、哪个状态可恢复。RAG 解决外部知识检索，也不能修复错误保存。我的顺序是先明确不变式与故障，再选择文件快照或数据库；具体技术应对应具体问题。

#### P48.2｜追问：最小交付和回滚标准是什么？

**标准回答：** 最小交付是原故障测试先失败、修复后通过，正常历史不重复，下一轮读到正确状态，并覆盖写入失败。保留旧文件备份和版本，变更可逐步启用；回滚时能识别新格式，避免旧代码误读。没有完成前，方案只作为设计回答。

**代码依据：** [二次开发大纲](../S8-二次开发改进大纲.md)、[Runner](../../src/kama_claude/core/runner.py)、[SessionStore](../../src/kama_claude/core/session/store.py)。
