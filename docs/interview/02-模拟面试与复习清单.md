# KamaClaude 场景面试：故障排查、设计取舍与标准回答

## 场景与练习方式

版本范围：本套题以 S0–S7 为基线；S8 已合并后的差异见[项目主线的阅读约定](./01-项目面试题与参考答案.md#阅读约定)。故障与改进题中的旧限制不全部代表当前 dev。

你作为 KamaClaude 的项目负责人接受面试。面试官先要求解释流程，再改变一个条件，观察你能否沿代码推导，而不是只重复组件名称。

本篇 **12 个场景，每个有 1 个主问题和 2 个追问，共 36 个问答**。所有问题均给出完整参考口径。当前实现与拟议改进分开；提出方案不代表已经修改代码。

复核说明：SDK 版本和局部实验环境见项目主线的阅读约定。以下区分当前代码故障、替代设计的等待关系与未来方案；局部无网络实验不代表完整回归或真实模型评测。

## 一、从一次请求开始

### S01｜面试官：用户输入“读取 README 并总结”，TUI 一直没显示内容，你从哪里查？

**标准回答：** 我先分清是未连接、请求未响应、模型没返回还是事件没显示。检查 Core 监听地址和 TUI 日志，确认接收循环已启动、订阅与 Session 创建成功。再按请求 ID 查 IPC Trace，看是否进入 session.send_message，按 Run ID 看 RunStarted、模型选择、token 与工具事件。若执行正常而界面没内容，再查广播过滤、客户端回调和 TUI 渲染。没有依据前不会直接改模型提示词。

#### S01.1｜追问：send_command 已调用，为什么 Future 仍一直等？

**标准回答：** 可能接收循环未运行、连接已断、服务 handler 仍执行、请求响应没被正确分发，或 send_command 自身缺少超时。当前方法发送后只等 pending Future，不自己读取响应。要同时看请求是否到 Core、相同 ID 的响应是否回来，而不是只看 write 成功。

#### S01.2｜追问：你怎样区分模型慢与工具慢？

**标准回答：** 我先看最后一个已确认事件，再对照日志与状态。Trace 有模型请求但没有响应，既可能仍在等待，也可能模型已抛异常而 TracingProvider 没记录失败响应，不能仅凭这一点断言模型慢。tool.call_started 没结束可能是工具、审批或前置事件处理出错；出现 permission.requested 则查 pending 和 UI。最后结合 run.finished、RPC 错误与 Core 日志定位，确认记录链路本身没有失败。

**代码定位：** [SocketClient](../../src/kama_claude/core/transport/socket_client.py)、[CoreApp](../../src/kama_claude/core/app.py)、[Trace](../../src/kama_claude/core/trace/)。对应 P04、P11、P17。

### S02｜面试官：TUI 已选择允许，Core 却不继续，可能是什么原因？

**标准回答：** 我沿“UI 消息 → permission.respond → Core handler → Manager.respond → 对应 Future”核对。当前 TUI 会先更新审批控件，再尝试发送决定，发送异常还可能被忽略，因此看到允许不代表 Core 已收到。先查 IPC 请求与响应，再比对 tool_use_id、pending、超时和取消；还要看获准后是否在执行慢工具。当前 SocketServer 已为每条请求创建 Task，不能直接把旧式串行读循环的等待环当成现版本根因。若审批事件处理本身异常，pending 也可能没有进入正常等待路径。

#### S02.1｜追问：如果改成读循环同步等待整个 Run，会形成什么等待环？

**标准回答：** 在这种替代实现中，读取协程等待 send_message handler 结束；handler 等审批 Future；完成 Future 的响应请求又等读取协程继续读，形成循环依赖。当前 create_task 的作用正是让读取与长业务等待分开。这是解释设计必要性的对比场景，不是当前读循环仍同步等待 Run 的证据；并发请求还需任务管理与限额。

#### S02.2｜追问：审批期间断网，当前会怎样，你会如何设计？

**标准回答：** 当前断连没有完整接入 cancel_session；已经进入等待且超时配置大于零时，通常靠审批超时拒绝，设零则不能依赖该兜底。如果登记 Future 后发布事件就异常，尚未进入超时 try，还可能遗留 pending。我的方案是明确审批控制者、让登记/发布/等待都有 finally 清理，在相应控制连接失效时拒绝或取消未执行操作；存在其他有效控制客户端时不能一概取消。未来策略不等于当前已实现断网自动清理。

**代码定位：** [审批 UI](../../src/kama_claude/tui/app.py)、[PermissionManager](../../src/kama_claude/core/permissions/manager.py)、[SocketServer](../../src/kama_claude/core/transport/socket_server.py)。对应 P12、P27。

### S03｜面试官：每条输入都创建新 Runner，第二轮为什么还能知道第一轮内容？

**标准回答：** 历史存在 SessionStore 的 thread.jsonl。SessionManager 先写本轮输入，再通过工厂创建 Runner；新 Runner 读取同一会话历史作为 Context 的 prefill，所以模型能看到前文。Runner 是执行对象，会话存储才承载跨轮数据。Core 内存中的会话索引则负责当前可访问哪些 Session，这与磁盘历史又是不同层。

#### S03.1｜追问：第二轮把第一轮历史又写一遍，会发生什么？

**标准回答：** 文件会重复增长，模型看到重复消息，成本和行为都会受影响。所以正常结束只追加本次新增消息。当前 prefill_len 适合只在尾部追加的路径，但自动压缩替换列表后失效，需要新的提交边界，不能一味沿用同一下标。

#### S03.2｜追问：怎样做最小验证？

**标准回答：** 用临时 SessionStore 和假 Provider 运行两轮，记录第二轮 Provider 收到的 messages，断言第一轮回答和第二轮输入按预期出现且不重复；再读取磁盘验证。分别运行未压缩与强制压缩版本，才能检验保存边界的差异。

**代码定位：** [SessionManager](../../src/kama_claude/core/session/manager.py)、[Runner](../../src/kama_claude/core/runner.py)、[Context](../../src/kama_claude/core/context.py)。对应 P18、P31。

## 二、历史与后台任务故障

### S04｜面试官：自动压缩显示成功，下一轮上下文又很长，甚至刚才的消息没保存，怎么解释？

**标准回答：** 自动 compact 替换运行时 messages 并写 summary 文件，没有直接重写 thread。下一轮 Runner 仍读原 thread，因此原长历史又回来了。同时结束时按旧 prefill_len 对已变短的列表切片，可能漏存后续消息。这是工作历史与持久化协议不一致的两个表现，不能只增加模型窗口解决。

#### S04.1｜追问：请给一个具体数字证明下标错误。

**标准回答：** 开始历史 10 条，记录 prefill_len=10。压缩后两条摘要消息，再产生三条消息，结束总长五条；取 messages[10:] 得到空列表，新增内容没有保存。即使最后长度超过十，下标也不再代表原来的历史边界，仍可能错位。

#### S04.2｜追问：你会怎样修并控制风险？

**标准回答：** 我会把原始记录与模型工作历史区分，显式保存压缩快照版本及其后新增消息，单会话锁内提交权威状态。文件方案先做同文件系统临时写入与替换，再设计备份恢复；多个权威文件需要额外提交协议。用跨轮、重复压缩、写失败和取消验证，不直接全量追加摘要到旧 thread。

**代码定位：** [Compactor](../../src/kama_claude/core/compact/compactor.py)、[Runner](../../src/kama_claude/core/runner.py)。对应 P35、P36、B18。

### S05｜面试官：thread.jsonl 明明有最新输入，模型却总看不到，可能是什么？

**标准回答：** 我先对比磁盘原始行与 read_messages 的返回值。读取会过滤角色、处理坏行、裁剪孤立工具调用并截断长结果。若早先有 tool_use 没有结果，trim 会一直返回最后平衡前缀，后续合法输入也可能一起被裁掉。因此“文件存在这条输入”不证明“Provider 收到了它”。

#### S05.1｜追问：直接删除这段历史可以吗？

**标准回答：** 不应没有记录地删除。先保存原始审计与定位损坏回合，定义可用历史重建边界。可以归档坏片段或加入明确的中断记录，再保留后续合法信息；要防止错误修复伪造工具成功或重复原消息。

#### S05.2｜追问：怎样证明修复不是临时绕过？

**标准回答：** 重复加载修复后的工作历史，并继续运行多轮；断言每轮新增消息都进入模型，工具配对合法，原始坏片段仍可追溯。再测修复中断和重复执行，保证不会每次读取都改出不同历史。

**代码定位：** [SessionStore.read_messages / _trim_orphan_tool_use](../../src/kama_claude/core/session/store.py)。对应 P32。

### S06｜面试官：第一轮启动的后台子 Agent，第二轮返回 Unknown run_id，为什么？

**标准回答：** ID 不一定错，关键是注册表生命周期。Runner 创建 BackgroundTaskRegistry，每轮 SessionManager 又创建新 Runner。第一轮任务登记在旧字典里，第二轮 AgentResultTool 查询新字典，自然找不到。任务可能仍在后台运行，因此查不到也不等于它已经被取消。

#### S06.1｜追问：你会把注册表放在哪里？

**标准回答：** 放到 Core 持有的后台任务服务，显式注入各 Runner，记录会话、父子 Run、任务对象、业务状态和结果。查询检查归属，完成记录有保留规则，Core 退出时统一取消并等待。不能只把字典换成全局变量就结束设计。

#### S06.2｜追问：重启 Core 还能恢复原后台任务吗？

**标准回答：** 不能恢复原 Task 对象。可持久化描述、状态和结果，重启后把未完成任务标为中断；是否重新执行必须由副作用与检查点决定。若需要真正可恢复的工作流，要另设计持久调度与执行协议，当前尚未实现。

**代码定位：** [Runner](../../src/kama_claude/core/runner.py)、[注册表](../../src/kama_claude/core/subagent/registry.py)、[AgentResultTool](../../src/kama_claude/core/subagent/tool.py)。对应 P41。

### S07｜面试官：后台 Task 没有异常，但其实任务失败了，你怎么发现？

**标准回答：** 需要看 Context 的业务状态。AgentLoop 可以捕获模型调用处的普通 Exception，mark_failed 后正常返回，Task.exception 因而是 None；当前 agent_result 没有完整检查 Context.status，可能返回 completed with no text。另外，工具阶段取消独立 Loop 时，Task 已取消而 Context 仍可能 running，查询工具会先命中 Task.cancelled 分支，但其他观察者不能据 Context 误判仍在执行。我会分开管理调度结束、业务结果与取消状态。

#### S07.1｜追问：用异常表示所有业务失败是否更简单？

**标准回答：** 可以制定这种接口契约，但当前代码没有统一如此。业务失败、取消、模型 end_turn 和程序缺陷也未必适合混成一种异常。重点是执行层与查询层契约一致，状态、原因、结果明确，并让 TUI 与父模型都能正确判断。

#### S07.2｜追问：如何测试这个容易漏掉的分支？

**标准回答：** 用假 Provider 抛模型异常，让 Loop 把 Context 标为 failed 后正常结束，等待后台 Task 完成，再调用 agent_result，断言返回失败及原因。还要分别覆盖显式取消、未捕获异常与正常成功，避免只测 task.done 为真。

**代码定位：** [Loop](../../src/kama_claude/core/loop.py)、[AgentResultTool](../../src/kama_claude/core/subagent/tool.py)。对应 P19、P41、B05。

## 三、扩展与资源问题

### S08｜面试官：MCP 工具返回“权限不足”，界面却显示调用成功，哪里有问题？

**标准回答：** 先检查响应层次。顶层 RPC error 与 result 内 isError 是不同语义。Client 当前主要拼接 result.content 文本，如果 isError=true 没传成 ToolResult.is_error，统一执行层就会发布工具完成事件。我会保留两层错误类型并让 wrapper 映射业务错误，而不是靠文本包含“失败”来猜。

#### S08.1｜追问：这种错误应当自动重试吗？

**标准回答：** 权限不足通常不是等待后就恢复的错误，不应按通用 runtime_error 盲目重试。应返回可辨识类型，由用户授权或模型调整方案。网络超时也要判断远端工具是否可能已执行，不能把所有 MCP 失败都当安全可重试。

#### S08.2｜追问：怎样测试又不依赖真实第三方服务？

**标准回答：** 建本地假 stdio/TCP server，完成握手后按脚本返回顶层 error、嵌套 isError、非文本内容、畸形消息或断连。断言模型结果、工具事件与资源回收一致；再用少量真实服务做兼容测试。假服务验证协议处理，真实服务验证实际兼容。

**代码定位：** [McpClient](../../src/kama_claude/core/mcp/client.py)、[McpTool](../../src/kama_claude/core/mcp/tool.py)、[invoke_tool](../../src/kama_claude/core/tools/invocation.py)。对应 P43–P45。

### S09｜面试官：模型不断输出 token，一个客户端很慢，系统会怎样？

**标准回答：** 当前 EventBus 顺序 await，广播器又逐个 writer.drain。慢连接可能拖住后续订阅者和发布协程，影响生成事件的及时处理。Trace 的无界队列则可能在写盘跟不上时增长。要先测慢点，再把客户端缓冲、追踪写入和关键状态的可靠路径分别设计。

#### S09.1｜追问：把每个广播都 create_task 就解决了吗？

**标准回答：** 没有。它可能形成无界任务数、同连接写入顺序难管理和异常无人处理。合理方案是每连接受管发送队列、容量限制与单写者，定义慢消费者处置；token 可合并，审批/结束事件不能随便丢。

#### S09.2｜追问：你会怎样验证没有事件串到其他 Run 文件？

**标准回答：** 同时启动两个带不同 Run ID 的确定性任务，检查各事件文件仅包含约定归属的事件，并验证主子 Run 桥接规则；Run 结束后检查 EventBus 订阅数回到基线。当前 Writer 无 Run 过滤和退订，测试应先暴露问题，再用于验证修复。

**代码定位：** [EventBus](../../src/kama_claude/core/events/bus.py)、[广播器](../../src/kama_claude/core/transport/ipc_broadcaster.py)、[EventWriter](../../src/kama_claude/core/events/writer.py)。对应 P15–P17、B19。

### S10｜面试官：用户要求重启后继续昨天的会话，你的方案是什么？

**标准回答：** 当前能保存文件，但没完整恢复入口。我会先从 meta 恢复 Session 索引与锁，增加会话列表和打开操作，TUI 选择旧会话并加载工作历史。运行中遗留状态标记为中断，再让用户明确继续。事件回放只用于展示，不把历史工具事件当作再次执行的指令。

#### S10.1｜追问：为什么不能把所有旧工具调用重放一次？

**标准回答：** 某些调用可能已经写文件、发送请求或产生不可逆副作用，重放会重复。恢复需要区分计划、实际执行、结果已知和结果未知。第一版恢复对话与结果即可，只有具备幂等或可查证执行记录的步骤才考虑自动重试。

#### S10.2｜追问：一个 meta 文件损坏，Core 应该整个启动失败吗？

**标准回答：** 对可隔离的历史会话，通常可以隔离坏记录并报告，其他会话继续可用；是否失败退出取决于产品约定。要验证 Schema、版本与路径，避免扫描时信任任意文件。备份和修复入口比静默跳过更便于用户理解数据状态。

**代码定位：** [SessionStore](../../src/kama_claude/core/session/store.py)、[SessionManager](../../src/kama_claude/core/session/manager.py)、[TUI](../../src/kama_claude/tui/app.py)。对应 P30、B18、B23。

## 四、设计取舍与效果验证

### S11｜面试官：文件内容要求 Agent 忽略用户并执行危险命令，你怎样处理？

**标准回答：** 我把文件内容视为外部数据，不能让它替代用户授权。模型即使提出危险工具调用，程序仍要查白名单、参数、权限和工作区边界。当前审批与路径检查只能提供部分控制，没有沙箱或完整认证；我会按实际能力描述，并优先收紧强能力工具的执行权限。

#### S11.1｜追问：Skill 和子 Agent 的提示是否能绕过权限？

**标准回答：** 设计上不应允许，但当前白名单存在空列表无限制、子角色未取父权限交集的边界，需要修复注册与继承规则。提示模板不能拥有扩大能力的权限；真正执行检查必须在统一工具路径上生效。

#### S11.2｜追问：如何用安全的自动测试验证？

**标准回答：** 用临时工作区与假工具模拟越界读写、危险命令和越权审批，断言 invoke 没执行、返回拒绝、事件正确，不访问真实私人文件。再覆盖绝对路径、符号链接与 Windows 路径。测试安全策略不需要真的执行危险副作用。

**代码定位：** [权限](../../src/kama_claude/core/permissions/)、[工具执行](../../src/kama_claude/core/tools/invocation.py)、[子工具注册](../../src/kama_claude/core/subagent/tool.py)。对应 P29、P38。

### S12｜面试官：只给你一个迭代，怎样证明改进有价值？

**标准回答：** 我选历史一致性这一具体问题，先保留可复现失败，再定义消息不漏、不重、下一轮使用已提交工作历史的不变式。完成最小修复和异常测试，补一个 TUI 演示。若测真实模型，固定任务与配置，报告成功/失败、耗时和用量；没有结果前不声称某个提升比例。

#### S12.1｜追问：数据库、微服务、多 Agent 都加上，会更有亮点吗？

**标准回答：** 组件数量本身不证明价值。数据库对应事务或查询需求，微服务对应独立部署与规模，子 Agent 对应可分解任务。我要说明它解决的故障、代价和验证数据。当前本地项目先把主链路做好，才有可信的后续扩展依据。

#### S12.2｜追问：请给一句能经得住追问的成果表述。

**标准回答：** 当前可以说“实现本地 Agent 的模型工具循环、事件推送与会话交互，识别并复现压缩保存和后台任务生命周期问题”。完成修复后才替换为“重构压缩工作历史提交，补充跨轮与异常写入回归，验证新增消息不漏存、不重复”。具体采用哪句要看实际交付，性能比例必须有同口径实验。

**代码定位：** [改进大纲](../S8-二次开发改进大纲.md)、[项目验证入口](../../tests/)。对应 P46–P48、B22。

## 五、把答案转成自己的理解

每次练习保留一页记录，包含四项：自己的原回答、漏掉的状态/调用、对应代码、验证结果。下一次先重答同一题，再换追问条件。

| 熟练程度 | 可观察的表现 | 下一步 |
| --- | --- | --- |
| 能辨认 | 看答案觉得熟悉，闭卷讲不顺 | 画一个最小调用链并口述 |
| 能解释 | 能描述正常路径 | 加入取消、失败或重启条件 |
| 能定位 | 能指出具体函数和状态位置 | 用假 Provider/工具验证推断 |
| 能负责 | 能解释取舍、修复并提供证据 | 整理可运行演示与回归记录 |

建议的七次练习：

1. 项目开场与请求链路：P01–P12，练 S01。
