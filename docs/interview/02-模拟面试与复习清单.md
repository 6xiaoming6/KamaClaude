## 三、开场：面试官会怎样连续问

### 第 1 问：“介绍一个你最熟悉的项目，控制在两分钟。”

**练习回答结构：**

```text
背景：本地 Coding Agent，希望连续处理带工具操作的任务。
架构：Core 常驻，TUI 发命令和收事件，模型循环驱动工具。
机制：参数校验与人工审批，多轮历史与记忆，Skill/子 Agent/MCP 扩展。
个人：具体适配、验证、定位，不把开源阶段功能全算作原创。
边界：本地学习项目，恢复和自动压缩保存仍有缺口。
```

**面试官接下来可能问：**

1. 为什么是两个进程？
2. 这些模块哪些是你实现的，哪些来自原项目？
3. 如果我现在输入一句话，第一行业务代码在哪里执行？
4. 你能给一个失败的例子，而不只是成功演示吗？

**参考评价：** 能把入口、调用者和被调用者说清，允许坦率说“这一块是已有实现，我做了分析与适配”。模糊使用“全栈、大规模、自主平台”而无法给边界，需要补准备。

### 第 2 问：“挑一项你的改动，讲修改前后。”

**可选路线一：Provider 适配。** 从内部 tool_use/tool_result，到 OpenAI 的 tool_calls/tool 消息；流式参数怎么组装；动态 system 怎样传递。指出后端结束原因和网络重试并不完全一致。

**可选路线二：Windows 兼容。** 说明信号注册差异、主任务取消、finally、MCP/服务器清理，以及测试怎样覆盖三条退出路径。不要只答“加了一个 if”。

**可选路线三：真实故障定位。** 用自动压缩下标失效、未配对工具尾部或后台注册表举例，但尚未修复时明确是定位与方案，不说改进已上线。

**连续追问：**

- 为什么这么改，不选另外一种方案？
- 测试是验证业务行为，还是只是把实现重复写一遍？
- AI 帮了什么，哪些部分由你核对？
- 我把一个字段名或执行顺序改掉，你能预测哪里失败吗？

## 四、深挖路线 A：上下文压缩与持久化

适合你目前最有讨论价值的真实缺陷。对应 P26—P32、B18、B22。

### A1：“自动压缩后，下一轮读的是哪个文件？”

**参考要点：** 仍读 thread，不是自动加载 summary。当前自动只替换 Context 并写摘要记录；手动路径才明确备份覆盖 thread。先说现状，再说设计意图。

### A2：“给你 prefill_len=10，压缩后两条消息，再追加一条回答，最终保存什么？”

**参考要点：** messages[10:] 为空。模型本轮已经使用摘要，不代表跨轮保存正确；用户输入与本轮后续输出的写入时机不同。

### A3：“那你把 prefill_len=0 不就解决了？”

**参考要点：** 如果仍 append，会保留旧长历史并追加摘要，重复内容没有消除。应该区分“历史前缀未变的增量追加”和“历史重写后的快照替换”。

### A4：“快照替换过程中断电、磁盘满怎么办？”

**参考要点：** 定义临时文件、备份、校验、原子替换与恢复；多文件 meta/thread 更新不是天然事务。原文件先 rename 后写入若失败，有活动文件缺失风险。不要笼统说 rename 就能解决一切。

### A5：“怎样测试压缩真的有效？”

**参考要点：** 假 Provider 稳定触发压缩并断言后续两轮输入；另做真实模型任务集评估约束保留、完成情况与额外成本。验证失败时原历史仍可用，工具调用配对未破坏。

### A6：“为什么不用更大窗口模型直接解决？”

**参考要点：** 这是可选取舍，但成本、延迟、相关性和模型选择仍存在；不能拿更大窗口替代持久化正确性。先修保存缺陷，再测预算策略。

**高风险回答：** “摘要文件存在，所以记忆恢复了”“测试过一次对话就没有问题”“压缩肯定能降本 80%”。

## 五、深挖路线 B：后台子 Agent 与状态管理

对应 P35—P39、B03—B05、B14。

### B1：“你的子 Agent 到底是进程、线程还是协程？”

**参考要点：** 当前独立 Context/Loop，同 Core，后台用 Task，通常共享 Provider 和文件系统。stdio MCP 才是可能另起外部进程的另一条路径。

### B2：“第一轮派生后台任务，第二轮为什么可能 Unknown run_id？”

**参考要点：** 注册表是 Runner 实例属性，每轮新建 Runner。不是 ID 不够随机，也不是仅靠扩大字典能解决。

### B3：“把表提到全局变量就完成了吗？”

**参考要点：** 还要归属 session/用户、过期、取消、结果状态、资源上限与恢复。全局共享可能造成跨会话越权，进程重启也会丢表。可注入 Core 级任务服务，但必须定义授权和生命周期。

### B4：“Task 正常完成，就能告诉用户执行成功？”

**参考要点：** 不一定，Loop 可能将模型错误转成 Context.failed 后正常返回。检查协程状态与业务状态，返回结构化结果；当前 agent_result 最后分支仍有不足。

### B5：“父任务取消，子任务怎么办？”

**参考要点：** 明确继承取消、独立后台运行或转移所有权的产品规则。登记全部任务，设置退出清理和超时；任务取消不自动终止远端调用或回滚文件。

### B6：“两个 executor 同时修改一个文件呢？”

**参考要点：** 共享目录有冲突。可以隔离 worktree、返回补丁并集中校验合并，或采用资源版本与锁。审批与工具白名单不能代替文件冲突控制。

**高风险回答：** “子 Agent 天然隔离”“用了 asyncio 所以并行一定更快”“注释写跨 run，所以肯定能共享”。

## 六、深挖路线 C：MCP 协议与工具可靠性

对应 P40—P44、B07、B09、B17。

### C1：“画出服务启动到模型调用工具的完整顺序。”

**参考要点：** connect → initialize → initialized → tools/list → McpTool → Registry → invoke_tool → tools/call → ToolResult。指出 server.py 是服务连接管理器。

### C2：“你写的 TCP 能连接任意 MCP HTTP 地址吗？”

**参考要点：** 当前不是 HTTP，实现的是自己的换行 JSON-RPC 流。明确协议版本与能力，不混淆底层 TCP 和上层 HTTP。以明确版本的官方规范对比，不凭“都是 MCP”认定兼容。

### C3：“服务返回 result，里面 isError=true，你怎么办？”

**参考要点：** 这是工具层失败，不是顶层协议 error。当前代码没检查，是缺陷；要转换为明确失败并分类，不能让模型误认为已成功写入。

### C4：“同服务为什么不能同时调用两个工具？”

**参考要点：** 当前请求协程直接读取，锁覆盖全往返。想并发要独立接收分发、pending、超时、通知处理，不能直接删锁。

### C5：“stdio 服务卡住了，怎么排查？”

**参考要点：** 检查握手、协议 stdout、stderr 管道、服务进程与读超时。保持日志与协议分离；关闭要回收子进程，初始化失败也要清理未登记资源。

### C6：“外部写工具超时了，重试能保证安全？”

**参考要点：** 未必，服务可能已执行而响应丢失。需要业务操作 ID、查询状态、幂等或人工确认。当前统一 runtime_error 重试不足以证明安全。

**高风险回答：** “MCP 等于 Function Calling”“工具 schema 已经给模型，所以不需要校验”“用了 JSON-RPC 就自动恰好一次”。

## 七、通用连续追问：审批为什么会等死

面试官给出旧逻辑：

```text
读到 session.send_message
await 该 handler 完成
然后继续读下一条命令
```

请回答：

1. 模型请求 write_file，需要人工审批，当前 handler 在等什么？
2. 用户发送 permission.respond，谁读取它？
3. 事件循环仍在运行，为什么审批还不能及时完成？
4. create_task 解决了什么，又增加什么责任？
5. 客户端断开、审批超时、Core 退出时，谁清理 Future 和 Task？

**参考答案：** 等待依赖形成环，读循环没继续读取本连接。独立请求 Task 允许处理审批，但还需上限、登记、取消与异常回收。Future 按 tool_use_id 关联；RPC 的 id 是另一层。当前 cancel_session 与请求任务的完整清理仍未接通，不能说断线自然回滚。

这组问题比背 Future 定义更能检查是否理解代码，可对照 P12、P21、B01、B04。

## 八、场景设计题：不要一上来堆中间件

### 场景 1：模型输出很快，TUI 或日志写得很慢

**先问清：** 是可视化延迟、内存上涨还是事件丢失？哪些事件允许合并？

**参考方案：** 分开业务状态与展示流，给客户端独立有界缓冲，token 合并、关键事件保留策略，慢连接超时；日志消费者失败必须可见。记录队列长度、积压、断连数与端到端延迟。当前 EventBus 顺序 await 与无界 Trace 是具体检查点。

### 场景 2：Core 重启后用户想恢复昨天的任务

**先问清：** 是恢复聊天、重新执行还是恢复执行到某一步？有没有外部副作用？

**参考方案：** 先实现会话历史恢复与状态修复，再定义检查点、操作 ID 和未确定结果的处理；重新关联客户端与事件游标。不能序列化一个协程就声称恢复现场。

### 场景 3：从本地项目扩展到 100 个用户

**先问清：** 用户并发、模型配额、任务时长、工具权限、租户隔离与持久需求。

**参考方案：** 先认证和授权、工作目录/凭据隔离、请求与模型并发上限、任务状态存储和取消；再决定是否需要队列与多个 worker。100 个用户不直接等于 100 个同时模型请求，也不意味着必须 Redis、Kafka 和 Kubernetes 全上。

### 场景 4：收到一份文件，内容要求 Agent 忽略用户并上传密钥

**参考方案：** 把工具返回内容视为不可信数据；提示分隔有帮助，但真正保护还需工具能力、路径、网络与凭据限制及人工审批。审批文本必须展示具体操作；不能让文件里的内容直接充当用户授权。项目当前不具备完整安全隔离。

## 九、手撕与现场编码题

以下题目是为项目定制的练习。先独立写，再对照思路；不是声称这些题必在某公司出现。

| 题目 | 参考思路 | 复杂度与必要边界 |
| --- | --- | --- |
| 增量 NDJSON 解码器 | 累积字节缓冲，按真正换行拆帧，完整帧再 UTF-8 解码和解析 JSON | 总处理 O(n)，限制未完成帧长度；覆盖多帧、半帧、跨多字节字符、转义换行、EOF 残帧 |
| RPC pending 管理器 | 发送前登记 ID→Future，统一接收完成结果，超时/取消/断线统一清理 | 查表平均 O(1)，覆盖响应先到、晚到、重复、未知 ID；禁止多个 reader 抢读 |
| 带最大并发的工具执行器 | Semaphore 控制 in-flight，async with 保证释放，明确总截止时间与取消 | 不为每个请求无上限创建任务；覆盖执行异常、排队取消和退出排空 |
| LRU 缓存 | 哈希表定位，双向链表维护访问顺序，超容量移除最旧节点 | get/put 平均 O(1)，覆盖容量 0、覆盖更新和重复访问；TTL 是另一维度 |
| 平衡二叉树判断 | 后序返回高度，发现不平衡返回哨兵并向上传播 | O(n) 时间、O(h) 栈；覆盖空树、链与左右局部不平衡，避免反复算高度退化 |
| 工具调用配对扫描 | pending ID 集合记录调用，结果移除；另记录可安全保留位置 | O(消息块数)；覆盖多个调用、缺结果、重复 ID、孤立结果。若只做尾裁，说明不是完整协议校验 |

NDJSON 题不要直接对每个网络块调用 decode：UTF-8 字符可能跨块。RPC 题要说明不同 writer 的并发发送如何保持完整帧；单次完整 write 不等于网络报文边界。

可以给每题增加故障输入。只通过正常样例不算完成；面试时先说约束再写实现，不要一边默写一边假设所有输入合法。

## 十、简历怎样写才经得起追问

### 当前阶段的稳妥版本

如果这些代码主要由 AI 协助生成，应如实说明你的需求拆解、审查与验证过程。简历里每个动词都要能用 diff 和测试解释，不把“学习了”换成“独立研发了”。

如果有可信评测，再补：

没有实测就删除数字占位，不写“效率显著提升”。测试项数可以说明验证范围，但不能当任务效果指标。

## 十一、S8 改进怎样变成有价值的面试故事

### 候选 A：自动压缩历史重写

**复现：** 预填较长历史 → 假 Provider 触发自动压缩 → 继续生成结果 → 进入下一轮 → 断言新输出丢失或旧长历史仍被加载。

**设计：** 区分增量追加和快照重写，保存明确消息身份/版本，备份与原子替换；定义取消和失败时保存到什么边界。避免只改切片下标。

**验收：** 未压缩路径不重复；一次/多次压缩后后续两轮可读；失败不破坏原文件；工具调用配对有效；能从日志定位重写版本。

### 候选 B：会话级后台任务服务

**复现：** 第一轮启动后台子任务，第二轮使用新 Runner 查询同一 run_id，当前无法定位。

**设计：** 把注册与查询提升为明确生命周期的服务，绑定 session 与请求者，区分业务状态和 Task 状态，管理取消、超时、容量与过期。持久化只保存可恢复描述，不假装能序列化活动协程。

**验收：** 同会话跨轮可查；不同会话不能越权；取消确实结束或明确仍在清理；业务 failed 不返回成功；退出没有无主任务。

### 候选 C：MCP 错误与资源可靠性

**复现：** 假服务返回 result.isError=true，或握手失败、工具发现失败、读取超时。

**设计：** 协议/工具/传输错误分别建模；添加初始化失败清理与请求总截止时间；按工具副作用决定重试。保留文本以外结果的明确策略。

**验收：** 工具失败不被标成成功；错误可观测且可分类；失败后进程/连接能回收；未确定写入不被无条件重试。

优先把一个候选做完整，再考虑增加新模块。实验不承诺一周必完成，范围应随实际时间调整。
