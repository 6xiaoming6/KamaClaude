# 只读工具受控并行

## 做了什么

原来模型一次返回多个工具调用时，Core 会逐个执行、保存，再处理下一个。现在允许少量无需审批的工作区只读操作同时执行；默认每组最多三个，减少独立读取之间的等待。

主线保持不变：

```text
AgentLoop：推进模型与工具阶段
    ↓
ToolBatchExecutor：按顺序分组、接收结果、保存与收尾
    ↓
invoke_tool：参数、路径、权限、执行意图、执行与受控重试
```

## 怎么分组

内置 `read_file`、`list_dir`、`find_files`、`search_text` 声明 `parallel_safe=True`。其他工具默认关闭。这个后端属性与 `retry_safe` 无关，也不进入模型参数或工具 Schema。

分组还必须满足：调用待执行、工具已暴露、参数合法、实际路径在工作区内、当前权限无需询问。需要审批、参数错误、未暴露或外部路径的调用走原串行入口。

每次最多创建三个调用 Task，等待整组结束后继续。不会先创建整批 Task 再让大量任务等待信号量。

```text
模型声明：read(A), read(B), edit(A), read(C), search(D)

实际执行：并行读取 A/B → 等待完成 → 编辑 A → 等待完成 → 并行读取 C、搜索 D
```

写入、编辑、Bash、MCP、记忆、任务管理、Skill、工具加载和子 Agent 派生继续串行。已有后台子 Agent 仍可独立运行。并发限制属于每个执行器，不提供全 Core 的文件系统快照或写入互斥。

## 执行前仍然检查权限

分组使用权限管理器的只读预判，不创建审批 Future、不写授权缓存。实际调用继续走 `invoke_tool`，传入后端内部选项 `allow_prompt=False`。

真正执行前如果路径越界，或者策略变化导致需要审批，本次返回 `permission_denied`，不在并行 Task 中弹出审批。模型下一次重新调用时会根据新的真实路径和权限重新分组，需要询问时走串行审批。

模型不能通过工具参数伪造 `parallel_safe`、`allow_prompt` 或内部路径批准；这些字段不属于工具参数 Schema。

## 结果乱序完成，如何保存

假设模型声明 A、B，但 B 先完成：

```text
A：executing
B：completed，完整结果及 tool_result 配对消息已保存
tool_index：0，A 尚未完成顺序收尾
```

每个结果都由协调者在同一事件循环中提交，不等整组结束才保存。工具线程不写 Context 或检查点。审批前、执行前的保存钩子绑定具体工具记录，不再用共享游标猜测哪个工具正在执行。

两种历史的职责不同：

- `checkpoint.json` 的模型工作历史：同一批 `tool_result` 按声明顺序排列。B 先出现，A 完成后插入 A 的结果，最终为 A、B；整批处理结束才再次请求模型。
- `thread.jsonl`：逐条追加原始结果，按真实接收完成结果的顺序记录 B、A，不回写旧记录。

`tool_index` 现在表示**最早尚未完成顺序收尾的位置**。完成事实可能先落盘，重复失败计数、无进展检测和游标推进仍按声明顺序一起提交，避免不同完成顺序产生不同保护结果。

输出全文与消息先保存，再生成模型预览。顺序保护产生的后端提醒可补入工作历史，不改写已经记录的原始输出。归档失败后只重新整理结果，不重新执行已完成工具。

## 中断和恢复

1. B 已保存、A 正在执行时，Core 硬退出。
2. 重新打开会话，A 从 `executing` 变为 `unknown`，B 保持 `completed`。
3. 用户确认重试 A，恢复沿用原 Run、Step 和工具记录。
4. 执行 A，复用 B 的结果；按顺序补完保护计数、预览与游标，不再读取 B。

检查点读取允许游标之后存在 `completed`，但必须有保存结果和配对消息。游标之前的工具仍必须是已完成状态。格式版本保持 1；旧串行快照继续可读，旧版本程序不保证能读取新的乱序完成快照。

预算终止和用户终止也逐项检查状态，不能把游标之后已保存的 B 覆盖成“未执行”。TUI 完整列出所有未知调用；“核实后重试”作用于所展示的全部未知项。

## 停止与失败

- Ctrl+C：停止启动下一组，等待已启动的组结束，再由原 Loop 保存用户停止状态。
- Core 取消或时间预算超时：取消并回收该组 asyncio Task；未提交结果沿用现有未知结果处理。
- 检查点保存失败：阻止后续执行意图提交，不启动下一组，回收当前组 Task，不发布未提交的成功结果。
- 单项明确失败：正常记录；达到重复失败或无进展保护时不再调度新组，已保存结果继续保留。

取消 `asyncio.to_thread` 的等待不等于强制终止底层线程，因此不承诺瞬间停止所有文件读取。这里没有加入写工具并发、MCP 只读推断、任务 DAG 或资源锁框架。
