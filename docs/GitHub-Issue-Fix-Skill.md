# GitHub Issue 修复：评测复盘与内置 Skill

## 1. 本次复盘看到了什么

依据本地 `runs/swebench-verified-50/summary.json`、50 份当前 `kama/official-tests-report.json`，以及部分案例的模型最终回复、工具事件、生成补丁和判分测试日志进行分析。没有重跑付费模型，也没有用参考补丁编写 Skill。

| 当前结果 | 数量 | 含义 |
|---|---:|---|
| 已解决 | 32 / 50（64%） | 当前报告的 `resolved=true` |
| 未解决 | 18 / 50 | 当前报告的 `resolved=false` |
| 仍有 FAIL_TO_PASS 失败 | 17 | 新要求没有全部满足 |
| 有 PASS_TO_PASS 失败 | 3 | 原有兼容行为出现回归 |
| 上述两类同时出现 | 2 | 不能把 17 和 3 直接相加 |
| 未解决但 Run 为 success | 18 | 模型正常结束了回复，不代表补丁验收通过 |

50 份当前报告均显示补丁应用成功、`infra_failure=false`，且与汇总的 resolved 值一致。因此这份最终汇总中的失败不能笼统归因于补丁应用失败或当前判分基础设施故障。

**统计边界**：这是用户本地选取的 50 题结果，不是完整 SWE-bench Verified 成绩。样本中 Django 占 32 题；目录包含旧结果、重试和不同执行时间预算，不能据此宣称统一预算下的首次尝试成功率。`before-replacement/` 和尚未跑完的 `budget-1800s/` 也不能混到当前结果中重新计数。最终判分正常，不代表每次中间测试都没有环境问题。

## 2. 主要问题及证据

### 2.1 修复示例，但没有检查完整契约

- `sphinx-doc__sphinx-11510`：示例中的文本替换生效，但事件中的文档名不符合判分断言。说明“页面看起来正确”不能替代事件参数验证。
- `pytest-dev__pytest-10356`：标记继承场景能够工作，但判分直接比较返回值时拿到的是迭代对象，而不是期望的列表。说明值、类型和顺序都可能是接口契约。
- `django__django-15127`：最终回复验证了 Message 的展示变化，但公开的模块状态仍未随配置更新。只修调用链末端，可能留下其他消费者读取旧状态。

Skill 因此要求先列出验收清单，再检查调用方、公开状态、类型、顺序、异常和精确输出等与本题相关的约定，不预设隐藏测试的具体答案。

### 2.2 引入回归，却把它解释为可接受变化

- `django__django-16560`：新增功能对应的 FAIL_TO_PASS 已全部通过，但旧的位置参数行为回归。只跑新功能不能作为最终验收。
- `astropy__astropy-13398`：当前报告同时存在新要求未满足与 5 个 PASS_TO_PASS 失败；模型回复也承认新增的路由一致性失败，却推测测试应该调整。

Skill 要求先保持兼容；新增失败必须调查。不能仅以“这正是预期行为”或“上游大概会更新测试”带过，也不能改弱旧测试制造通过。

### 2.3 测试数量多，但与验收问题没有对齐

未解决案例的最终回复不乏数百、数千项测试通过的陈述。抽查的事件中，`sphinx-doc__sphinx-11510` 有 50 次 `run_tests` 调用，仍漏掉事件参数契约。这里的次数是工具调用数，不等于 50 个有效测试套件；其中也有探测环境和失败命令。

这不证明“大量测试没用”，而是说明应该先运行直接覆盖缺陷的断言，再扩大到相关回归。Skill 要求保留修复前后相同的复现、真实退出码、测试收集数及失败详情，避免只报告“大套件通过”。

### 2.4 无谓环境探测与结论过满

抽查中多次尝试访问测试容器已经移除的 Git 历史；有的回复仍把未确认的输出约定写成“已修复”。Skill 要求确认一次环境限制后转向源码证据，严格区分已验证、未验证、环境阻塞与新增回归。对“既有失败”的判断应有隔离基线对照，不能仅凭错误看起来与改动无关。

这些是基于日志的流程判断，不是对每道题根因的完整复现，也不能保证仅改提示就解决全部 18 题。

## 3. 新 Skill 怎么用

包内模板：[github-issue-fix.md](../src/kama_claude/core/skills/builtin/github-issue-fix.md)。运行时仍使用全局目录：

```text
~/.kama/skills/github-issue-fix/SKILL.md
```

在 TUI 的新一轮消息中输入：

```text
/github-issue-fix 修复下面的 Issue：
现象：……
复现步骤：……
预期行为：……
限制：……
```

也可以要求模型先调用：

```json
{"name":"github-issue-fix"}
```

这是 `load_skill` 的参数，不是新的业务工具。只有一个链接而没有访问能力时，模型应请求补充题面；Skill 本身不新增 GitHub API 或网络访问能力。

新 Run 的 system prompt 只简列 Skill 名称和描述，并要求相关任务先调用 `load_skill(name)`；目录不再放在工具描述中。完整正文通过加载结果进入工作历史。主、子 Agent 共用此规则；白名单未允许 `load_skill` 时，不展示不可用的目录。目录在本轮执行、压缩和恢复中保持冻结，下一 Run 才读取更新。

工作流程：

```text
题面 → 验收条件 → 代码与调用方 → 修复前复现
     → 最小修改 → 同一复现 + 边界检查 + 相关回归
     → 补丁审查 → finish 中报告证据和遗留事项
```

Skill 不替换 system、不扩大工具权限、不增加执行器或强制多 Agent。正文通过既有 Skill 上下文进入模型请求，活动快照仍随检查点保存；恢复不重新读取被修改的磁盘文件。

## 4. 验收要求

- 对照已知需求逐项核对，不能只检查题面中一个示例“不报错”。
- 同一复现在修改前失败、修改后通过；无法建立对照时说明限制。
- 增加针对根因的回归验证，保留接口兼容性；不删除、跳过或弱化测试。
- 查看真实退出码、收集数和失败详情，超时、取消、零测试不是通过。
- 最终检查生产差异和新增文件，保留用户原有改动，清理自己的临时产物。
- 最终回复说明结论、根因与改动、验证证据和遗留事项。有新增回归或核心需求未验证时，不宣称验收成功。

这些要求是模型应遵循的流程，**不是后端新增的强制验收门禁**。`finish` 和 Run 的 success 语义保持不变；要证明修复效果，仍需测试结果或独立判分。

## 5. 已有用户目录如何升级

[loader.py](../src/kama_claude/core/skills/loader.py) 的旧 `.examples-initialized` 是空标记，会阻止后续新增内置示例被安装。本轮改为原子记录已处理的示例名称：

- 首次使用安装五个内置示例。
- 旧空标记视为原四个示例已经处理，只补新增 `github-issue-fix`。
- 已有同名用户文件不覆盖；用户后来删除的示例不自动恢复。
- 标记提交失败明确报错；重试只补齐缺失步骤，不覆盖已经存在的内容。

更新代码并重启 Core，在新 Run 中即可发现新 Skill。已有 Run 的目录与正文快照仍冻结；不要在中断 Run 中静默切换流程。

## 6. 旧评测脚本不会自动使用新 Skill

本地的 `runs/swebench-verified-50/run.py` 通过 `runs/swebench-issue10/issue_eval.py` 调用独立 Runner，并使用自定义 system 与显式工具白名单。该白名单没有 `load_skill`，因此仅新增模板不会改变这份旧评测的行为。

后续做对照实验时，在实验副本中开放 `load_skill`，并在原有约束后明确要求先加载 `github-issue-fix`；模型必须仍能使用评测提供的 `run_tests`。验证日志中实际发生了成功的加载调用，并检查运行快照的 `active_skill`，不要仅凭提示词推断已经使用。原题面、测试工具和评测隔离规则应保持一致。

基线与 Skill 组使用相同题目、模型、预算、重试规则和环境，并分开保存结果；记录加载开销、resolved、回归、耗时与用量。不要让 Agent 读取本次复盘、判分侧日志或参考补丁来解同一批题。此轮没有修改原始评测数据或驱动，也没有进行新增付费模型验证，因此没有“改进后通过率”的结论。

## 7. 实现验证

新增 Issue Skill 与 1M 默认配置后的完整非付费回归为 **1,344 项通过、2 项跳过**，覆盖首次补齐、旧标记升级、同名保护、主动删除、并发初始化、标记失败重试和加载恢复。随后将目录从工具描述迁入 system，相关 **107 项测试通过**，覆盖主子 Agent 白名单、目录冻结、下一 Run 更新、压缩及真实 Core 重启恢复；Ruff、源码 mypy 和协议一致性检查通过。这些验证证明接入与现有流程兼容，不证明模型修复成功率已经提升。
