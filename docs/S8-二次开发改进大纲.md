# S8 改进选题：当前 KamaClaude 的真实问题与可落地方案

> 复核对象：S0–S7 实现，复核日期：2026-11-02。这是一份改进前的问题选题记录。
>
> 2026-11-04 更新：S8 已实现主 Agent 检查点恢复、工具结果不确定时的人工确认，以及压缩历史的持久化。本文中的旧缺陷与建议按原审查时点阅读；当前行为以源码、README 和恢复测试为准，其他候选项不表示已经实现。
>
> 本文是问题分析与实施建议，不表示功能已经完成。只改本文，不修改业务代码。
>
> 目标：选出你能独立解释、能演示改造前后差异、能用实验验证的改进，而不是把所有候选项一起做完。

## 1. 先看结论：哪些值得你做

当前项目已经能跑通“输入 → 模型 → 工具 → 继续推理 → 回复”。更值得深入的地方，是**多轮、并发、中断、外部失败、实际改代码**这些条件出现后，行为是否仍然正确。

旧版大纲把很多事项并列，缺少对选题价值和工作量的区分。新版按下面的标准挑选：

- **实际问题**：能解释用户在什么情况下遇到它。
- **代码证据**：定位到方法和调用链，不能只说“还不够完善”。
- **最小范围**：第一版能做完，不靠堆数据库、消息队列来扩大规模。
- **结果证据**：有失败用例、修复后断言或对照实验。
- **面试深度**：能讨论一致性、并发、副作用、上下文或工具执行等核心设计。

### 1.1 最推荐的三种 S8 选法

| 方案 | 主要解决什么 | 核心条目 | 难度与建议 |
| --- | --- | --- | --- |
| A：可靠的工具执行与可取消任务 | 工具重复执行、停止不彻底、完成状态不可信 | Q01、Q02、Q03，补 Q04 的基本隔离 | 中高；最推荐，容易做出确定性实验，也有完整工程故事 |
| B：可靠的长对话与上下文管理 | 压缩失效、大输出撑爆下一次请求、重启后接不上 | Q07、Q08、Q09、Q10 | 中高；最贴近 Agent 上下文工程，但效果需要真实任务对照 |
| C：可审查的代码修改助手 | 全文件覆盖、修改冲突、没有验证就宣布完成 | Q12、Q13、Q14 | 中高；TUI 演示最直观，也更容易形成自己的产品特点 |

**如果只能选一条，我建议先做 A。** 先稳定复现 Q01 的“工具实际成功，日志/广播失败导致再次执行”，然后打通“运行 → 审批 → 执行 → 取消 → 收尾”。这条主线能体现你对 Agent 执行可靠性的理解。

## 2. 本轮实际验证了什么

环境为本地 Python 3.12.0。使用假 Provider、假 StreamWriter、假进程以及临时目录；没有调用真实模型，没有执行真实 shell 命令，没有启动真实 MCP 服务。

| 实验 | 注入条件 | 当前实际结果 |
| --- | --- | --- |
| E01 | 工具成功返回；首次处理 tool.call_finished 的订阅者抛异常 | 工具执行 2 次，最终 ToolResult 为成功 |
| E02 | 假模型正常结束；让 append_messages 抛出磁盘错误 | 已收集到 run.finished(success)，历史中只有 user 消息 |
| E03 | 假进程 communicate 挂起时，取消 BashTool.invoke 所在 Task | Task 被取消，进程 kill 调用次数为 0 |
| E04 | task_update 添加自身 ID、另一个任务 ID、999，再构造反向依赖 | 自依赖、环、不存在的依赖均被接受；仍可进入 in_progress |
| E05 | 对很短输入返回更长摘要，stop_reason=max_tokens | 压缩结果仍被接受；粗估原文 0 token，摘要 199 token |
| E06 | 前一响应 context_pct=0.1，工具返回 100000 字符，阈值 0.8 | 压缩调用次数为 0，下一模型请求包含 100227 字符的 messages 表示 |
| E07 | 向 TUI 路由器依次传入 Run A 和 Run B 的 token | 两者被追加到同一个文本块 |
| E08 | 当前会话为 A，传入 B 的 session.waiting_for_input | A 对应界面的 busy 被改为 false |
| E09 | 第一个订阅者的 drain 等待，第二个订阅者正常 | 第二个订阅者尚未写入，发布协程仍未完成 |

这些结果的含义要准确理解：

- E03 证明**取消路径没有清理调用**，没有证明所有操作系统上的所有子进程必然残留。
- E06 证明**没有为新增大结果做预算检查**，没有实际向模型发送超窗请求，也没有测真实 token 数。
- E07/E08 验证事件路由方法，尚未跑两个真实 TUI 的端到端演示。
- E09 使用可控的 drain 等待来复现阻塞，不代表普通小消息广播必然慢。
- 以上是针对性行为实验，不是完整回归测试，也不是模型任务成功率评测。

## 3. 执行可靠性：优先值得修的核心问题

### Q01：工具已成功，却可能因“通知失败”被重新执行

**使用场景。** Agent 执行一个有副作用的命令，命令已经修改文件；随后通知界面的订阅者出错，工具被重试。用户可能看到重复追加、重复创建或重复提交。

**代码原因。** [invoke_tool](../src/kama_claude/core/tools/invocation.py) 把工具执行和成功事件发布放在同一个 try 中：

```python
try:
    result = await tool.invoke(params)
    if not result.is_error:
        await bus.publish(ToolCallFinishedEvent(...))
        return result
except Exception:
    error_class = "runtime_error"

# runtime_error 属于可重试类型
```

[EventBus.publish](../src/kama_claude/core/events/bus.py) 不隔离订阅者异常。因此不是工具失败，也可能进入重试。E01 已复现工具执行两次。

此外，Bash 非零退出被映射为 runtime_error。如果命令先写入文件、再因其他步骤失败，当前通用重试也可能重复前半段操作。这与通知异常是两条不同的触发路径。

**第一版怎么改。**

1. 把“工具执行结果”和“事件投递结果”分开处理；通知失败不得自动触发工具重执行。
2. 工具声明副作用与重试策略，例如只读操作、可重复写入、有不确定副作用的操作。不要仅靠一个 runtime_error 决定全部重试。
3. 外部操作结果不确定时返回明确状态，例如 outcome_unknown，交由查询/人工确认；不能直接假定失败。
4. 同一次逻辑操作保留 operation_id，不同尝试增加 attempt。需要去重时，执行记录与外部服务的幂等能力配合使用。
5. 不要把新增一个本地字典当作“保证 exactly-once”：进程崩溃或远端已执行但响应丢失，仍然存在不确定窗口。

**验收。** 工具成功、事件异常时执行次数仍为 1；有副作用工具在结果不确定时不自动重试；只读工具的可恢复错误仍遵守次数和退避；最终结果可查询。

**面试深挖。** “执行成功但响应丢了，你怎么区分？为什么重试可能产生重复副作用？你的幂等保证到哪一层？”

### Q02：取消协程不等于停止它启动的进程

**使用场景。** Agent 正在运行长命令，用户停止任务，Python Task 被取消，底层 shell 或它创建的进程却没有受控退出。

**代码原因。** [BashTool.invoke](../src/kama_claude/core/tools/builtin/bash.py) 只在内部 TimeoutError 分支调用 kill；外部 CancelledError 没有对应 finally 清理。E03 的假进程验证中 kill 调用为 0。

需要一起看 [CoreApp](../src/kama_claude/core/app.py) 和 [SocketServer](../src/kama_claude/core/transport/socket_server.py)：Core 的 _running_runs 主要登记 agent.run 启动的任务；session.send_message 与连接分发创建的任务没有统一纳入同一运行管理服务。解释器退出时可能取消其他任务，但这不能替代应用自己的收尾协议。

**第一版怎么改。**

1. 建立 RunHandle，记录 Task、取消信号、当前阶段、所持资源和终态。
2. 增加 run.cancel；TUI 增加停止入口，不靠关闭整个 Core。
3. 先进入 cancelling，停止发起新模型调用与工具调用，再清理已有工具。
4. Bash 在取消、超时和普通异常中执行统一回收；先请求终止，超过宽限期再强制结束，并等待进程回收。
5. 区分“直接 shell”和“进程树”。Windows 与 POSIX 使用各自适合的机制，不能以杀掉一个 PID 宣称清理全部后代。
6. 权限等待、模型流、MCP 调用各自定义取消语义；取消后已经产生的外部副作用不承诺撤销。

**验收。** 分别在等待审批、模型流输出、工具运行、后台子任务中取消；Run 最终状态确定；会话锁释放；无 pending 审批；受管进程在规定时间内退出；后续能继续发起新 Run。

真实进程实验应在临时目录运行受控测试程序，记录其 PID；不要对用户机器上的任意进程做探测性 kill。

**面试深挖。** “cancel() 后为什么还要 await？CancelledError 在哪层处理？用户取消和工具超时的区别是什么？”

### Q03：界面显示完成时，对话可能还没有保存

**代码原因。** [AgentRunner.run_and_capture](../src/kama_claude/core/runner.py) 当前顺序为：

```text
loop 结束
→ publish RunFinishedEvent
→ 关闭 EventWriter
→ store.append_messages(...)
→ 返回 RunOutcome
```

E02 注入保存失败后，成功事件已经发出，磁盘只有用户输入。

**改进目标。** 明确区分“模型执行完成”“结果已保存”“客户端已收到”。三者不能用同一个 completed 含糊表示。

**第一版怎么改。**

- 先保存权威结果，再发布表示“已提交完成”的通知。
- 执行成功但保存失败时保留 execution_status 与 persistence_status，给 TUI 明确提示；不要为了补存历史重跑已经执行过的工具。
- 提供 run.get 查询权威终态，推送只是通知。否则通知丢失后客户端仍然不知道结果。
- 文件方案先用同目录临时文件与替换保证单文件可见性，再考虑多文件对账；需要跨记录事务时再选择数据库。
- 进程崩溃的一致性与断电后的持久性不是同一保证，文档应写清楚承诺范围。

**验收。** 保存失败不展示“已保存完成”；提交成功但推送失败，重连查询仍能获得结果；重复查询不触发执行；写入中断后能识别不完整 Run。

**面试深挖。** “为什么不先推送再落盘？先落盘后推送也可能失败，怎么恢复？”

### Q04：观察 Agent 的客户端，反过来能阻塞 Agent

**代码原因。** 当前调用链：

```text
Provider 收到 token
→ await bus.publish
→ await broadcaster.handle
→ 对客户端逐个 writer.write + await writer.drain
→ 才能继续读取模型流
```

[广播器](../src/kama_claude/core/transport/ipc_broadcaster.py) 没有为每个连接独立排队，也没有 drain 超时。缓冲区达到背压条件后，一个不再读取的客户端可能挂住整条发布链。E09 已验证慢订阅者阻止后面的正常订阅者收到事件。

另外 [EventWriter](../src/kama_claude/core/events/writer.py) 没有 Run 过滤，关闭后不退订；共享总线下，多个活跃 Writer 会收到其他 Run 的事件。

**第一版怎么改。**

1. 每连接建立有界发送队列，由独立发送任务写 socket。
2. 发布路径只做短时间入队；定义满队列策略，不能换成无界队列。
3. token 可合并成小批量；终态、审批等事件不能静默丢弃。投递失败可以标记断线，让客户端查询状态补齐。
4. 为观察类订阅者隔离异常；关键持久化失败要明确传播或记录，不能一律吞异常。
5. 订阅返回释放句柄，Writer 结束即退订，并按 Run/子 Run 归属过滤。
6. 保持每个 Run 内部事件顺序；不承诺所有并发 Run 的全局顺序。

**验收。** 慢客户端不显著拖慢快客户端；队列长度有上限；连续多次 Run 后订阅数回到基线；并发 Run 文件不串事件。性能收益需用相同消息量、相同延迟注入条件对照。

**面试深挖。** “为什么异步 await 仍会形成串行阻塞？有界队列满了怎么办？哪些事件允许合并？”

## 4. 前端状态：当前不只是显示问题

### Q05：不同会话和子 Agent 的输出会相互干扰

**代码原因。** [TUI._socket_loop](../src/kama_claude/tui/app.py) 使用 scope=global；_handle_event_inner 对 llm.token 使用单个 _current_llm，没有按 run_id 选择文本块。session.waiting_for_input 和 session.closed 也没有先检查是否为当前会话。

E07 证明不同 Run 的 token 进入同一块；E08 证明其他会话的 waiting 事件会改变当前 busy 状态。

**具体影响。**

- 开两个 TUI 时，可能看到对方的运行输出和审批。
- 同一会话父子 Agent 同时输出，文本可能拼接成含义错误的回答。
- 另一会话结束，可能提前把当前会话界面切成 ready。后端锁可能仍拒绝请求，所以不意味着后端一定并发执行，但前后端状态已不一致。

**第一版怎么改。**

- Core 维护 session → run → parent_run 的归属关系，让订阅支持会话范围。
- UI 只处理选中会话的事件；文本使用 (run_id, message_id/attempt) 定位，不再共用单一流块。
- 子 Agent 单独展示；父 Run 是否完成不由子事件决定。
- 审批增加连接身份/控制权校验。仅在前端过滤事件，不能保证其他客户端无法代为审批。
- 这里服务于本机多窗口使用，不必立刻扩展成网络多租户系统。

**验收。** 两会话同时运行，输出、busy、审批互不干扰；父子 token 交错仍归属正确；后台子任务完成不会重置当前输入状态。

### Q06：工具重试成功了，TUI 可能仍然显示失败

**代码原因。** invoke_tool 在重试前发 tool.call_failed，带 attempt；但是 [TUI](../src/kama_claude/tui/app.py) 一收到该事件就从 _pending_tool_blocks 中 pop 对应工具块。后续成功事件找不到原工具块，无法更新。ToolCallStartedEvent 当前在整个重试循环外发布一次。

**第一版怎么改。**

- 协议明确 tool.attempt_failed、tool.retry_scheduled、tool.finished，或增加 terminal 字段；名字可选，语义必须明确。
- 同一个逻辑调用的 UI 块保持到终态；展示“第 1 次失败，准备重试”，成功后显示最终结果和尝试次数。
- 与 Q01 配合，只对允许重试的工具展示该流程。
- 模型流重试也要类似处理：当前 AnthropicProvider 仅首次尝试发布 token，后续成功文本不会自动补回 TUI。需要“重置该次输出”或“用最终全文对齐”的协议。

**验收。** 假工具第一次失败、第二次成功，最终 UI 显示成功；最终失败仅结算一次；中途取消显示 cancelled；模型流重试后显示文本与保存文本一致。

**面试深挖。** “一次逻辑调用和一次执行尝试是什么关系？事件到达不完整时前端从哪里恢复权威状态？”


## 5. 上下文与会话：把“能够压缩”变成“压缩后能继续”

### Q07：压缩后保存下标失效，孤立工具调用也会持续截断历史

**代码原因。** [Runner](../src/kama_claude/core/runner.py) 记录 prefill_len，最后追加 context.messages[prefill_len:]；[Compactor](../src/kama_claude/core/compact/compactor.py) 把 messages 换成摘要两条。

例如原历史 10 条，压缩后 2 条，再追加 3 条，总数 5。保存 [10:] 得到空列表。即使后续总数超过 10，也只是偶然保存某一段，并不能恢复正确边界。

[SessionStore._trim_orphan_tool_use](../src/kama_claude/core/session/store.py) 只在读取时裁剪：如果磁盘某个 tool_use 一直没有配对，后面正常对话也可能持续被裁掉。不能只修自动压缩，忽略历史修复。

**第一版怎么改。**

1. 将原始交互记录和模型工作历史分开：前者用于追溯，后者用于下一轮请求。
2. 消息有稳定 ID，工作历史有 generation/version；压缩生成新快照，不能继续用旧数组长度表示增量。
3. 原始消息记录带 run_id，压缩摘要记录覆盖的消息区间，避免重复追加。
4. 同会话锁内提交快照；失败保留旧版本并报告。多份文件需要明确提交标记和恢复规则，或使用事务存储。
5. 孤立工具调用采用明确修复：归档损坏段、补“中断/结果未知”状态或重建合法边界；不能捏造成功结果。
6. 自动压缩、手动压缩、正常结束、取消统一走保存协议。

**验收。** 一次/连续多次压缩后新增消息不丢；新 Run 确实加载摘要；原始记录仍可追溯；历史有坏尾部时，修复后新消息可正常读取。

**不要这样修。** 直接把 prefill_len 改成 0，再向原文件追加全部压缩历史，会重复信息，也不能消除旧的长历史。

### Q08：自动压缩时机太晚，预算也没有覆盖完整下一次请求

**代码原因。** [AgentLoop](../src/kama_claude/core/loop.py) 在工具执行后检查上一轮 response.usage.context_pct。这个比例对应刚刚完成的模型请求，不包含之后加入的工具结果。

当前 [budget.py](../src/kama_claude/core/compact/budget.py) 的截断主要在 SessionStore.read_messages 时使用，不能保护本次 Run 中刚拿到的巨大结果。E06 中新结果超过 10 万字符，下一次请求前没有压缩。

还有两个入口：

- 开始 Run 时，系统提示、项目记忆、笔记、工具 schema 和历史合起来可能已经太长。
- 工具结果被截断后没有统一的内容引用和续读机制，重要错误可能在被删掉的后半段。

**第一版怎么改。**

```text
每次模型请求前：
  构造 system + tools + messages
  估算当前输入，并预留输出空间和安全余量
  若超预算：
    先处理低价值/超长工具结果
    再压缩旧历史，保留关键约束与近期完整工具回合
    重新检查；仍超限则给明确错误，不盲目发送
  发送请求
```

- 估算要按 Provider/模型能力配置，字符数只能是带误差的兜底。
- 真实 usage 用于校正后续估算；不能把上次比例当下一次输入大小。
- 超长输出保存为 artifact，返回摘要、路径/ID、总长度和读取方法。先补按行读取/搜索即可，不必为了这个问题引入向量数据库。
- ReadFile 当前先 read_bytes 全读再切片；Bash 先 communicate 收全再截断。因此“返回有上限”不等于“峰值内存有上限”，需要实际分块读取和受控落盘。
- 把 config 中截断字段传到真正执行位置，增加配置行为测试。

**验收。** 短历史+巨量新结果、长系统提示、多工具 schema、无 usage 返回均受控；输出不足时能继续按需读取；对比请求大小和峰值内存，不能只比返回字符串长度。

**面试深挖。** “为什么调用后拿到的 usage 不足以防止下一次超窗？为什么压缩也可能无法处理已经过大的输入？”

### Q09：摘要没有“值得替换原历史”的检查

**代码原因。** [Compactor.compact_messages](../src/kama_claude/core/compact/compactor.py) 只要 response.text 非空就接受，没有检查 stop_reason、压缩收益和关键内容。E05 中比原文更长、stop_reason=max_tokens 的输出仍然被接受。

原文使用字符粗估，摘要可能使用模型 usage；两种口径混在一起，saved_tokens 也不能被当作精确节省量。

**第一版怎么改。**

1. 完成状态与结构先校验，输出截断时不直接替换权威历史。
2. 原文和摘要使用同一估算器比较，明确最低压缩收益；保留估计值与实际 usage 的区别。
3. 原目标、明确约束、未完成事项、关键文件与操作结果拆成结构化字段；近期完整工具回合尽可能直接保留。
4. 摘要失败保留原历史；若原历史已超预算，返回可处理状态，采用分段摘要/用户介入，而非无穷重试。
5. 对事实保留做独立测试。格式正确、字数变少并不代表没有失真。

**验收。** 空摘要、截断摘要、变长摘要不替换原文；指定关键约束在压缩后保留；构建“压缩前给约束，压缩后执行任务”的测试集，比较遗漏率、重复执行率、成本和延迟。

**学习价值。** 可以做“全部摘要 / 摘要+近期回合 / 结构化事实+近期回合”三组对照。固定任务和模型配置，多次重复；数据不足时报告样本，不宣布普遍提升。

### Q10：有历史文件，不等于支持恢复；回放与实时流之间也可能漏事件

**代码原因。**

- [SessionManager](../src/kama_claude/core/session/manager.py) 初始化空 _sessions，查询只查内存。
- TUI 每次重连重新 session.create。
- [CoreApp._subscribe_handler](../src/kama_claude/core/app.py) 先 _replay_events，之后注册实时订阅。回放最后的 drain 一旦挂起，此时新产生的事件可能不在已读取文件快照中，也尚未进入该客户端订阅。
- 目前没有用于断点续传的事件序号。上面的竞争窗口需要真实集成测试，不应说每次回放都会漏。

**第一版怎么改。**

1. 会话元数据可重建索引，提供 list/open/history；坏记录单独隔离。
2. TUI 保存会话 ID，重连先恢复已有会话，随后同步正在运行、已结束、待审批状态。
3. 每会话或每 Run 维护单调递增序号；客户端记录最后处理位置。
4. 回放和实时流通过“先接入实时缓存、确定回放水位、回放后合并去重”等协议衔接；简单交换两行顺序也可能制造重复与乱序。
5. 重启后原协程和外部操作不会自动恢复；未完成 Run 标为 interrupted/unknown。恢复历史与重放工具是两个动作。

**验收。** 重连不创建重复会话；回放期间持续发事件，无缺失且重复可去除；重启后能打开旧会话；已结束 Run 查询正确；未完成操作不会静默重执行。

**取舍。** 第一版可以只做“恢复历史+查询当前状态”，不承诺每个 token 都能精确补齐。明确能力范围，比实现一个不可靠的全量重放更有价值。

## 6. 子任务与实际改代码：能形成产品特点的方向

### Q11：后台子 Agent 缺少跨轮生命周期

**代码原因。** [AgentRunner.__init__](../src/kama_claude/core/runner.py) 每次创建 BackgroundTaskRegistry；SessionManager 每轮创建新 Runner。因此注释里的“跨 run 共享”没有在正常会话调用链中成立。

[AgentResultTool.invoke](../src/kama_claude/core/subagent/tool.py) 检查 Task 是否结束、取消或异常，但没有继续判断 context.status。Loop 因 exceeded_max_steps 等原因失败、协程正常返回时，查询结果仍可能是普通成功 ToolResult。

**第一版怎么改。**

- Core 持有共享子任务服务，Runner 注入引用；记录 session_id、父子 Run、状态、结果、时间。
- 区分协程结束和业务成功，定义 queued/running/succeeded/failed/cancelled/interrupted。
- 支持跨轮查询、取消、结束回收、结果保留期限；不同会话检查归属。
- 加并发额度与整个任务树预算。max_steps 和嵌套深度不能限制总子任务数量。
- TUI 提供任务树与结果页；完成后通知父会话。是否自动再次唤醒父 Agent，要单独设计，第一版可由用户选择继续。
- 子 Agent 第一版只读分析，由父 Agent 写文件；后续需要并行修改，再引入独立 worktree 和冲突检查。

**验收。** 第一轮启动慢子任务、第二轮查询成功；超步数不能显示成功；关闭会话/退出 Core 时按明确策略取消或保留；历史任务不会使注册表无限增长。

### Q12：多个会话共享 Core 工作目录，项目边界不明确

**使用场景。** 从项目 A 启动 Core，再从项目 B 启动 TUI，工具不会因为客户端目录改变就自动在 B 工作。不同会话也没有独立 workspace。

**代码原因。** Session 模型没有工作区绑定；[ReadFileTool](../src/kama_claude/core/tools/builtin/read_file.py)、[WriteFileTool](../src/kama_claude/core/tools/builtin/write_file.py) 使用 Path(path_str)，Bash 没有显式 cwd；[Runner](../src/kama_claude/core/runner.py) 读取项目记忆时使用相对路径。当前语义取决于 Core 的进程 cwd。

文件工具主要拒绝路径中的 ..，没有统一拒绝绝对路径或解析后逃出根目录的链接；这与描述中的“相对路径”不完全一致。

**第一版怎么改。**

1. 创建会话时绑定规范化 workspace_root，TUI 明确显示。
2. 每个工具收到显式 ToolContext，携带工作区、Run、审批服务等。
3. 文件路径以工作区为基准解析，判断实际目标归属；项目记忆、Skill 加载也基于该工作区。
4. Bash 使用 subprocess 的 cwd 参数。**不要在并发服务里用 os.chdir 切换会话目录**，它改变整个进程的状态。
5. 授权按工作区+工具+操作范围保存，提供撤销；“始终允许”不能只让用户看到一句话而不知道影响范围。
6. 如需对任意 shell 命令建立强隔离，再选择操作系统层沙箱；路径检查与正则审批不能等价于沙箱。

**验收。** 两个临时工作区同名文件，两个会话分别读取和修改正确目标；绝对路径、符号链接/目录联接、相似前缀、Windows 路径按声明策略处理；授权不会无意扩散到其他项目。

### Q13：修改一个函数也要覆盖整个文件，且缺少版本冲突保护

**现状。** [WriteFileTool](../src/kama_claude/core/tools/builtin/write_file.py) 只支持 path+content 全量覆盖；[审批预览](../src/kama_claude/core/permissions/policy.py) 对 write_file 主要展示路径。用户很难在允许前看清删了什么、改了什么。

这是适合 Coding Agent 的功能增强。要证明收益，应在固定代码修改任务集上测量，不能先假定新增 patch 工具必然提高成功率。

**第一版目标：从“让模型写完整文件”改为“提交可审查的局部修改”。**

```text
read_file 返回内容 + 文件版本/hash
→ 模型提交局部补丁
→ Core 校验目标与预期版本
→ TUI 展示 diff
→ 用户批准
→ 应用前再次检查版本
→ 原子写入并保存变更记录
→ 运行约定验证
```

**实现步骤。**

- 先做单文件精确替换：old_text 必须唯一匹配；不存在或多处匹配则拒绝并让模型重读。也可选择统一 diff，但要正确处理应用失败。
- 基线 hash 防止模型读完后用户修改文件，Agent 再把用户新内容覆盖。
- 校验、预览、审批、应用绑定同一个补丁摘要；审批后文件变化也必须使旧批准失效。
- 同目录临时文件替换，考虑编码、换行和权限元数据。
- 撤销时同样检查当前版本，避免回滚覆盖用户后来修改。
- 多文件补丁的原子性、跨 Agent 合并放第二版；单文件写入原子不等于全项目事务。

**验收。** 修改单函数不改变其他内容；目标不唯一时拒绝；审批期间用户改文件后发生冲突；撤销只撤自己的变更；Windows CRLF 与中文文件保存正常。

**面试深挖。** “为什么 diff 审批后还要检查 hash？原子替换解决什么，不解决什么？两个 Agent 修改同一文件怎么办？”

### Q14：模型说“完成”与代码真的修好之间没有验证层

**代码原因。** [AgentLoop](../src/kama_claude/core/loop.py) 在 response.stop_reason=end_turn 时直接 context.mark_success。它表示模型结束当前回复，不能证明需求已满足。

普通问答可以允许这种结束语义；对于“修复这个 bug 并通过测试”，缺少可执行验收标准就无法可靠判断。这是产品设计缺口，不是要求每个自然语言任务都有万能判题器。

**第一版怎么改。**

1. 区分 execution_completed 与 verification_passed。
2. 任务开始时约定验收方式：指定测试、构建命令、文件差异约束等。
3. 模型提出完成后，运行受控验证器，返回结构化结果。
4. 验证失败将关键信息反馈给 Agent，最多修复 N 轮，受总预算和取消机制约束。
5. 不允许模型为了“通过”而任意改验收用例；记录测试基线与测试变更。
6. 对无法自动验收的任务标记“待人工确认”，不要伪造验证成功。

**验收。** 模型提前结束但测试失败时不显示 verified；通过测试后保留命令、退出码与结果；预算用尽有明确终态；测试环境错误与代码失败分开记录。

**适合展示的实验。** 选择一组小型临时仓库任务，每题有独立验收脚本，比较“直接 end_turn 结束”和“验证后有限修复”的完成率、额外成本、耗时和误报率。

### Q15：Task 依赖现在只是松散字段，不是可信的任务图

**代码原因。** [TaskManager.create](../src/kama_claude/core/task/manager.py) 创建时检查依赖存在，但 update(add_blocked_by=...) 没有对应检查；没有拒绝自身依赖、环，也未阻止带未完成依赖的任务进入 in_progress。E04 已复现。

完成任务会从其他任务的 blocked_by 中删除其 ID。依赖关系因此变成可变的“剩余阻塞列表”，不适合直接用作可追溯的完整 DAG。

另外 TaskManager 存在 Run 目录下，多轮会话默认不共享同一任务清单。是否改为会话级需要明确产品目标。

**可以做两个层次。**

- **轻量修复**：保留清单语义，校验 ID、自依赖、环，定义状态转移规则；文档说明不会自动调度。
- **较完整增强**：依赖边与任务状态分开存储，派生 ready 状态；任务在会话内持续存在，再接入有限并发调度。

**验收。** 自依赖和环被拒绝；不存在 ID 被拒绝；未完成依赖不能进入受管执行；完成/重开任务后的就绪状态一致；跨轮清单按约定保留。

**优先级。** 适合做规划能力练习，但如果主线是 A，先别把它扩成复杂 DAG 引擎。依赖合法不代表模型拆解出的任务合理。


## 7. 外部能力与可观测性：值得配套修的部分

### Q16：MCP 的“请求成功”和“工具执行成功”被混为一谈

**代码原因。** [McpClient.call_tool](../src/kama_claude/core/mcp/client.py) 只拼接 result.content 中的 text，未保留 result.isError。[McpTool.invoke](../src/kama_claude/core/mcp/tool.py) 拿到字符串即返回普通 ToolResult。

因此 JSON-RPC 返回 result、其中工具实际失败时，项目可能把错误文本作为成功工具输出。这里是当前适配代码丢失字段，不需要真实调用付费服务才能检查。

其他边界：非文本内容被忽略；_call 持锁等待完整响应，同一客户端调用串行；_read_line 的 30 秒是每次读取超时，不是包含排队、写入、通知循环的整个调用截止时间。

**第一版怎么改。**

- 让客户端返回内部结构化结果：content、is_error、structured_data/artifacts，而不是直接压平成字符串。
- 明确区分连接失败、协议错误、工具业务失败、结果不确定；重试遵循 Q01 的副作用策略。
- 设置总截止时间，并定义等待连接锁是否占用预算；不要因为不断收到通知就无限延长。
- 启动失败清理已创建的连接/进程；kill 后等待回收。
- 先保持串行实现也可以，只有证据表明有吞吐需求时，再加单读循环和 pending future 做并发多路复用。
- 本地参数校验需遵循所支持的 schema 能力；当前 params_model=None 不等于动态 JSON Schema 已被验证。

**验收。** 假 MCP 返回 isError=true 时得到失败 ToolResult；非文本返回有明确表示；通知持续到来时总超时仍生效；初始化失败无残留资源；连接断开时不重试不确定写操作。

**面试深挖。** “HTTP/JSON-RPC 成功为什么不代表业务成功？串行锁的作用是什么？如何避免多个协程抢读同一条流？”

### Q17：Skill 看起来展开了参数，模型实际收到的却可能还是模板

**代码原因。** [SessionManager.send_message](../src/kama_claude/core/session/manager.py) 先把原始 /skill args 写入历史，然后把渲染后的字符串放到 goal；但 system_prompt_override 赋的是未渲染模板。

[ExecutionContext.__post_init__](../src/kama_claude/core/context.py) 有 prefill_messages 时优先用历史，不再自动追加 goal。因此 normal session 路径中，已渲染的 goal 不保证进入模型请求。

另一个问题：skill.allowed_tools or None、Runner 的 if tool_whitelist 使空列表和“不限制”混同。必须先定义空列表语义，再修实现，而不是默认所有配置都应该改变含义。

**第一版怎么改。**

1. Skill 解析在构建有效模型输入前完成；原始用户指令与展开后的输入分别记录。
2. 模板只在一个地方渲染一次，明确它属于 system 还是 user，不依赖不同构造路径碰巧注入。
3. 使用 None 表示未配置，[] 表示不授予工具（如果采用此语义，旧配置需迁移说明）。
4. 父能力范围、角色白名单、用户审批取交集；派生子 Agent 不能通过默认配置重新获得父 Agent 没有的能力。
5. "/" 或空白命令返回可理解错误，不能在写入用户消息后因 parts[0] 越界中断。

**验收。** 假 Provider 捕获的 system/messages 中有展开参数、无未替换占位符；空白名单的结果符合约定；只读角色的子 Agent 不获得写工具；未知 Skill 和空输入行为明确。

**定位。** 适合做一个独立小里程碑；如果只修模板替换，不必包装成“完整插件平台”。

### Q18：Trace 很多，但出错时仍可能无法回答“发生了什么”

**代码原因。**

- [TracingProvider.chat](../src/kama_claude/core/trace/provider.py) 在 await inner.chat 前后分别记录；中间抛异常时，没有对应失败/取消记录和结束耗时。
- api_call 的 data 持有 messages 等可变对象，队列写盘前内容可能已改变；记录应代表调用当时的快照。
- [TraceWriter](../src/kama_claude/core/trace/writer.py) 队列无界，消费者中同步 write/flush；后台任务失败后，剩余队列可能无人消费，stop 的 queue.join 不能自行处理这种情况。
- 每次请求会再记录完整上下文，长会话下存储开销可能增长很快。具体大小需要实际量化。
- 关闭 include_llm_payload 只影响这层载荷；其他事件和 IPC Trace 仍可能包含输入、工具参数或输出，不能将它当成全局脱敏开关。

**第一版怎么改。**

1. 每次调用分配 call_id/attempt，正常、失败、取消均有结束记录；并保留父子 Run 关联。
2. emit 前生成快照或完成序列化，验证修改原 messages 不会改变旧记录。
3. 有界队列、批量写入、可诊断的消费者失败；stop 设置有界等待并报告未写数量。
4. 统一 UTF-8；按大小或时间保留文件；大载荷采用受控 artifact 引用。
5. 脱敏按字段/来源统一处理，测试消息、命令输出和工具结果等不同入口。
6. 加可查询的指标：模型耗时、工具耗时、审批等待、重试数、取消耗时、token 用量。先用简单报表或 TUI 页面即可。

**验收。** 模型异常与取消有完整记录；模拟慢写盘时队列不无限增长；写盘失败不会无限卡住退出；调用快照稳定；统计能按一次 Run 汇总。

**面试深挖。** “日志、事件、Trace 分别解决什么？为什么异步写入仍可能阻塞？采样和丢弃会影响哪些排障结论？”

## 9. 如何把选题做成能写进简历的成果

### 9.1 方案 A 的建议实施顺序

| 阶段 | 交付内容 | 必须证明的事情 |
| --- | --- | --- |
| A0：故障基线 | Q01/Q02/Q03 最小复现，记录版本 | 原行为可稳定复现，不依赖模型随机性 |
| A1：执行与通知分离 | 重构 invoke_tool 的异常边界、工具重试策略 | 观察者失败不会重执行已成功工具 |
| A2：运行管理 | RunHandle、终态查询、取消、资源清理 | 不同阶段可取消；锁、审批、受管进程正确回收 |
| A3：提交与推送 | 权威结果先保存，推送失败可查询补齐 | 保存失败和通知失败不会被混同 |
| A4：TUI 与事件 | 正确状态、停止按钮、Run 隔离、必要背压 | 用户能看清正在重试、正在取消、已结束且是否保存 |
| A5：验证报告 | 确定性回归、受控进程集成、演示 | 每个设计结论都有对应证据和边界 |

先做 A0–A2 就有一个可审查的阶段成果；之后再完善其余部分。不要因为文档列了 18 项，就一次性重构 18 项。

### 9.2 方案 B 的完成边界

至少完成以下闭环：

```text
模型调用前预算
→ 大工具输出按需取回
→ 合格摘要与近期回合
→ 工作历史持久化
→ 下一 Run 继续
→ TUI 显示当前上下文与恢复状态
```

结果证据包括：历史完整性测试、摘要质量对照、请求 token/成本/延迟。摘要策略的“更好”必须限定在你的测试任务和模型配置中。

### 9.3 方案 C 的完成边界

至少完成以下闭环：

```text
绑定项目
→ 读取文件和基线版本
→ 生成局部补丁
→ 审查 diff
→ 校验版本后应用
→ 自动验收
→ 失败反馈与有限修复
→ 变更报告/安全回退
```

第一版先支持单文件修改与一类测试命令；之后再扩大到多文件、并行子 Agent 和复杂项目。这个规模已经足够讨论文件冲突、审批有效性、测试可信度与预算。

### 9.4 测试分层：每一层分别说明了什么

1. **确定性单元测试**：假 Provider/工具/Writer 注入异常，证明状态机、重试和数据逻辑。
2. **本地集成测试**：真实临时文件、受控子进程、TCP、TUI，证明组件接线与平台行为。
3. **真实模型任务评测**：固定任务集、模型配置、预算和验收脚本，证明在这些条件下的任务表现。

不要用“单测通过”代替“模型确实更会改代码”，也不要用一次成功演示代替异常路径验证。

建议评测记录字段：

```text
case_id / baseline_or_improved / commit / os / dependency_versions
provider / model / model_parameters / task_input / acceptance_script
execution_status / verification_status / failure_category
model_calls / tool_calls / retries / token_usage / elapsed_time
artifacts / trace_reference
```

统计 token 和价格时保留厂商字段语义，价格使用实验时配置。没有测过的成功率、节省比例和并发量不填。

## 10. 现在就能开始的第一步

建议从 Q01 开始，范围足够小，又直接触及 Agent 最重要的执行语义：

1. 注册一个假工具，每次执行让 counter 加 1，返回成功。
2. 订阅完成事件，第一次故意抛异常。
3. 调用 invoke_tool，断言 counter 应为 1。当前实现会到 2。
4. 修复异常边界后，确认该断言通过。
5. 再加入“工具已产生副作用、自己返回 runtime_error”的用例，设计默认不自动重试的策略。
6. 最后在 TUI 展示执行结果与通知故障，说明“任务做成了，通知失败”如何查询和恢复。

这一步完成后，再决定是否延伸到方案 A，或者把这项基础修复作为方案 C 的依赖。你应当能够解释每个断言为什么成立，而不只是看到测试变绿。
